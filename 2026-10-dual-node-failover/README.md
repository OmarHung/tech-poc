# 雙機備援機制

- 狀態：已完成
- 開始日期：2026-10-30
- 結論：有條件可行（三種架構、三種語言的結果一致；條件見最後一節）

## 背景與目標

驗證兩台機器組成備援架構時，其中一台故障，服務能不能繼續，而且資料不遺失。

兩台機器怎麼分工，常見有三種做法，這個 PoC 三種都做：

| 架構 | 兩台之間 | 掛一台時 | 例子 |
|------|---------|---------|------|
| **A. 主備＋資料同步** | 主機把資料同步複寫給備機 | 備機升格接手 | 資料庫（PostgreSQL + Patroni、SQL Server Always On） |
| **B. 熱熱備援** | 不通訊；兩台都處理每一筆，下游去掉重複 | 不用切換，另一台本來就在做 | 兩台都收同一份行情或設備資料、各自計算 |
| **C. 上游指派** | 不通訊；上游把每件工作派給其中一台 | 上游把沒做完的工作改派給另一台 | 任務佇列加 worker（SQS、RabbitMQ、job table） |

三種架構都用 .NET、Rust、Python 各實作一次，行為和 HTTP 介面完全相同：.NET 版先做，Rust、Python 版照著它移植。所有架構都用同一支跟語言無關的黑箱腳本製造故障並量測結果。

## 要驗證的假設

- **架構 A**：任一台故障時，服務可以在目標秒數內自動切換，切換過程資料遺失量在可接受範圍，故障機器修好後也能安全加回來。
- **架構 B**：兩台不通訊、各自處理每一筆時，掛掉任一台不會漏掉任何結果，服務也不會中斷；代價是每一筆都做兩次，下游必須能去掉重複。
- **架構 C**：兩台不通訊、由上游指派工作時，掛掉或凍結任一台都不會漏掉工作，只有它手上那件會延遲；代價是少數工作會做兩次。

## 待釐清問題

**架構 A：主備＋資料同步**

- [x] **備援模式**：主備（Active-Standby）。同一時間只有一台接受寫入，另一台同步複寫。雙主（Active-Active）要處理兩邊同時寫同一筆資料的衝突，不在這次範圍。
- [x] **故障偵測**：用租約（lease），不用「幾秒沒心跳就判定死亡」。主機每 0.5 秒向 witness 續約，租約 3 秒，續約失敗也要等租約到期才換人。實測 20 秒的網路抖動（最長斷線 1.16 秒）：3 秒租約在三種語言都沒有誤判；改成 1 秒租約，三種語言都誤判一次（.NET 重跑 5 次有 4 次）。
- [x] **切換方式**：前面放 gateway，每 100ms 問兩台的 `/health`，把請求轉給回報自己是主機的那台。這是 HAProxy + Patroni 常見的做法。虛擬 IP（keepalived / VRRP）在單機 macOS 上做不出來，沒有驗證。gateway 本身是單點，正式環境要用 VIP 或雲端 load balancer。
- [x] **資料同步**：同步和非同步都量了，數字見實驗紀錄。
  - 同步：RPO = 0，寫入延遲會多出 1 到 2 個網路來回。
  - 非同步：寫入很快，但主機崩潰會丟掉最後一小段寫入。在 10 ms 鏈路上，三種語言各丟了 3–12 筆，都是崩潰前十幾毫秒內確認的。
  - 兩種模式的 RTO 一樣，都約等於租約長度。
- [x] **腦裂（split-brain）**：需要第三方仲裁，而且實測差很多。
  - 有 witness：腦裂情境下 0 筆衝突。
  - 只靠兩台互相心跳：網路分區時兩邊都當主機，恢復後有 3,231–3,429 筆「已經回覆 client 成功」的寫入消失（三種語言）。
  - witness 掛掉時服務不受影響（實測 0 筆失敗），因為主機只要拿到 3 票中的 2 票（自己＋備機）就能繼續。
- [x] **故障回復（failback）**：全自動，不用人工處理。
  - 舊主機重啟後發現有更新的 epoch，就以備機身分加入。
  - 它會丟掉跟新主機分歧的 log。這些都是當初沒回覆成功的寫入。
  - 追上進度後，witness 重新把它標記為可以接手。
  - 實測加回來的節點可以再接手一次，兩次切換合計 0 筆遺失。

**架構 B：熱熱備援**

- [x] **結果不能漏**：上游保留所有事件（像 Kafka 一樣可以重讀），每台自己記住讀到哪裡、算到哪裡（檢查點）。掛掉的那台重啟後從檢查點補讀：停機 3 秒間的約 600 筆，從下重啟指令算起 0.12–0.54 秒就補完（含程式啟動，三種語言），最後的帳戶餘額跟正確答案完全一樣。網路斷 3 秒的情況也一樣，恢復後 0.11–0.60 秒補完。
- [x] **重複怎麼處理**：每一筆兩台都會送一次，下游以事件編號去重，只套用第一份。實測約 1,500 筆事件，下游收到約 2,600–2,700 份；沒有去重的話，副作用（例如寄信、扣款）會多發生約 1,100 次（三種語言）。
- [x] **兩台結果不一致怎麼辦**：處理必須是決定性的，同樣的事件、同樣的順序，要算出同樣的結果。實測兩種常見的錯：
  - 重啟時直接從最新的事件開始，沒有補讀：餘額少了停機期間的事件，之後的結果跟另一台不一致（400–422 筆）；等另一台也掛了，下游就開始套用錯的結果（451–625 筆）。
  - 結果裡帶了本機時鐘：只有 3–4% 的事件不一致，因為兩台常在同一毫秒處理同一筆；機器負載一高，比例就變（Rust 版開發時量到 1%–39%）。這種偶發的不一致最難發現，下游先收到誰的就用誰的。
- [x] **中斷多久**：不用偵測、不用切換。掛掉一台時，下游最長 13–14 ms 沒有新結果，跟平常一樣。
- [x] **上游不能丟歷史**：這個架構假設上游可以重播。實作裡的上游只存在記憶體，如果它重啟、事件編號從頭開始，worker 會停下來報錯，不會把新事件當成舊編號處理。正式環境的上游必須是持久化的（Kafka 之類）。

**架構 C：上游指派**

- [x] **工作不能漏**：上游把每件工作租給一台 worker（租約 2 秒），worker 每 0.67 秒送一次心跳延長租約。worker 不再心跳，租約到期後工作放回佇列最前面，改派給另一台。實測砍掉正在做事的 worker，那件工作 2.34–2.35 秒後由另一台完成（三種語言），其他工作照常。比租約還長的工作（3 秒）靠心跳延長租約，0 次被誤判改派。
- [x] **被凍結的 worker**（長時間 GC、VM 暫停）：恢復後還以為工作是自己的，會把結果再寫一次。解法跟架構 A 的主機一樣：worker 以送出請求的時間起算租約、提早結束，寫結果前先檢查，而且寫結果這個呼叫的逾時不超過剩下的租約。實測凍結 4 秒：有檢查時 0 次重複寫入，不檢查時多寫 1 次。但這擋不住「檢查完、請求已經送出去」之後才被凍結的情況，這段空窗很短，但存在。
- [x] **活著但做不完的 worker**：worker 連不到下游、但心跳照常送到上游時，租約會一直被延長，另一台永遠接不到這件工作。心跳只能證明 worker 活著，不能證明它做得完。解法是 worker 寫不出結果超過一個租約就主動放手，**而且放手後先停止接新工作，等下游恢復**（斷路器）：不然它會一件接一件地卡，甚至接回剛放掉的同一件（它往往是等最久的那台）。實測那件工作 4.48–4.55 秒後由另一台完成，被卡住的只有這 1 件。
- [x] **重複無法完全避免**：worker 做完、寫了結果，但回報完成時斷線，上游只能當作沒做完，改派給另一台，這件工作就做了兩次。實測 1 件工作做了兩次，下游只套用一次。所以下游一定要能去重。
- [x] **下游的 fencing 擋不住所有重複**：下游可以拒絕比已收到的還舊的 attempt。實測那次剛好新的先到，所以擋下了 1 筆晚到的結果；但如果舊的那份先到，就沒有東西可比，它會被套用。要真正擋住，寫結果和檢查租約必須在同一個交易裡（例如 job table 的 `UPDATE … WHERE id = ? AND attempt = ?`）。這次的做法是讓結果可以重現、以工作編號去重，讓重複變得無害。

## 範圍外

- 跨機房 / 跨區域備援
- 三台以上的叢集架構（witness 只投票、不存資料，不算第三個資料節點）
- 真實的多台機器與網路：全部在一台 Mac 上跑，網路故障用 TCP 代理模擬
- 斷電：寫入只送到作業系統，沒有 fsync。這次只模擬「程序被砍掉」（kill -9）
- 時鐘漂移：主機把租約提早 10% 結束來容忍漂移，但沒有實際製造時鐘誤差
- 虛擬 IP 與 gateway 本身的備援
- 真正的資料庫：資料存在自己寫的 append-only log，不是 PostgreSQL 或 SQL Server
- 驗證與授權：所有程序只綁 `127.0.0.1`。正式環境的 `/internal`、`/admin` 和 witness 一定要加身分驗證（例如 mTLS）
- 架構 B、C 的上游（事件流水帳、任務佇列）和下游都是單一程序，資料只在記憶體。正式環境的上游是 Kafka、SQS 這類本身就有備援的系統

## 技術選型

| 項目 | 選擇 | 理由 |
|------|------|------|
| 實驗環境 | 單機多程序，加上自己寫的 TCP 代理 | 節點之間的連線都經過代理，可以斷線（封包直接消失，連線卡到逾時，跟真實分區一樣）或加延遲，程式本身不知道有人在搞破壞 |
| 故障偵測與切換 | witness 租約 + epoch（fencing token），前面放 gateway | witness 是 2 台機器做到「多數決」的最小成本；epoch 讓被換掉的舊主機寫不進去 |
| 資料複寫 | 自己寫的 append-only log，Raft 式的 log matching，可切同步或非同步 | 要看清楚每個步驟、能量測，所以自己做；機制跟現成方案一一對應（見下表） |
| .NET | ASP.NET Core 10 Minimal API、YARP 2.3（gateway 的轉發）、xUnit | 跟[模組化單體 PoC](../2026-10-modular-monolith-to-microservices/) 相同 |
| Rust | axum 0.8、reqwest 0.13、tokio 1.54，Rust 1.98（edition 2024） | 同上 |
| Python | FastAPI 0.162、httpx 0.28、uvicorn（uvloop），Python 3.12，uv 管理 | 同上。單執行緒的 asyncio 不用鎖，但「檢查後動作」中間不能有 `await` |
| 驗證 | Python 標準函式庫寫的黑箱腳本 | 不依賴實作語言，三種語言跑同一套情境，數字才能比較 |

| 這次的做法 | PostgreSQL + Patroni | SQL Server Always On |
|-----------|----------------------|----------------------|
| witness 租約 | 存在 etcd / Consul 的 leader key（有 TTL） | 叢集仲裁（file share / cloud witness） |
| epoch | timeline | — |
| 「備機同步中才准升格」 | synchronous mode 的 `sync_standby` | 同步認可模式的 SYNCHRONIZED 狀態 |
| 舊主機丟掉分歧的 log | `pg_rewind` | 重新同步資料庫 |

| 這次的做法 | 現成方案 |
|-----------|---------|
| 上游的事件流水帳，每台自己記讀到哪 | Kafka：兩台各用不同的 consumer group，各自記 offset |
| worker 的檢查點（讀到哪＋算到哪） | Kafka Streams 的 state store 加 changelog、Flink checkpoint |

| 下游以編號去重 | 資料表 unique key、冪等鍵（idempotency key）、`INSERT … ON CONFLICT DO NOTHING` |

## 做法

### 架構 A：主備＋資料同步

```
                      client
                        │
              gateway :8100   每 100ms 問兩台 /health，轉給 role=primary 的那台
               ┌────────┴────────┐
        node a :8101        node b :8102     主機：接受讀寫，同步複寫給備機
               │ ◀── 複寫 / 心跳 ──▶ │       備機：只接收複寫
               └──── witness :8103 ───┘      只存三個欄位：epoch、誰拿租約、備機是否同步中
```

驗證時，節點之間、節點到 witness 的連線都經過 TCP 代理（`a->b` :8111、`b->a` :8112、`a->w` :8113、`b->w` :8114）。client 和 gateway 直接連節點。

機制：

1. **誰是主機**：拿到 witness 租約的節點。每換一次主機，epoch 就加 1。所有複寫訊息都帶 epoch，備機看到比自己舊的 epoch 一律拒絕，被換掉的舊主機因此寫不進去（fencing）。
2. **主機一定比別人先放手**：主機以「送出續約請求的時間」起算租約，再提早 10% 結束。witness 那邊的租約到期時，主機早就停止服務了。
3. **witness 掛掉不影響服務**：備機每次接受複寫，就等於承諾「3 秒內不去搶主機」。主機只要 witness 的租約或備機的承諾其中一個還有效，就能繼續服務。這等於 3 票中拿到 2 票，所以 witness 單獨掛掉，或備機單獨掛掉，都不會讓主機停下來。
4. **什麼時候才回 200**（同步模式）：寫入要等備機收到才回覆成功。如果備機超過 1 秒沒回應，主機先請 witness 記下「備機不同步，不准升格」，witness 確認後才自己確認寫入。如果 witness 也連不到，就回 503，不冒險確認。
5. **寧可停機也不丟資料**：witness 只會把租約交給同步中的備機。如果備機已經落後，主機又在這時掛掉，叢集會停止服務，等主機回來。
6. **舊主機回來**：舊主機看到更新的 epoch，就轉成備機。它用 (index, epoch) 跟新主機逐筆比對 log，丟掉分歧的部分，再補上缺少的資料。追上進度後，新主機通知 witness「備機同步中」，它就又能接手了。

程式怎麼運作（含可以點選情境的互動流程圖、一筆寫入經過哪些檔案和函式），每種語言各有一份，用瀏覽器直接打開：[.NET](./dotnet/how-it-works.html)、[Rust](./rust/how-it-works.html)、[Python](./python/how-it-works.html)。

HTTP 介面：

| 方法與路徑 | 誰提供 | 說明 |
|-----------|--------|------|
| `PUT /kv/{key}` `{"value": "..."}` | 節點（透過 gateway） | 寫入，回 `{key, value, index, epoch}`。不是主機回 503 |
| `GET /kv/{key}` | 節點（透過 gateway） | 讀取。只有主機能讀，而且只回已經安全的值 |
| `GET /health` | 三者都有 | 節點會回 `role`、`epoch`、`peer`（`in-sync`／`solo`／`catching-up`）等 |
| `POST /internal/replicate` | 節點 | 主機送給備機的複寫和心跳 |
| `GET /admin/data` | 節點 | 這台節點目前持有的全部資料，驗證腳本比對用 |
| `POST /lease`、`POST /sync` | witness | 取得／續約租約；回報備機是否同步中 |

- 錯誤一律回 `{"error": "..."}`：400 輸入錯誤、404 找不到、409 witness 拒絕、503 不是主機或無法安全確認寫入
- 每個回應都帶 `X-Served-By`（`node-a`、`node-b`、`witness`、`gateway`）

設定（環境變數）：

| 變數 | 預設 | 說明 |
|------|------|------|
| `ARBITER` | `witness` | `none` 是對照組：沒有 witness，備機 3 秒沒聽到主機就自己升格 |
| `REPLICATION` | `sync` | `async`：寫進本機就回 200，背景再複寫 |
| `LEASE_TTL_MS` | 3000 | 租約長度。RTO 大約就是這個數字；節點和 witness 要設一樣 |
| `RENEW_INTERVAL_MS` | 500 | 續約與心跳的間隔，也是每次呼叫 witness／備機的逾時 |
| `REPLICATION_TIMEOUT_MS` | 1000 | 同步寫入等備機多久，超過就請 witness 允許單獨確認 |
| `ELECTION_DELAY_MS` | 0 | 搶主前多等一下。只在沒有 witness 時有用，作用類似 keepalived 的 priority |

### 架構 B：熱熱備援

```
             verify（產生事件）
                   │
          upstream :8120   事件流水帳：只能附加，可以從任何位置重讀
            ┌──────┴──────┐
     worker a :8121   worker b :8122   各自讀全部事件、各自算餘額、各自存檢查點
            └──────┬──────┘             兩台之間沒有任何連線
             sink :8123    以事件編號去重：第一份套用，其他只計數
```

1. 每台 worker 從自己的檢查點位置往後讀事件（一次最多 100 筆），依序更新帳戶餘額，每筆送一個結果到下游：`event-<編號>` → `帳戶:餘額`。
2. 一批全部送完，才把讀到的位置和餘額存成檢查點。如果在中間被砍掉，重啟後會重送這一批，下游當成重複忽略，不會漏。
3. 掛掉的 worker 重啟後從檢查點補讀。另一台照常運作，完全不知道發生了什麼事。
4. 下游收到同一個事件編號的第二份結果：內容相同就是重複，不同就是衝突（保留第一份並計數）。

### 架構 C：上游指派

```
             verify（產生任務）
                   │
          upstream :8120   任務佇列：每件任務租給一台，租約 2 秒
            ┌──────┴──────┐
     worker a :8121   worker b :8122   租任務 → 定時心跳 → 做事 → 寫結果 → 回報完成
            └──────┬──────┘
             sink :8123    以任務編號去重
```

1. worker 向上游要任務，沒有任務時最多等 0.5 秒。上游把佇列最前面的任務租給它，attempt 加 1。
2. 做事期間每 1/3 個租約送一次心跳（固定間隔，每次呼叫最多等一個間隔，卡住一次不會拖垮下一次）。上游回「租約已失去」，或 worker 自己算出租約到期（從送出請求的時間起算，提早 10% 結束），就放棄這件工作，不寫結果。
3. 先寫結果到下游，再向上游回報完成。寫結果的逾時不超過剩下的租約；連不到下游超過一個租約就放手，並在下游恢復前不接新工作。回報前斷掉，上游會把任務改派出去，所以是 at-least-once。
4. 上游每 0.1 秒檢查一次租約，到期的任務放回佇列最前面，讓等待中的 worker 馬上拿到。

架構 B、C 的檔案（以 .NET 版為例，Rust、Python 版一一對應）：

| 檔案 | 內容 |
|------|------|
| `dotnet/src/Upstream/EventLog.cs` | 事件流水帳：附加、從任何位置讀、沒有新事件時等一下 |
| `dotnet/src/Upstream/TaskQueue.cs` | 任務佇列：租約、心跳、完成、到期改派 |
| `dotnet/src/Worker/HotHot/HotHotWorker.cs`、`Ledger.cs` | 熱熱模式：讀事件、算餘額、送結果、存檢查點 |
| `dotnet/src/Worker/Dispatch/DispatchWorker.cs`、`LeaseTracker.cs` | 指派模式：租任務、心跳、檢查租約、寫結果、回報完成 |
| `dotnet/src/Sink/ResultStore.cs` | 下游：去重，記錄重複、衝突、過期的 attempt |
| `verify/independent.py` | 架構 B、C 的故障情境 |

HTTP 介面：

| 方法與路徑 | 誰提供 | 說明 |
|-----------|--------|------|
| `POST /events` `{"account", "amount"}` | upstream | 附加事件，回 `{seq, account, amount}` |

### 怎麼跑

需要 .NET 10 SDK、Rust 1.85 以上、Python 3.12 以上加 uv。架構 A 用到 port 8100–8103、8111–8114，架構 B、C 用到 8120–8123、8131–8134。

```bash
./verify/run.sh dotnet                  # 或 rust、python：建置 → 依序跑全部情境（約 8 分鐘）
./verify/run.sh rust crash partition    # 只跑指定情境

```

每個情境都從全新的叢集開始：
- 架構 A：用 4 個 client 持續寫入（每個 key 只寫一次）。製造故障後，比對「client 收到 200 的寫入」和「叢集最後持有的資料」。

### 2026-10-31：架構 A，三種語言的結果

**功能驗證**

| 語言 | 黑箱驗證 | 單元與整合測試 | 其他 |
|------|---------|---------------|------|
| .NET | 12 個情境、50 / 50 項檢查 | 107 個，行覆蓋率 88.8%（不算三個 `Program.cs` 是 92.1%） | 建置 0 警告 |
| Rust | 12 個情境、50 / 50 項檢查 | 150 個 | clippy 無警告；沒有安裝 cargo-llvm-cov，未量覆蓋率 |
| Python | 12 個情境、50 / 50 項檢查 | 195 個，覆蓋率 99% | ruff 無警告 |

三種語言在同一台機器上依序各跑一輪（不同時跑，避免互相搶 CPU），都用預設設定：租約 3 秒、續約 0.5 秒、同步複寫、4 個 client 持續寫入。逐項結果在 `verify/results/<語言>-<情境>.json`，下面的表由 `python3 verify/scenario.py compare` 整理。

**1. 安全性：三種語言完全一樣**

| 情境 | .NET | Rust | Python |
|------|------|------|--------|
| 主機崩潰兩次（切走再切回）：遺失 ／ 確認的寫入 | 0 ／ 6,598 | 0 ／ 6,438 | 0 ／ 5,363 |
| 網路分區、有 witness：兩台同時確認 ／ 遺失 | 0 ／ 0 | 0 ／ 0 | 0 ／ 0 |
| 網路分區、有 witness：舊主機丟掉的未確認寫入 | 8 | 8 | 8 |
| 網路分區、**沒有 witness**：兩台同時確認 | 1,376 | 1,377 | 1,417 |
| 網路分區、**沒有 witness**：遺失的已確認寫入 | **3,344** | **3,429** | **3,231** |
| witness 掛掉 6 秒：失敗的寫入 | 0 | 0 | 0 |
| 備機落後時主機又掛：遺失（主機單獨確認的寫入） | 0（1,572） | 0（1,500） | 0（1,253） |
| 訊息晚到：遺失 ／ 備機有沒有接手 | 0 ／ 沒有 | 0 ／ 沒有 | 0 ／ 沒有 |

- 有 witness 時，被隔離的舊主機在斷線後一筆都沒確認；網路恢復後丟掉的 8 筆都是從沒回過 200 的寫入。
- 沒有 witness 時，被隔離的舊主機只覺得「備機連不到」，就自己繼續確認寫入；備機以為主機死了，也自己升格。兩邊各自確認了上千筆，網路恢復後 epoch 較舊的那邊整批被蓋掉，client 不會收到任何通知。
- 「備機落後」情境：備機先掛，主機單獨確認寫入；接著主機也掛，只有落後的備機先回來。witness 拒絕讓它接手，服務停擺到主機回來為止。

**2. 可用性：由租約長度決定，跟語言無關**

| 指標 | .NET | Rust | Python |
|------|------|------|--------|
| 主機崩潰：RTO | 3.29 秒 | 3.49 秒 | 3.11 秒 |
| 切回修好的節點：RTO | 3.49 秒 | 3.38 秒 | 3.41 秒 |
| 網路分區：新主機開始服務 | 3.28 秒 | 3.03 秒 | 3.05 秒 |
| 租約改 1 秒：RTO | 1.14 秒 | 1.23 秒 | 1.18 秒 |
| 舊主機重啟到追上進度（含程式啟動） | 0.39 秒 | 0.17 秒 | 0.37 秒 |
| 備機落後時的停機（等主機回來） | 11.7 秒 | 11.1 秒 | 11.5 秒 |
| 沒有 witness 時備機自己升格 | 4.80 秒 | 4.99 秒 | 4.65 秒 |

RTO ＝ 租約 3 秒＋選主迴圈每 0.5 秒才檢查一次＋gateway 輪詢，所以落在 3.0–3.6 秒之間。三種語言的差異只是剛好落在這個區間的哪裡，重跑也會變動。客戶端看到的空窗跟 RTO 幾乎一樣。

**3. 誤判切換（網路抖動 20 秒）**：主機的所有對外連線隨機斷線 0.2–1.5 秒（實際 3 次，最長 1.16 秒），或加 20–200 ms 延遲（5 段）。抖動的順序固定（固定亂數種子），三種語言遇到的是同一場「天氣」。

| 租約 | .NET | Rust | Python |
|------|------|------|--------|
| 3 秒：誤判切換 ／ 失敗的寫入 | **0** ／ 4 | **0** ／ 4 | **0** ／ 4 |
| 1 秒：誤判切換 ／ 失敗的寫入 | 1 ／ 116 | 1 ／ 59 | 1 ／ 122 |

.NET 版另外重跑過：3 秒租約 3 次都是 0；1 秒租約 5 次中有 4 次切換。租約越短 RTO 越小（3.3 秒 → 1.2 秒），但斷線長度一接近租約，就會被當成主機死掉。就算誤判切換了，也沒有遺失或腦裂：安全性不靠租約長度，靠 epoch 和 witness。

**4. 寫入延遲：同步 vs. 非同步**（4 個 client 同時寫，主機崩潰前的量測）

| | .NET | Rust | Python |
|---|------|------|--------|
| 同步、本機 loopback：p50 ／ p99 | 0.94 ／ 2.03 ms | 1.61 ／ 4.39 ms | 3.48 ／ 7.10 ms |
| 非同步、本機 loopback：p50 | 0.44 ms | 0.84 ms | 2.55 ms |
| 同步、節點之間單程 10 ms：p50 ／ p99 | 40.5 ／ 48.3 ms | 42.6 ／ 49.1 ms | 46.4 ／ 53.7 ms |
| 非同步、節點之間單程 10 ms：p50 | 0.38 ms | 0.73 ms | 2.53 ms |
| 非同步、本機 loopback：崩潰時遺失的已確認寫入 | 0 | 0 | 1 |
| 非同步、單程 10 ms：崩潰時遺失的已確認寫入 | 3 | 12 | 7 |

- 同步複寫在 10 ms 鏈路上三種語言都是 40–46 ms，由網路主導。這是 2 個來回而不是 1 個，原因見下面 .NET 的第 2 點。
- 本機 loopback 上 Python 每筆寫入多 2–3 ms，是處理 HTTP 本身的成本。Rust 和 .NET 的差距在重跑之間的波動範圍內（Rust 版開發時同一個情境量到 0.35–1.46 ms），不代表誰比較快。
- 非同步在三種語言崩潰時都會丟資料：10 ms 鏈路上丟 3–12 筆，都是崩潰前十幾毫秒內確認的。loopback 上也會丟，只是很少：Python 這輪丟 1 筆，Rust 開發時有一次丟 2 筆。只在本機測非同步，會嚴重低估風險。

**.NET 版開發過程遇到的問題**（.NET 版先做，其他兩版照它移植）

1. **第一次冒煙測試，主機一升格就整個程序停掉**：複寫迴圈用 `TimeSpan.MinValue` 當「上次送出時間」，相減時溢位。背景服務丟出例外，ASP.NET 預設會直接停掉整個 host。單元測試沒抓到，因為當時沒有測背景迴圈，後來補了在同一程序內跑整個叢集的整合測試（`ClusterTests`）。
2. **同步複寫的延遲是 2 個來回，不是 1 個**：10 ms 鏈路下 p50 是 41 ms，不是預期的 20 ms。原因是複寫一次只送一批（stop-and-wait）。寫入如果在一批送出途中到達，要等這批回來，再等下一批。要降到 1 個來回需要 pipelining（同時有多批在途中），這次沒做。
3. **差點出現的腦裂**：設計時發現，備機向 witness 搶主的同時，如果又接受舊主機的複寫（等於又承諾不搶主），兩邊會同時認為自己有權服務。解法是備機在向 witness 要租約的期間，拒絕所有複寫。
4. **獨立 review 找到兩個會丟資料的競態**：所有情境都通過之後，另外請一個沒看過設計的 reviewer 只看程式碼找問題。它找到兩個「晚到的請求」造成的漏洞。這兩個漏洞在 loopback 上幾乎不會出現，原本的情境也都沒抓到：
   - **晚到的「備機已同步」**：主機逾時放棄的請求，還是可能在之後送到 witness，蓋掉比它晚送的「允許單獨確認」。這時 witness 會以為備機可以接手，主機一掛，就升格一台缺資料的備機。原本只靠「同一任期內的 witness 呼叫排隊」防，擋不住已經放棄、但還在路上的請求。修法是 witness 的同步狀態加版本號：「已同步」必須附上節點最後看到的版本，中間有任何變動就拒絕。新任期如果一開始就看到「備機不同步」，會先送一次「單獨確認」，讓舊程序晚到的訊息全部失效。
   - **晚到的心跳截掉已確認的寫入**：備機收到「已送到主機最後一筆」的請求時，會截掉後面多出來的資料。如果收到的是一個晚到的舊心跳，就會把剛確認過的寫入截掉。修法是只截掉比目前主機舊的 epoch。
   - 另外兩個問題：「允許單獨確認」其實成功了但回覆遺失時，witness 會一直以為備機落後，造成不必要的拒絕切換（修法是續約時比對 witness 的狀態）；一個很窄的競態可能讓節點程序整個停掉。
   - 為此加了 `late-messages` 情境（主機的連線慢到超過逾時，期間備機重啟、最後主機被砍），以及對應的單元測試；每個情境結束時也改成檢查 witness 自己的紀錄，不只看節點的說法。
5. **gateway 收到不是 JSON 的 200 會整個停掉**：健康檢查只攔了網路錯誤，`NotSupportedException` 會讓背景服務崩潰。寫 gateway 測試時發現並修正。
6. **教訓**：這類機制的正確性取決於訊息晚到、亂序時的行為。正常的故障情境（崩潰、斷線）全部通過，並不代表沒有 bug。正式導入時應該用現成、經過驗證的實作（見結論），不要自己寫。

**移植成 Rust、Python 時發現的事**

1. **.NET 原版還有四個問題**，移植的 agent 和 Rust 版的 reviewer 找到的，三個版本都已修正：
   - **witness 先改記憶體才寫檔**：寫檔失敗（例如磁碟滿）時，記憶體已經把租約交出去，磁碟上還是舊的；witness 重啟後，兩台節點都可能認為自己持有租約。改成先寫檔再改記憶體。
   - **log 檔最後一行只少了換行**：程序剛好在換行字元之前被砍掉時，這行會被當成正常資料接受，但沒有補上換行，下一筆就會黏在它後面。下次啟動時這兩筆會被當成殘骸丟掉，之後同一個 index 可能被重新使用，造成兩台的 log 在相同的 (index, epoch) 下內容不同，等於可能丟掉已確認的寫入。寫入失敗留下的半行也有類似問題。改成啟動時補齊、寫入失敗時截掉半行。
   - **log 截斷也是先改記憶體才寫檔**，改成先寫檔。
   - 不合法的複寫請求（`prevIndex` 0 但 epoch 不是 0）會讀到 `_entries[-1]` 而回 500。
2. **驗證腳本的延遲模型有誤**：TCP 代理原本對每次讀到的資料依序 sleep，等於每一次 TCP write 都多付一次延遲。Python 的 httpx 和 uvicorn 會把 header 和 body 分兩次寫，所以 10 ms 鏈路上的寫入被量成 71 ms。改成「每段資料都晚 10 ms 到，但連續送出的仍然連續到達」之後，Python 降到 46 ms；.NET 維持 41 ms，因為它的 2 個來回是 stop-and-wait 本身造成的。
3. **語言特有的陷阱**：
   - Rust：`tokio::select!` 會隨機挑一個已就緒的分支，已經結束的任期還可能送出 witness 報告，要加 `biased` 讓「任期結束」優先。程序被砍在多位元組字元中間時，log 的最後一行不是合法的 UTF-8，要用 bytes 讀。axum 預設不設 `TCP_NODELAY`。
   - Python：uvicorn 預設的 `--lifespan auto` 會吞掉啟動錯誤，在沒有背景迴圈的情況下照常回應，必須用 `--lifespan on`。gateway 的轉發和健康檢查原本共用 httpx 預設的 100 條連線，寫入一慢就把健康檢查擠掉，gateway 會以為沒有主機。asyncio 不用鎖，但所有「先檢查再動作」的地方中間都不能有 `await`。
4. **網路比逾時還慢時會停擺**：`late-messages` 情境中三種語言都有 20 秒以上沒有主機。舊主機的續約在它自己看來都逾時了，但請求還是晚晚送到 witness，一直把租約續下去：備機搶不到，舊主機也不敢服務。這是「寧可停機也不丟資料」的另一面，代表逾時要依真實網路的延遲來設定。
5. **review**：Python 版的 agent 自己做了一次獨立 review，修掉 gateway 連線池、請求大小上限、背景任務監督等問題。Rust 版另外請 reviewer 檢查，叢集協定沒有發現問題，只找到上面第 1 點的 log 檔問題。

- 安全性的結果三種語言完全一樣：0 遺失、0 錯誤；對照組的問題在三種語言都會發生。
- 延遲由租約和設定決定，三種語言幾乎相同。唯一明顯的差別是補讀速度：熱熱模式每筆結果都是一次 HTTP 呼叫，Rust 最快，Python 最慢。
- 對照組的數字（不一致幾筆、錯誤結果幾筆）會隨每次跑的時序變動，重點是「會發生」，不是確切數字。

**發現**

1. **熱熱備援真的不中斷**：沒有偵測、沒有切換，掛掉一台時下游完全感覺不到。代價全部轉到下游：每一筆都要去重，而且兩台的結果必須逐字相同。
2. **重啟補讀是必要的，而且要靠上游能重播**。上游如果不能重讀（例如 UDP 廣播、只推不存的 webhook），重啟的那台就永遠少一段，這個架構就不成立。
3. **「結果帶時鐘」這類不一致是偶發的**，而且比例隨負載變動（這輪 3–4%，Rust 版開發時在機器很忙的情況下量到 39%），平常的測試很容易漏掉。下游應該把「同一個編號、不同內容」當成警報。
4. **上游指派的中斷只限於那台手上的工作**，延遲約等於租約長度。跟架構 A 的 RTO 一樣，由租約決定。
5. **有三種情況會讓同一件工作做兩次**：worker 被砍在「寫結果」和「回報完成」之間、worker 被凍結超過租約、回報時斷線。第二種可以靠 worker 檢查租約大致避免，另外兩種只能靠下游去重。
6. **.NET 版的獨立 review 找到的問題**（全部情境第一次就都通過之後才找到）：
   - **活著但做不完的 worker 會一直抓著工作**：連不到下游、心跳照常時，租約一直被延長。改成寫不出結果超過一個租約就放手，並加了 `dispatch-sink-cut` 情境。
   - **心跳卡住一次就可能失去租約**：原本下一次心跳是在上一次結束後才計時。改成固定間隔、每次最多等一個間隔，並加了 `dispatch-long` 情境證明長任務確實靠心跳活著。
   - **租約檢查之後的寫入可以拖很久**：寫結果的逾時原本是 1 秒，比 0.2 秒的安全邊際長。改成不超過剩下的租約。
   - **上游重啟會默默算錯**：改成發現上游比自己的進度還短就停下來報錯。
   - **驗證腳本可能空過**：改成沒有產生任何資料就直接判失敗，並補了熱熱模式的網路分區情境。
7. **移植成 Rust、Python 時又找到的問題**：
   - **放手之後又接回同一件**：Rust 版發現連不到下游的 worker 放掉一件後，馬上又接一件、再卡一件；Python 版發現它甚至常接回剛放掉的同一件，因為它往往是等最久的那台。佇列裡沒有別的工作時，那件可能一直卡下去。原本的情境沒抓到，只是因為佇列一直有存貨。三種語言都加了斷路器（放手後先確認下游恢復才接新工作），`dispatch-sink-cut` 也多檢查「只放掉 1 件」。
   - **一個極少發生的漏洞**：Rust、Python 的 review 順帶發現 .NET 原版在「寫結果前發現租約用完」時會再檢查一次；如果剛好有心跳回覆在那幾微秒內延長了租約，worker 會什麼都沒寫就回報完成，那件工作就不見了。改成租約用完就直接放棄（Rust 原本就是這樣寫）。
   - **Python 特有**：uvicorn 在 client 斷線後還會繼續執行請求，被砍掉的 worker 那個還沒回來的「租任務」請求，仍可能拿走一件工作。改成 client 斷線就取消。
8. **worker 檢查租約也不是百分之百**：如果剛好在「檢查完、請求已經送出」之後被凍結，結果還是會晚到。這段空窗很短但存在，所以下游的去重不能省。

**量測環境與限制**：macOS（Apple Silicon）單機，所有程序走 loopback，網路故障由 `verify/chaos.py` 的 TCP 代理模擬。每種語言、每個情境只跑一輪（另外註明的除外），數字適合比較相對大小，不代表正式環境。

## 結論

- 結果：**有條件可行**，三種架構的條件不同；每種架構在 .NET、Rust、Python 的結果都一致。

**三種架構怎麼選**

| | A. 主備＋資料同步 | B. 熱熱備援 | C. 上游指派 |
|---|---|---|---|
| 掛一台時的中斷 | 約等於租約（實測 3.1–3.5 秒） | 沒有中斷（實測最長 14 ms 沒有新結果） | 只有那台手上的工作延遲約一個租約（實測 2.34–2.35 秒） |
| 不丟資料靠什麼 | 同步複寫＋witness | 上游保留事件＋每台自己的檢查點 | 上游的租約與改派 |
| 重複的工作 | 沒有 | 每一筆都做兩次 | 少數工作做兩次 |
| 下游要做什麼 | 不用特別處理 | 一定要去重；兩台的結果必須完全相同 | 一定要去重 |
| 需要的第三方 | witness | 可以重播的上游 | 有租約的佇列 |
| 適合 | 有狀態、要強一致的資料（資料庫、帳務） | 結果可重現、一刻都不能停的計算（行情、監控、告警） | 可以重做的獨立工作（轉檔、寄信、批次） |

**架構 A 的條件**（三種語言結果一致）：

  1. **一定要有第三方仲裁（witness）**。兩台互相心跳的做法，在網路分區時會腦裂，三種語言都實測丟了 3,200 筆以上已確認的寫入。witness 很輕，只存四個欄位，可以放在一台小機器或雲端，但必須跟兩台主機在不同的故障域（不同電源、不同交換器）。witness 單獨掛掉不影響服務。
  2. **要不丟資料就得同步複寫**。代價是每筆寫入多 1 到 2 個網路來回：在 10 ms 的鏈路上，p50 從 0.4–2.5 ms 變成 40–46 ms。非同步很快，但主機崩潰會丟掉最後十幾毫秒確認的寫入。
  3. **備機落後時主機又掛掉，系統會停機，不會自動切換**。這是「不丟資料」的代價。要強制切換，只能人工介入並接受資料遺失。
  4. **RTO 約等於租約長度**：3 秒租約 → 3.1–3.5 秒，1 秒租約 → 1.1–1.2 秒。但租約越短越容易被網路抖動誤判：1 秒租約下，三種語言都被 1.16 秒的斷線觸發了一次切換。建議租約至少是「可容忍的最長網路中斷」的 2 倍。
  5. **逾時要配合真實網路**。網路延遲一旦超過逾時，整個叢集會停擺（實測 20 秒以上沒有主機），不會不安全，但也不能服務。
  6. **入口要另外做備援**。這次的 gateway 是單點，正式環境要用虛擬 IP（keepalived）或雲端 load balancer。
  7. **語言不影響結論**。安全性三種語言結果完全相同，RTO 由租約決定。語言只影響本機延遲（Python 每筆多 2–3 ms），一跨機器就被網路蓋過。用團隊熟悉的語言即可。
  8. **自己寫很容易出錯**。全部故障情境都通過之後，review 和移植又陸續找到 2 個會丟資料的競態和 4 個崩潰復原的問題，而這些在正常的故障測試裡都沒有出現。
  9. **這是單機模擬的結果**。真實網路、斷電（這次沒有 fsync）、時鐘漂移都還沒驗證。
**架構 B 的條件**：

  1. **上游必須能重播、而且不能丟歷史**（Kafka 之類），每台 worker 要有自己的檢查點。上游如果只推不存，重啟的那台會永遠少一段。
  2. **處理必須是決定性的**：同樣的輸入、同樣的順序，算出一模一樣的結果。不能用本機時鐘、亂數、本機計數器，也不能在處理當下去查會變動的外部資料。
  3. **下游必須以事件編號去重**，並且把「同一個編號、不同內容」當成警報。
  4. **成本是兩倍的運算和下游流量**。

**架構 C 的條件**：

  1. **工作必須可以重做，下游必須以工作編號去重**：at-least-once 無法避免。
  2. **worker 寫結果前要先檢查自己的租約**，寫入的逾時不超過剩下的租約，避免被凍結後晚到的寫入。要完全擋住，寫結果和檢查租約必須在同一個交易裡（例如 job table 的 `UPDATE … WHERE attempt = ?`），否則只能靠冪等。
  3. **worker 做不完時要主動放手，然後先停手**。心跳只證明 worker 活著，不證明它做得完；連不到下游還一直心跳，工作就會卡住。放手後如果馬上接新工作，會一件接一件地卡，甚至接回同一件，所以要加斷路器，等下游恢復再接。
  4. **任務延遲的上限約等於租約長度**。租約太短，網路抖動或 GC 時會誤判（跟架構 A 同一個取捨）。
  5. **佇列本身要有備援**（SQS、RabbitMQ 叢集、資料庫的 job table）。

- 如果要正式導入，下一步是：
  1. **架構 A 不要自己寫複寫**。改用 PostgreSQL + Patroni（etcd 當 witness，開 `synchronous_mode_strict`）或 SQL Server Always On + file share witness，把 `verify/` 的情境改成對真實系統跑。這次的機制跟它們一一對應（見技術選型的對照表），可以直接比較結果。
  2. 用兩台真機器加第三台 witness 重跑，量真實網路下的寫入延遲和 RTO。
  3. 驗證入口備援：keepalived VIP 或雲端 load balancer，量切換時間。
  4. 架構 B：用 Kafka（兩個 consumer group）加 Kafka Streams 或 Flink 的 checkpoint，跑同樣的情境。
  5. 架構 C：用 SQS 或資料表加租約欄位跑同樣的情境，量真實網路下的重複率。
  6. 架構 C：worker 放手時主動通知上游（例如 `POST /tasks/{id}/release`），讓改派不必等租約到期，連不到下游的情況可以再快約 2 秒。
