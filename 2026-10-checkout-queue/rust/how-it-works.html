結帳排隊機制｜Rust 版運作說明

這頁說明 rust/ 裡的程式怎麼運作：使用者怎麼排隊、什麼時候被放行，以及下單和付款怎麼保證不超賣、不重複扣款。框架是 axum 0.8 ＋ tokio（Rust edition 2024），透過 redis crate 1.8（ConnectionManager）在 Redis 7.4 上執行和 .NET 版同一份 Lua 腳本。

1. 全貌 2. 互動流程圖 3. 從排隊到付款的程式碼 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：一種程式開很多台，共用一個 Redis

只有一個程式 checkout-queue（一個 Cargo package，裡面是 library ＋ binary）。要撐更多流量就多開幾台，全部指向同一個 Redis、同一個 SALE_ID，就是在服務同一場活動。程式本身不存任何狀態，排隊、名額、庫存、訂單全部在 Redis 裡。HTTP 介面和 .NET 版完全一樣，同一支 verify/run.sh 驗證兩者。

checkout-queue（HTTP 端點）

127.0.0.1:8090（PORT，驗證時開兩台）

收使用者的請求：排隊、輪詢、下單、付款。先檢查輸入格式，再呼叫對應的 Lua 腳本，最後把腳本的結果翻成 HTTP 狀態碼。排隊狀態除了輪詢，也可以連 /queue/tickets/{id}/events 改由伺服器推送（SSE）。根目錄 / 另外附一個操作頁，可以用滑鼠模擬一群顧客。

背景迴圈（每台都有）

maintenance::run_every()，每 TICK_MS 一次；TicketPushWorker，每 POLL_INTERVAL_MS 一次 ＋ pub/sub

定時任務先釋放逾時未付款的訂單，再從隊頭放行使用者。每台都跑，不需要選出一台負責，因為每一步都是原子的。推送迴圈把狀態變化送給連在這台的 SSE 串流。

Redis

127.0.0.1:6379（REDIS_URL，格式 host:port）

存所有狀態，並執行 Lua 腳本。Redis 一次只執行一支腳本，所以腳本裡的「檢查再寫入」不會被別的請求插隊。

2. 互動流程圖：一張 ticket 的一生

點下面的按鈕切換情境。藍色虛線是這個情境實際走的路徑，紅色是斷掉的路徑；Redis 裡亮起來的格子是這次被改到的資料，旁邊的藍字說明改了什麼。線上的藍字是被執行的 Lua 腳本。

排隊取號：POST /queue/join {"userId":"alice"}

做了什麼
join.lua 把序號 seq 加 1，建立一張 ticket，加到 waiting 的隊尾，並記下「alice 的 ticket 是這張」。回 201，Location 指向這張 ticket，內容有目前順位 position。
重複排隊
alice 重新整理、開第二個分頁、或網路重試，都會拿到同一張 ticket（200），一個人不會佔兩個位置。只有上一張已經結束（沒輪詢被跳過、放行逾時、訂單沒付款）才會發新的一張，排到最後。
已經賣完
架上是 0、也沒有未付款訂單時，直接回 409 sold_out，不用排了。

輪詢等待：GET /queue/tickets/{ticketId}

做了什麼
ticket.lua 先更新 ticket 的 lastSeenAt，再回傳狀態、順位和預估等待秒數。回應裡的 pollAfterMs 告訴客戶端多久後再問一次。
心跳
輪詢就是心跳。之後放行時，lastSeenAt 太舊的人會被跳過（見「排隊中離開」）。
打到另一台
這次請求打到 instance-1，結果跟打 instance-0 完全一樣，因為 instance 本身不存狀態。
預估等待
TicketView::from_reply() 用「前面人數 ÷ 最近 10 秒的放行速度」算出 estimatedWaitSeconds（queue/view.rs 的 estimate()）。速度太低（每秒不到 0.01 人）時不給預估。

改用 SSE 推送：GET /queue/tickets/{ticketId}/events

連上時
queue/events.rs 的 stream() 先用 TicketStreams::open() 登記這條串流，再讀一次 ticket、送出目前狀態。之後不用再問，有變化伺服器會推。
放行那一刻
instance-0 的定時任務跑 admit.lua，放行的同時 PUBLISH 被放行的 ticket。兩台都有訂閱；這位使用者的串流連在 instance-1，所以由 instance-1 的 TicketPushWorker 推給他。Rust 版實測放行到使用者知道 p50 2 ms、p95 10 ms，polling 是 462 ms。
順位
每台每秒用一支批次腳本 watch.lua（QueueStore::watch()，每批最多 500 張）取回所有連線者的狀態，順位有變才推，推送頻率不會超過 polling。
心跳
串流開著就算在線上：watch.lua 順便更新 lastSeenAt。關掉分頁，串流斷了，心跳就停。
負載
同樣 1000 人，打到 app 的請求從每秒 931 次降到 9 次，兩台 app 合計 CPU 從 8.8% 降到 3.9%；名額回收得快，每秒放行人數從 4.7 變成 9.4。

放行：兩台的定時任務都在跑

做了什麼
admit.lua 算出還能放幾人：min(MAX_ACTIVE, 架上庫存) − 已放行人數，然後從 waiting 的隊頭一個一個取出，放進 active，並設定放行截止時間（ADMISSION_WINDOW_MS）。
兩台同時跑
兩台的計時器各自觸發，但 Redis 一次只跑一支腳本：先跑的放滿名額，後跑的算出來可放 0 人。十台同時跑，結果跟一台一樣（concurrency::parallel_admitters_never_exceed_max_active）。
看庫存放行
剩 3 件就最多放 3 人進來。放進來卻一定買不到，只是換個方式告訴他「賣完了」。
順便做的事
同一支腳本也會收回逾時的名額（見「放行後沒下單」），並更新放行速度給預估用。

下單扣庫存：POST /checkout {"ticketId":"…","quantity":2}

檢查
checkout.lua 依序檢查：ticket 存在、這張 ticket 還沒下過單、狀態是已放行、還沒過放行截止時間、架上庫存夠。
寫入
全部通過才在同一支腳本裡：庫存 DECRBY 2、建立訂單放進 pending（付款截止時間 PAYMENT_WINDOW_MS）、ticket 標成 ordered、從 active 移出。回 201。
名額
從 active 移出後，下一輪放行就能再放一個人進來。
庫存不夠
還有未付款訂單時回 409 insufficient_stock（可能是 0 件），放行期間可以重試；完全賣完才回 409 sold_out。

連點結帳，兩個請求分別打到兩台

發生什麼
兩台 instance 幾乎同時執行 checkout.lua。Redis 一次只跑一支：先到的建立訂單、扣庫存（201）；後到的看到這張 ticket 已經有 orderId，直接回傳同一張訂單（200），不再扣庫存。
為什麼
ticket 本身就是 idempotency key，不需要客戶端另外產生。
數量不同
如果第二次送的數量不一樣，回 409 ticket_used。
實測
1000 人的搶購情境裡三分之一的人這樣連點，沒有任何人拿到兩張訂單；測試裡 100 個已放行的人各點 3 次（共 300 個請求同時送出），剛好成立 50 張訂單、庫存剛好 0（concurrency::parallel_checkouts_never_oversell_nor_order_twice_per_ticket）。

付款：POST /orders/{orderId}/pay

做了什麼
pay.lua 在同一個原子步驟裡：在 payments 加一筆扣款紀錄、訂單改成 paid、從 pending 移出。回 201。
重複付款
再送一次時訂單已經是 paid，回 200，不會再加扣款紀錄。所以 201 表示「這次扣的」，200 表示「之前已經扣過」。
太晚付款
超過付款截止時間就回 410 order_expired，並在同一支腳本裡把庫存放回去。
注意
付款是模擬的。串真實金流時，扣款發生在外部，不能放進 Redis 腳本，見第 3 節最後的說明。

排隊中離開（關分頁、手機休眠）

發生什麼
使用者停止輪詢，lastSeenAt 不再更新。輪到他時，admit.lua 發現已經超過 HEARTBEAT_TIMEOUT_MS 沒輪詢，把 ticket 標成 abandoned，名額直接給下一位。
為什麼要這樣
不這樣做的話，名額會放給一個已經不在的人，白白等到放行截止時間才收回。
回來了
他回來再呼叫一次 /queue/join，會拿到新的 ticket，排到最後。
設定限制
HEARTBEAT_TIMEOUT_MS 至少要是 POLL_INTERVAL_MS 的 3 倍，漏掉一兩次輪詢不會被誤判離開；設定違反時 Config::validate() 讓啟動失敗。

放行後沒下單

發生什麼
過了放行截止時間還沒下單。下一輪 admit.lua 先把 active 裡截止時間已過的人標成 expired 並移出，空出的名額在同一輪就放給隊頭的下一位。
還沒輪到定時任務
在定時任務處理之前，輪詢和下單就已經會把它當成過期（common.lua 的 ticket_status() 依當下時間判斷）。下單回 410 admission_expired。
之後
可以重新排隊，排到最後。

下單後沒付款

發生什麼
定時任務每一輪先執行 expire_orders.lua：pending 裡付款截止時間已過的訂單改成 expired，庫存 INCRBY 放回架上。
接著放行
同一輪接著執行 admit.lua，放回的庫存馬上就能放下一位進來。
不會放回兩次
付款請求和釋放同時發生時，兩支腳本都只處理還在 pending_payment 的訂單。誰先執行誰處理，另一支看到狀態已經變了就不動（concurrency::payments_racing_the_expiry_sweep_return_each_orders_stock_once）。
實測
Rust 版跑 1000 人搶 200 件的情境，有 21 筆訂單沒付款，庫存放回後被別人買走，最後 200 件全部付款。

3. 從排隊到付款：程式碼怎麼走

以 alice 從排隊一路到付款完成為例。HTTP 端點負責檢查輸入格式；所有會改變狀態的判斷都在 Lua 腳本裡，Rust 只負責呼叫和翻譯結果。路徑都相對於 rust/。

  1. 排隊請求進來，先檢查格式
    src/queue/routes.rs 的 join()；src/http/request.rs 的 JsonBody、valid_user_id()

    axum 內建的 Json 擷取器遇到型別錯會回 422、少 Content-Type 會回 415，而且都是純文字。所以這裡自己寫了 JsonBody 擷取器：不是 JSON、null、型別錯（不做轉型，"quantity":"1" 也算錯）、少欄位，一律變成 400 invalid_request 加上錯誤格式。欄位名稱不分大小寫，和 .NET 版一樣。userId 只接受 1–64 個英數字和 . _ - @，因為它會成為 Redis key 的一部分。

    async fn join(State(sale): State<Arc<Sale>>, body: JsonBody) -> Result<Response, ApiError> {
    let user_id = valid_user_id(body.string("userId")?)?;
    match sale.queue.join(&user_id).await? {
        JoinResult::Created(view) => {
            let location = format!("/queue/tickets/{}", view.ticket_id);
            Ok((
                StatusCode::CREATED,
                [(header::LOCATION, location)],
                Json(view),
            )
                .into_response())
        }
        JoinResult::Existing(view) => Ok(Json(view).into_response()),
        JoinResult::SoldOut => Err(ApiError::conflict("sold_out", "sold out")),
    }
}
  2. Rust 呼叫 Lua 腳本
    src/queue/store.rs 的 QueueStore::join() → src/sale_redis/mod.rs 的 SaleRedis::run()

    join() 產生新的 ticket 編號（ids::new_id()）、從時鐘取得目前時間（SaleRedis::now_ms()），交給 run()。run() 把活動的 key 前綴 cq:{SALE_ID}: 放在第一個參數，其餘照順序接上，用 redis crate 的 Script 送出（先送 EVALSHA，Redis 還沒有這支腳本時自動載入再執行），再用 ScriptReply::parse() 把回覆解析成「結果代碼 ＋ 欄位」。

    async fn invoke(
    &self,
    script: &SaleScript,
    args: &[ScriptArg<'_>],
) -> Result<Value, StoreError> {
    let mut invocation = script.script().prepare_invoke();
    invocation.arg(&*self.prefix);
    for arg in args {
        invocation.arg(arg.to_string());
    }
    let mut connection = self.connection.clone();
    Ok(invocation.invoke_async(&mut connection).await?)
}

    shared/lua/join.lua（前面接著 common.lua 的共用函式）

    「查有沒有 ticket → 沒有就建立」在同一支腳本裡，同一個人同時送 20 次排隊也只會拿到一張（concurrency::parallel_joins_from_the_same_user_yield_one_ticket）。

redis.call('ZADD', key('waiting'), seq, newId)
redis.call('ZADD', key('tickets'), seq, newId)

  4. 輪詢：更新心跳、回報順位
    QueueStore::ticket() → shared/lua/ticket.lua → src/queue/view.rs 的 TicketView::from_reply()

    腳本更新 lastSeenAt，回傳 ticket 的狀態、順位（ZRANK ＋ 1）和最近的放行速度 admitRate。TicketView::from_reply() 用它們算出預估等待秒數，再加上 pollAfterMs。序列化交給 serde：欄位 camelCase、狀態值 snake_case、None 的欄位不輸出（skip_serializing_if）。

    改用 SSE 時，客戶端連 /queue/tickets/{ticketId}/events（src/queue/events.rs 的 stream()），之後由 src/queue/push.rs 的 TicketPushWorker 推送：放行靠 Redis pub/sub 即時推（SaleRedis::subscribe_admitted() 開一條獨立的訂閱連線），順位每秒用 QueueStore::watch()（watch.lua）批次更新一次。

  5. 定時任務：先釋放、再放行
    src/maintenance.rs 的 run_every() → SaleMaintenance::run_once() → OrderStore::expire_orders()、QueueStore::admit()

    每台每 TICK_MS 跑一次，等待用的是注入的時鐘（Clock::sleep()），測試換成假時鐘就不用真的等。先跑 expire_orders.lua 放回逾時訂單的庫存，再跑 admit.lua，所以放回的庫存同一輪就能放行。Redis 暫時連不上（StoreError::Unavailable）只記警告，下一輪重試；其他錯誤代表程式有 bug，迴圈結束，main.rs 收到後讓程式停下來。

    pub async fn run_every(
    maintenance: SaleMaintenance,
    clock: Arc<dyn Clock>,
    tick: Duration,
) -> Result<(), StoreError> {
    loop {
        clock.sleep(tick).await;
        match maintenance.run_once().await {
            Ok(_) => {}
            Err(StoreError::Unavailable(error)) => {
                tracing::warn!("maintenance tick failed ({error}); retrying next tick");
            }
            Err(bug) => return Err(bug),
        }
    }
}
    -- admit.lua：從隊頭放行，跳過沒在輪詢的人
local free = math.min(maxActive, stock()) - redis.call('ZCARD', key('active'))
local inLine = redis.call('ZCARD', key('waiting'))
local admitted, abandoned, scanned = 0, 0, 0
local admittedIds = {}
while admitted < free and scanned < maxScan do
  local head = redis.call('ZPOPMIN', key('waiting'))
  if #head == 0 then break end
  scanned = scanned + 1
  local id = head[1]
  local ticketKey = key('ticket', id)
  if now - tonumber(redis.call('HGET', ticketKey, 'lastSeenAt')) > heartbeatMs then
    redis.call('HSET', ticketKey, 'status', 'abandoned')
    abandoned = abandoned + 1
  else
    local deadline = now + windowMs
    redis.call('HSET', ticketKey, 'status', 'admitted', 'admittedAt', now, 'admissionExpiresAt', deadline)
    redis.call('ZADD', key('active'), deadline, id)
    admitted = admitted + 1
    admittedIds[admitted] = id
  end
end

-- 告訴每台 instance 誰剛被放行，連著 SSE 的人馬上就能收到
if admitted > 0 then redis.call('PUBLISH', key('admitted'), table.concat(admittedIds, ' ')) end
  6. 下單：檢查數量，呼叫腳本
    src/orders/routes.rs 的 checkout() → src/orders/store.rs 的 OrderStore::checkout()

    端點先檢查 ticketId 是 32 位小寫 hex（http::valid_id()）、quantity 是 1 到 MAX_PER_ORDER 的整數。OrderStore::checkout() 產生新的訂單編號，連同付款期限交給 checkout.lua。

redis.call('HSET', key('order', newId), 'ticketId', ticketId, 'userId', t.userId, 'quantity', qty,
           'status', 'pending_payment', 'createdAt', now, 'paymentExpiresAt', deadline)
redis.call('ZADD', key('pending'), deadline, newId)
redis.call('SADD', key('orders'), newId)
redis.call('HSET', ticketKey, 'status', 'ordered', 'orderId', newId)
redis.call('ZREM', key('active'), ticketId)
return reply('created', order_view(newId, now))
  8. 付款：扣款紀錄和狀態一起改
    src/orders/routes.rs 的 pay() → OrderStore::pay() → shared/lua/pay.lua

    先看訂單狀態：已付款就回 already_paid，已過期就回 order_expired，剛好過了截止時間就在這裡把庫存放回去（expire_order()）。都不是才記扣款。

    看 pay.lua 的程式碼 
    if not o.status then return reply('order_not_found') end
if o.status == 'paid' then return reply('already_paid', order_view(id, now)) end
if o.status == 'expired' then return reply('order_expired', order_view(id, now)) end

if now >= tonumber(o.paymentExpiresAt) then
  expire_order(id, tonumber(o.quantity))
  return reply('order_expired', order_view(id, now))
end

redis.call('RPUSH', key('payments'), id)
redis.call('HSET', orderKey, 'status', 'paid', 'paidAt', now)
redis.call('ZREM', key('pending'), id)
return reply('paid', order_view(id, now))
  9. 把腳本結果翻成 HTTP 回應
    OrderStore::checkout() 把結果代碼對應成 CheckoutResult；orders/routes.rs 再對應成狀態碼；src/http/error.rs 的 ApiError 輸出錯誤

    每個結果代碼都是 enum 的一個 variant，match 沒寫到就編譯不過。成功的結果用 OrderView::from_reply() 組成 JSON；錯誤一律是 {"error": "…", "code": "…"}。Redis 錯誤包成 StoreError::Unavailable，在 impl From<StoreError> for ApiError 變成 503；腳本回了程式看不懂的東西（StoreError::Unexpected）是 bug，回 500。每個回應都由 http::served_by()（在 app::router() 用 map_response_with_state 掛上）加上 X-Served-By，標示哪台回的。

4. 啟動時發生什麼

1. 讀設定、連 Redis

Config::from_env() 讀所有環境變數：數字只接受純數字（沒有正負號、小數點）且要在範圍內、SALE_ID 有奇怪字元、INSTANCE_NAME 不能放進 header、心跳逾時小於輪詢間隔 3 倍，都會直接啟動失敗，訊息裡寫出是哪個變數。接著 limits::raise_open_file_limit() 把可開檔案數的軟上限調到 10,240：.NET 執行環境會自己調，Rust 標準函式庫不會，不調的話軟上限 256 時 600 條連線只有 247 條接得進來。再來 SaleRedis::connect() 建立 ConnectionManager（斷線會自動重連），連不上也是啟動失敗。

2. 組起所有 store

Sale::new() 建立 QueueStore、OrderStore、AuditStore、TicketBoardStore、SaleMaintenance、TicketStreams，全部共用同一個 SaleRedis（複製只是多一個參照，底下是同一條多工連線），整個 Sale 用 Arc 當 axum 的 state。

3. 初始化活動

SaleRedis::initialize() 執行 init.lua：只有活動第一次啟動才設定庫存（SETNX）。後啟動的 instance 或重啟時沿用目前的庫存，INITIAL_STOCK 不一樣就記一筆警告。

4. 先訂閱，再開始聽

app::start_background() 先用 SaleRedis::subscribe_admitted() 訂閱放行通知（在開始接請求之前，不會漏掉），再把四個迴圈放進同一個 JoinSet：訂閱監聽、每 POLL_INTERVAL_MS 的刷新計時、推送、定時任務。然後綁 127.0.0.1 開始服務 app::router()。任何一個背景迴圈結束（只有遇到 bug 才會），tokio::select! 就讓程式停下來。

// src/main.rs（節錄）
let config = Config::from_env()?;
let clock: Arc<dyn Clock> = Arc::new(SystemClock);
let redis = SaleRedis::connect(&config.redis_connection_url(), &config.sale_id, clock)
    .await
    .map_err(|error| format!("cannot connect to Redis at {}: {error}", config.redis_url))?;
let sale = Sale::new(config, redis)?;
let config = Arc::clone(&sale.config);

let started_with = sale.redis.initialize(config.initial_stock).await?;
// ……庫存跟設定不同時記警告……

let mut background = app::start_background(&sale, true).await;
let listener = TcpListener::bind((Ipv4Addr::LOCALHOST, config.port)).await?;
// ……
tokio::select! {
    served = axum::serve(listener, app::router(sale)) => Ok(served?),
    Some(stopped) = background.join_next() => match stopped {
        Ok(Ok(())) => Err("a background loop stopped".into()),
        Ok(Err(bug)) => Err(format!("a background loop failed: {bug}").into()),
        Err(panicked) => Err(format!("a background loop panicked: {panicked}").into()),
    },
}

Lua 腳本和操作頁放在 PoC 根目錄的 shared/，三種語言版本共用同一份；Rust 版在編譯時用 include_str! 直接編進執行檔（src/sale_redis/scripts.rs 的 lua! 巨集、src/demo.rs 的 PAGE），改了共用檔案重新編譯就會帶進去。SCRIPTS 第一次被用到時組好，每支前面都接上 common.lua，所以 key()、ticket_view()、expire_order() 這些共用函式每支腳本都能用。

5. 關鍵設計

每個狀態轉換一支 Lua 腳本

超賣和重複扣款的根源都是「檢查」和「寫入」之間被別人插隊。這裡每個狀態轉換（排隊、放行、下單、付款、釋放）都寫成一支腳本，Redis 一次只執行一支，所以不需要鎖、不需要重試，也不需要選主。代價是一場活動的資料必須在同一個 Redis 執行緒上，這就是承載上限（見 README 的實驗紀錄）。所有 key 都用 cq:{SALE_ID}: 當前綴，大括號是 Redis Cluster 的 hash tag，保證同一場活動的 key 落在同一個 slot。腳本是三種語言共用的，Rust 版一行都沒改。

放行規則：名額和庫存取小的

可放行人數 = min(MAX_ACTIVE, 架上庫存) − 已放行、還沒下單的人數

MAX_ACTIVE 就是削峰的旋鈕：外面排了多少人都不影響，同時在結帳的最多就這麼多。被未付款訂單保留的庫存不算架上庫存，等訂單逾時放回，下一輪就會再放人。

截止時間當下就算，定時任務只是收尾

放行和付款的截止時間一到，輪詢、下單、付款就會當成已過期，不用等定時任務。所以就算定時任務慢了或暫時連不上 Redis，使用者看到的狀態也和實際能做的事一致。

-- common.lua：狀態依當下時間判斷
local function ticket_status(t, now)
  if t.status == 'admitted' and now >= tonumber(t.admissionExpiresAt) then return 'expired' end
  if (t.status == 'waiting' or t.status == 'admitted') and sold_out() then return 'sold_out' end
  return t.status
end

時間由各台 instance 傳入，等待也走同一個時鐘

腳本不自己讀 Redis 的時鐘，而是由 Rust 從 Clock（src/clock.rs）取得目前時間傳進去。正式執行用 SystemClock，測試用 ManualClock：advance() 把時間往前推，同時叫醒所有等到時間的 sleep()。兩個背景迴圈（定時任務、SSE 每秒刷新）也用 Clock::sleep() 等，所以「推一秒，串流就收到新順位」這種測試也不用真的等。代價是各台 instance 的時鐘要同步（NTP）。時鐘差幾毫秒時，admit.lua 算放行速度的時間範圍至少取 1 秒，不會因此出錯（concurrency::admitter_with_a_clock_slightly_behind_still_completes_its_pass）。

Redis 連線：會自己重連，失敗要快

指令走 redis crate 的 ConnectionManager：一條多工連線，所有請求並行送出（和 .NET 的 multiplexer 一樣），斷線後下一個指令觸發重連。設定刻意偏向「快點失敗」：連線逾時 2 秒、指令逾時 5 秒、重連只重試 2 次，Redis 掛掉時請求很快拿到 503，下一個請求再試。pub/sub 用另外一條專用連線；斷了就由 listen_for_admissions() 每 POLL_INTERVAL_MS 重新訂閱一次，這段期間放行靠每秒刷新補上，只是慢一點。測試用一個可以剪斷、再接回的 TCP proxy 驗證這幾件事（api::redis_down_is_503_not_a_crash_and_recovers、ticket_events::admissions_are_pushed_again_once_the_subscription_comes_back、maintenance_worker::worker_keeps_ticking_through_a_redis_outage）。

SSE：每條串流只留最新的一個畫面

TicketStreams 為每條串流開一個 tokio watch channel，裡面永遠只有最新的一個 TicketView，客戶端慢的時候舊的直接被蓋掉，不會越積越多。回應本體是 stream::unfold 產生的串流：先送目前狀態，之後每收到一個和上次不同的畫面就送一個事件，15 秒沒東西就送 : keep-alive，狀態到終局（TicketStatus::is_final()）就結束。客戶端斷線時 hyper 丟掉這個串流，TicketStream 的 Drop 就把它從登記表移除。

其他

設計做法在哪裡
ticket 就是 idempotency key同一張 ticket 重送下單回同一張訂單，客戶端不用另外產生 keycheckout.lua
