SOLID 原則範例｜Python 版運作說明

這頁說明 python/ 裡的程式怎麼運作：SOLID 五個原則各用一個電商結帳的小情境，同一個模組裡放「違反版」和「遵守版」，示範程式把兩者的差別印出來。範例只用 Python 3.12 標準函式庫（dataclasses、typing.Protocol、abc），測試用 pytest 9.2 ＋ pytest-cov 7.1，ISP 的型別檢查用 mypy 2.4 驗證。

1. 全貌：五個原則各一個模組，一支示範程式，五組測試

這份實作不開任何 port，也沒有外部服務。每個模組對應一個原則，裡面先放違反版（名稱多半以 Legacy 開頭），再放遵守版。示範程式依序跑五個情境，把兩個版本在同一個需求下的結果並排印出來。

srp.py ～ dip.py

五個原則 ・ 被 demo.py 和測試匯入

每個檔案開頭的 docstring 寫情境，接著是 # --- 違反 --- 和 # --- 遵守 --- 兩段。lsp.py 沿用 ocp.py 的 DiscountRule 介面。

demo.py

示範程式 ・ ./run.sh demo

依序呼叫 show_srp() 到 show_dip()。「滿千折百」的新規則 SpendThresholdOff 就定義在這裡，用來證明不用改 ocp.py。三種語言的輸出逐字相同。

test_srp.py ～ test_dip.py

43 個測試 ・ ./run.sh test

README 的每一條成功標準都對應測試：違反版的錯誤真的會發生，遵守版不會。違反版的錯誤也寫成測試，是為了證明它不是想像出來的。

2. 互動流程圖：一個需求進來，漣漪擴散到哪裡

點按鈕切換原則。左半是違反版、右半是遵守版，兩邊處理的是同一個需求。藍色虛線是正常運作的路徑，紅色點線是被連帶影響或出錯的路徑，紅色虛框是有問題的地方，紫框是提出需求的角色。

S：單一職責原則——一個模組只為一種角色改變

需求
財務要求發票金額改成含 5% 營業稅。物流沒有任何新需求，規則還是「未稅小計滿 1000 元免運」。
違反版
LegacyOrder 的 invoice_amount() 和 ships_free() 共用 _amount()。把稅加進 _amount() 後，960 元的訂單算成 1008 元，免運判斷跟著變成「是」。
遵守版
財務的 InvoiceCalculator.amount() 和物流的 ShippingPolicy.ships_free() 分開。稅只寫在前者，後者還是拿未稅的 subtotal() 比較，免運維持「否」。
重點
可以共用的是「兩邊都認同的事實」（未稅小計），不能共用的是「某一方的規則」（稅）。這不是在算類別有幾個方法，而是看有幾種人會要求它改。
對應測試
test_legacy_order_tax_change_leaks_into_free_shipping、test_shipping_policy_is_unaffected_by_tax

O：開放封閉原則——加功能是寫新程式，不是改舊程式

需求
原本有 VIP 九折、員工八折，行銷部新增「滿 1000 折 100」。
違反版
legacy_total_after_discount(subtotal, kind) 用一串 if 比對字串。傳 "threshold" 進去只會得到 ValueError("不支援的折扣：threshold")，要支援就得修改這個已經測過的函式。
遵守版
total_after_discount(subtotal, rule) 只認 DiscountRule 介面。新的 SpendThresholdOff 直接寫在 demo.py，ocp.py 一行都沒改，1200 元算出 1100 元。
代價
多了一個介面和數個小類別。折扣種類固定、很少變的話，一串 if 反而比較好讀。
對應測試
test_legacy_rejects_a_new_kind_until_someone_edits_it、test_new_rule_works_without_editing_the_module（新規則定義在測試檔裡）、test_rules_match_legacy_for_existing_kinds（舊的三種折扣兩版結果相同）

L：里氏替換原則——子型別要守住父型別的契約

需求
新增「折 200 元」。小計只有 150 元的訂單套用後，總額應該是多少？
契約
DiscountRule 的 docstring 寫明 0 <= discount(subtotal) <= subtotal。total_after_discount() 依賴這個契約，才能保證總額不會是負數。
違反版
UncappedAmountOff(200) 不管小計多少都回 200，總額變成 −50 元。型別完全合法，呼叫端也沒寫錯，錯的是這個子型別沒守住契約。
遵守版
FixedAmountOff(200) 回 min(200, subtotal)，總額最低是 0 元。
怎麼把關
契約不在型別系統裡，所以用 contract_violations() 拿一組樣本小計檢查，再把每個實作丟進同一個參數化測試。新加的 SpendThresholdOff 也在 demo 裡過了一次契約檢查。
檢查的是實例
契約檢查只對「這組參數」有效。SpendThresholdOff(1000, 100) 守得住，但 SpendThresholdOff(50, 100) 遇到小計 60 會折 100，一樣違反契約。要一勞永逸，就得像 FixedAmountOff 一樣在 discount() 裡設上限，或在建構時擋下 amount > threshold。
對應測試
test_uncapped_amount_off_makes_the_total_negative、test_contract_check_catches_the_uncapped_rule、test_every_shipped_rule_honors_the_contract

I：介面隔離原則——不要逼實作者依賴用不到的方法

需求
新增貨到付款。它能收款，但不能線上退款，也沒有付款資訊可以記住給下次用。
違反版
肥介面 LegacyPaymentMethod 有 charge()、refund()、remember() 三個抽象方法。LegacyCashOnDelivery 只能讓後兩個丟 NotImplementedError。型別上看起來每種付款都能退款，要執行到才知道不行。
遵守版
拆成 Chargeable、Refundable、Rememberable 三個 Protocol。CashOnDelivery 只有 charge()，refund_order() 的參數型別是 Refundable，型別檢查工具會擋下傳貨到付款進去的呼叫。
Python 的限制
Python 執行時不檢查型別註記，所以「執行前擋下」要靠 mypy 這類工具。test_type_checker_rejects_refunding_cash_on_delivery 用 mypy.api.run() 檢查 refund_order(CashOnDelivery(), 300)，斷言 mypy 回報 incompatible type "CashOnDelivery"; expected "Refundable"；另一個測試確認換成 CreditCard() 就通過，證明失敗真的是型別造成的。三個介面也標成 @runtime_checkable，用 isinstance(cash, Refundable) 在執行時也能問「它能不能退款」。Rust、.NET 版是編譯就擋下。
附帶觀察
違反 ISP 常常順便違反 LSP：LegacyCashOnDelivery 丟例外，等於沒守住「付款方式可以退款」的契約。
對應測試
test_legacy_cash_on_delivery_is_forced_to_stub_two_methods、test_cash_on_delivery_only_implements_charging、test_type_checker_rejects_refunding_cash_on_delivery

D：依賴反轉原則——高層和低層都依賴抽象

需求
結帳後寄通知給客人。這個環境沒有 SMTP 伺服器（SmtpMailer.send() 一定丟 ConnectionError，模擬測試環境的真實狀況）。
違反版
LegacyCheckoutService.__init__() 自己建立 SmtpMailer()，外面換不掉。結帳一定失敗，連「金額算得對不對」都沒辦法測。
遵守版
CheckoutService 的建構子收一個 Notifier。測試和示範注入 RecordingNotifier，不連 SMTP 也能跑完結帳並檢查通知內容；正式環境注入 SmtpMailer，CheckoutService 一行都不用改。
覆蓋率
dip.py 的覆蓋率是 96%，唯一沒蓋到的是 LegacyCheckoutService.checkout() 的 return receipt：沒有 SMTP 就永遠跑不到。這行沒被測到，正是違反 DIP 的代價。
和其他 PoC 的關係
模組化單體轉微服務能做到「呼叫端不改、把目錄模組換成 HTTP 客戶端」，靠的就是同一招：訂單模組只依賴目錄的介面。
對應測試
test_legacy_checkout_cannot_run_without_an_smtp_server、test_checkout_with_a_fake_notifier_needs_no_smtp_server

3. 一條新折扣規則的旅程

SOLID 不是「請求進、回應出」的程式，這一節改成追一個改動：行銷部要「滿 1000 折 100」，從寫出新規則、算出總額、檢查契約到測試把關，依序經過這些程式碼。這條路線同時用到 O 和 L。

  1. 在模組外面寫新規則
    demo.py 的 SpendThresholdOff

    不繼承任何類別，只要有 discount(subtotal) -> int 這個方法，就符合 DiscountRule（Protocol 是結構型別，看形狀不看血緣）。

    @dataclass(frozen=True)
class SpendThresholdOff:
    threshold: int
    amount: int

    def discount(self, subtotal: int) -> int:
        return self.amount if subtotal >= self.threshold else 0
  2. 算總額的函式不用改
    ocp.py 的 DiscountRule、total_after_discount()

    total_after_discount(1200, SpendThresholdOff(1000, 100)) 呼叫 rule.discount(1200) 拿到 100，回傳 1100。這個函式從頭到尾不知道「滿千折百」存在。

    class DiscountRule(Protocol):
    """契約：0 <= discount(subtotal) <= subtotal。lsp.py 會檢查這件事。"""

    def discount(self, subtotal: int) -> int: ...


def total_after_discount(subtotal: int, rule: DiscountRule) -> int:
    return subtotal - rule.discount(subtotal)
  3. 檢查新規則有沒有守住契約
    lsp.py 的 contract_violations()

    拿樣本小計 (0, 150, 999, 1000, 5000) 逐一呼叫 discount()，回傳不符合 0 <= 折扣 <= 小計 的那些。SpendThresholdOff(1000, 100) 小計未滿 1000 時折 0，滿了折 100，全部守住，回傳空的 tuple。

    def contract_violations(
    rule: DiscountRule, subtotals: Iterable[int] = SAMPLE_SUBTOTALS
) -> tuple[int, ...]:
    return tuple(
        subtotal
        for subtotal in subtotals
        if not 0 <= rule.discount(subtotal) <= subtotal
    )
  4. 如果新規則沒守住契約
    lsp.py 的 UncappedAmountOff

    型別一樣合法，total_after_discount() 照樣接受，但 150 元的訂單會算出 −50 元。contract_violations(UncappedAmountOff(200)) 回傳 (0, 150)，指出是哪些小計出事。

    @dataclass(frozen=True)
class UncappedAmountOff:
    amount: int

    def discount(self, subtotal: int) -> int:
        return self.amount
  5. 測試把每個規則都檢查一次
    test_lsp.py、test_ocp.py

    同一個契約測試用 parametrize 套在每一個正式的規則上。test_ocp.py 也在測試檔裡自己定義一份 SpendThresholdOff，證明模組外面就能擴充。

    @pytest.mark.parametrize(
    "rule", [NoDiscount(), PercentOff(10), PercentOff(20), FixedAmountOff(200)]
)
def test_every_shipped_rule_honors_the_contract(rule):
    assert contract_violations(rule) == ()
  6. 印出結果
    demo.py 的 show_ocp()、show_lsp()

    印出 [遵守] 套 SpendThresholdOff(1000, 100) → 1100 元，以及「契約檢查 NoDiscount、PercentOff(10)、PercentOff(20)、SpendThresholdOff(1000, 100)、FixedAmountOff(200)：全部通過」。型別名稱和參數是手寫的標籤，不是 dataclass 的 repr，這樣三種語言才能印出一樣的字。

每種錯誤在哪裡、什麼時候被發現

狀況在哪裡什麼時候發現結果
違反版遇到新的折扣種類legacy_total_after_discount() 最後一行執行時ValueError("不支援的折扣：threshold")
折扣規則折得比小計還多contract_violations()、test_every_shipped_rule_honors_the_contract跑測試時列出違反契約的小計；不檢查的話執行時算出負數總額
違反版對貨到付款退款LegacyCashOnDelivery.refund()執行時NotImplementedError("貨到付款不能線上退款")
遵守版對貨到付款退款refund_order(method: Refundable, ...) 的型別註記執行前（mypy）型別錯誤，由 test_type_checker_rejects_refunding_cash_on_delivery 驗證；執行時 isinstance(cash, Refundable) 是 False
沒有 SMTP 伺服器SmtpMailer.send()執行時ConnectionError("連不到 smtp.example.com:25")；遵守版可以改注入 RecordingNotifier 避開
改了財務規則，物流被連帶影響LegacyOrder._amount()上線後才發現（沒有任何錯誤訊息）960 元的訂單被判成免運；只有寫了 test_legacy_order_tax_change_leaks_into_free_shipping 這種測試才抓得到

最難發現的是 SRP 那一列：程式沒有丟任何錯誤，只是結果悄悄變了。其他原則被違反時，多少還會在執行時炸出例外。

4. 啟動時發生什麼

demo.py

if __name__ == "__main__": 依序呼叫 show_srp()、show_ocp()、show_lsp()、show_isp()、show_dip()。每個函式自己建立需要的物件，彼此不共用狀態。沒有設定檔，也不讀環境變數。

五個原則模組

匯入時只有定義，沒有任何副作用。唯一的「組裝」發生在 show_dip()：它決定 CheckoutService 要接 RecordingNotifier 還是 SmtpMailer，這就是 DIP 說的組裝點（composition root）。

測試

pytest 從 5 個測試檔收集 24 個測試函式，parametrize 展開後共 43 個。test_ocp.py 的 test_rules_match_legacy_for_existing_kinds 疊了兩層參數化（3 種折扣 × 5 個小計），一個函式就展開成 15 個。

def show_dip() -> None:
    ...
    recorder = RecordingNotifier()
    receipt = attempt(lambda: CheckoutService(recorder).checkout(CUSTOMER_EMAIL, 1080))
    ...
    smtp = attempt(lambda: CheckoutService(SmtpMailer()).checkout(CUSTOMER_EMAIL, 1080))

attempt() 把例外轉成「錯誤：…」字串，這樣違反版的失敗也能印成一行，不會讓示範程式中斷。

5. 關鍵設計

違反版和遵守版放在同一個模組

每個檔案上半是違反版、下半是遵守版，打開一個檔案就能對照。名稱撞到時，違反版加 Legacy 前綴（LegacyOrder、LegacyCashOnDelivery、LegacyCheckoutService）。LSP 的違反版不是舊寫法，而是「型別對但行為錯」的新規則，所以叫 UncappedAmountOff。

Python 用 Protocol 當介面

DiscountRule、Chargeable、Notifier 都是 typing.Protocol：實作的類別不用繼承它，方法長得一樣就算符合。這讓「在模組外面擴充」變得很自然，但也代表沒有東西強迫你守住契約，所以 LSP 要靠 contract_violations() 和參數化測試。ISP 的違反版刻意用 abc.ABC，因為肥介面的問題就是「繼承了就得全部實作」。

輸出只印型別名稱

型別名稱在三種語言都是 PascalCase，方法名稱則不一樣（Python 的 ships_free、C# 的 ShipsFree）。示範輸出只出現型別名稱和中文描述，所以 .NET、Rust 版本可以用 diff 逐字比對。介面名稱也不印，因為 C# 慣例會加 I 前綴。

代價：型別變多了

原則違反版遵守版什麼時候不值得
S1 個類別2 個類別 ＋ 1 個共用函式只有一種角色會要求它改的時候
O1 個函式1 個介面 ＋ 2 個類別 ＋ 1 個函式，之後每種折扣再 ＋1 個類別種類固定、幾年才改一次的時候
L1 個類別1 個類別 ＋ 契約檢查沒有不值得的時候：違反 LSP 就是 bug
I1 個抽象類別 ＋ 2 個類別3 個介面 ＋ 2 個類別 ＋ 1 個函式所有實作都真的做得到每個方法的時候
D1 個類別1 個介面 ＋ 1 個類別 ＋ 1 個測試替身依賴的東西本身就是純計算、不碰外部的時候

其他

設計做法在哪裡
金額都用整數新台幣元，用 // 做整數除法，三種語言算出來的數字一樣，不會有浮點誤差srp.py、ocp.py
不可變的資料LineItem、LegacyOrder、各折扣規則都是 @dataclass(frozen=True)srp.py、ocp.py、lsp.py
唯一會變的物件RecordingNotifier.sent 是 list，因為「記錄收到的通知」本來就是副作用；只在測試和示範用dip.py
違反版的錯誤也寫成測試測試斷言「違反版真的會出錯」，避免範例變成只有口頭說明每個 test_*.py 的第一個測試
沒有外部套件範例只用標準函式庫；pytest、mypy 只放在 dev 群組pyproject.toml
