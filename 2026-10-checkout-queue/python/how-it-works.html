結帳排隊機制｜Python 版運作說明

這頁說明 python/ 裡的程式怎麼運作：使用者怎麼排隊、什麼時候被放行，以及下單和付款怎麼保證不超賣、不重複扣款。框架是 FastAPI 0.162 跑在 uvicorn 0.54（uvloop、httptools）上，Python 3.12，透過 redis-py 8.1 的 asyncio 用戶端在 Redis 7.4 上執行 Lua 腳本。HTTP 介面和 Lua 腳本跟 .NET 版完全相同，同一支 verify/run.sh 驗證。

1. 全貌 2. 互動流程圖 3. 從排隊到付款的程式碼 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：一種程式開很多台，共用一個 Redis

只有一個程式：python -m checkout_queue（一個 uvicorn 行程，單一 event loop）。要撐更多流量就多開幾台，全部指向同一個 Redis、同一個 SALE_ID，就是在服務同一場活動。程式本身不存任何狀態，排隊、名額、庫存、訂單全部在 Redis 裡；每台只在記憶體裡記「哪些 SSE 串流連在我身上」。

checkout_queue（HTTP 端點）

127.0.0.1:8090（PORT，驗證時開 8091、8092 兩台）

收使用者的請求：排隊、輪詢、下單、付款。先檢查輸入格式，再呼叫對應的 Lua 腳本，最後把腳本的結果翻成 HTTP 狀態碼。排隊狀態除了輪詢，也可以連 /queue/tickets/{id}/events 改由伺服器推送（SSE）。根目錄 / 另外附一個操作頁，可以用滑鼠模擬一群顧客。

背景工作（每台都有）

run_maintenance_loop() 每 TICK_MS 一次；TicketPushWorker 每 POLL_INTERVAL_MS 一次

定時任務先釋放逾時未付款的訂單，再從隊頭放行使用者。每台都跑，不需要選出一台負責，因為每一步都是原子的。推送工作把放行和順位變化送給連在這台的 SSE 串流。兩者都是同一個 event loop 上的 asyncio task。

Redis

127.0.0.1:6379（REDIS_URL，驗證時用 6390）

存所有狀態，並執行 Lua 腳本。Redis 一次只執行一支腳本，所以腳本裡的「檢查再寫入」不會被別的請求插隊。

2. 互動流程圖：一張 ticket 的一生

點下面的按鈕切換情境。藍色虛線是這個情境實際走的路徑，紅色是斷掉的路徑；Redis 裡亮起來的格子是這次被改到的資料，旁邊的藍字說明改了什麼。線上的藍字是被執行的 Lua 腳本。

排隊取號：POST /queue/join {"userId":"alice"}

做了什麼
join.lua 把序號 seq 加 1，建立一張 ticket，加到 waiting 的隊尾，並記下「alice 的 ticket 是這張」。回 201（Location: /queue/tickets/{ticketId}），內容有目前順位 position。
重複排隊
alice 重新整理、開第二個分頁、或網路重試，都會拿到同一張 ticket（200），一個人不會佔兩個位置。只有上一張已經結束（沒輪詢被跳過、放行逾時、訂單沒付款）才會發新的一張，排到最後。
已經賣完
架上是 0、也沒有未付款訂單時，直接回 409 sold_out，不用排了。

輪詢等待：GET /queue/tickets/{ticketId}

做了什麼
ticket.lua 先更新 ticket 的 lastSeenAt，再回傳狀態、順位和放行速度。回應裡的 pollAfterMs 告訴客戶端多久後再問一次。
心跳
輪詢就是心跳。之後放行時，lastSeenAt 太舊的人會被跳過（見「排隊中離開」）。
打到另一台
這次請求打到 instance-1，結果跟打 instance-0 完全一樣，因為 instance 本身不存狀態。
預估等待
tickets.py 的 TicketView.from_reply() 呼叫 _estimate()，用「前面人數 ÷ 最近 10 秒的放行速度」算出 estimatedWaitSeconds（無條件進位）。速度太低（每秒不到 0.01 人）時不給預估。

改用 SSE 推送：GET /queue/tickets/{ticketId}/events

連上時
events.py 的 ticket_events() 先在 TicketStreams 登記這條串流，再用 ticket.lua 讀一次目前狀態，交給 TicketEventStream 先送出去。之後不用再問，有變化伺服器會推。
放行那一刻
instance-0 的定時任務跑 admit.lua，放行的同時 PUBLISH 被放行的 ticket。兩台都有訂閱；這位使用者的串流連在 instance-1，所以由 instance-1 的 TicketPushWorker 推給他。Python 版實測放行到使用者知道 p50 4 ms、p95 7 ms，polling 是 495 ms。
順位
每台每秒用一支批次腳本 watch.lua（QueueStore.watch()，每批最多 500 張）取回所有連線者的狀態，順位有變才推，推送頻率不會超過 polling。
心跳
串流開著就算在線上：watch.lua 順便更新 lastSeenAt。關掉分頁，TicketEventStream 收到 http.disconnect 馬上取消登記，心跳就停。
負載
同樣 1000 人，打到 app 的請求從每秒 930 次降到 9 次，app CPU（兩台合計，單核百分比）從 39.7% 降到 9.8%；名額回收得快，每秒放行人數從 4.7 變成 9.5。

放行：兩台的定時任務都在跑

做了什麼
admit.lua 算出還能放幾人：min(MAX_ACTIVE, 架上庫存) − 已放行人數，然後從 waiting 的隊頭一個一個取出，放進 active，並設定放行截止時間（ADMISSION_WINDOW_MS）。
兩台同時跑
兩台的計時器各自觸發，但 Redis 一次只跑一支腳本：先跑的放滿名額，後跑的算出來可放 0 人。十台同時跑，結果跟一台一樣（tests/test_concurrency.py 的 test_parallel_admitters_never_exceed_max_active）。
看庫存放行
剩 3 件就最多放 3 人進來。放進來卻一定買不到，只是換個方式告訴他「賣完了」。
順便做的事
同一支腳本也會收回逾時的名額（見「放行後沒下單」），並更新放行速度給預估用。

下單扣庫存：POST /checkout {"ticketId":"…","quantity":2}

檢查
checkout.lua 依序檢查：ticket 存在、這張 ticket 還沒下過單、狀態是已放行、還沒過放行截止時間、架上庫存夠。
寫入
全部通過才在同一支腳本裡：庫存 DECRBY 2、建立訂單放進 pending（付款截止時間 PAYMENT_WINDOW_MS）、ticket 標成 ordered、從 active 移出。回 201（Location: /orders/{orderId}）。
名額
從 active 移出後，下一輪放行就能再放一個人進來。
庫存不夠
還有未付款訂單時回 409 insufficient_stock（可能是 0 件），放行期間可以重試；完全賣完才回 409 sold_out。

連點結帳，兩個請求分別打到兩台

發生什麼
兩台 instance 幾乎同時執行 checkout.lua。Redis 一次只跑一支：先到的建立訂單、扣庫存（201）；後到的看到這張 ticket 已經有 orderId，直接回傳同一張訂單（200），不再扣庫存。
為什麼
ticket 本身就是 idempotency key，不需要客戶端另外產生。
數量不同
如果第二次送的數量不一樣，回 409 ticket_used。
實測
1000 人的搶購情境裡三分之一的人這樣連點，沒有任何人拿到兩張訂單；測試裡 100 個已放行的人各點 3 次（共 300 個請求用 asyncio.gather() 同時送出），剛好成立 50 張訂單、庫存剛好 0（test_parallel_checkouts_never_oversell_nor_order_twice_per_ticket）。

付款：POST /orders/{orderId}/pay

做了什麼
pay.lua 在同一個原子步驟裡：在 payments 加一筆扣款紀錄、訂單改成 paid、從 pending 移出。回 201。
重複付款
再送一次時訂單已經是 paid，回 200，不會再加扣款紀錄。所以 201 表示「這次扣的」，200 表示「之前已經扣過」。
太晚付款
超過付款截止時間就回 410 order_expired，並在同一支腳本裡把庫存放回去。
注意
付款是模擬的。串真實金流時，扣款發生在外部，不能放進 Redis 腳本，見第 3 節最後的說明。

排隊中離開（關分頁、手機休眠）

發生什麼
使用者停止輪詢（或 SSE 串流斷了），lastSeenAt 不再更新。輪到他時，admit.lua 發現已經超過 HEARTBEAT_TIMEOUT_MS 沒心跳，把 ticket 標成 abandoned，名額直接給下一位。
為什麼要這樣
不這樣做的話，名額會放給一個已經不在的人，白白等到放行截止時間才收回。
回來了
他回來再呼叫一次 /queue/join，會拿到新的 ticket，排到最後。
設定限制
HEARTBEAT_TIMEOUT_MS 至少要是 POLL_INTERVAL_MS 的 3 倍，漏掉一兩次輪詢不會被誤判離開；設定違反時 Config.validate() 讓啟動失敗。

放行後沒下單

發生什麼
過了放行截止時間還沒下單。下一輪 admit.lua 先把 active 裡截止時間已過的人標成 expired 並移出，空出的名額在同一輪就放給隊頭的下一位。
還沒輪到定時任務
在定時任務處理之前，輪詢和下單就已經會把它當成過期（common.lua 的 ticket_status() 依當下時間判斷）。下單回 410 admission_expired。
之後
可以重新排隊，排到最後。

下單後沒付款

發生什麼
定時任務每一輪先執行 expire_orders.lua：pending 裡付款截止時間已過的訂單改成 expired，庫存 INCRBY 放回架上。
接著放行
同一輪接著執行 admit.lua，放回的庫存馬上就能放下一位進來。
不會放回兩次
付款請求和釋放同時發生時，兩支腳本都只處理還在 pending_payment 的訂單。誰先執行誰處理，另一支看到狀態已經變了就不動（test_payments_racing_the_expiry_sweep_return_each_orders_stock_once）。
實測
Python 版跑 1000 人搶 200 件的情境，有 21 筆訂單沒付款，庫存放回後被別人買走，最後 200 件全部付款。

3. 從排隊到付款：程式碼怎麼走

以 alice 從排隊一路到付款完成為例。HTTP 端點負責檢查輸入格式；所有會改變狀態的判斷都在 Lua 腳本裡，Python 只負責呼叫和翻譯結果。路徑都相對於 python/src/checkout_queue/。

  1. 排隊請求進來，先檢查格式
    api.py 的 create_api_router() 裡的 join()；web.py 的 read_json_object()、valid_user_id()

    不用 Pydantic 解析請求，因為它會把 "1" 轉成 1、錯誤回 422。read_json_object() 自己讀 body：Content-Type 不是 JSON、JSON 壞掉、null、不是物件都變成 400。userId 只接受 1–64 個英數字和 . _ - @，因為它會成為 Redis key 的一部分。

    @router.post("/queue/join")
async def join(request: Request) -> Response:
    body = await read_json_object(request)
    result = await services.queue.join(valid_user_id(body.get("userId")))
    if result.ticket is None:
        raise ApiError.conflict("sold_out", "sold out")
    if result.outcome == "created":
        location = f"/queue/tickets/{result.ticket.ticket_id}"
        return json_response(result.ticket.to_json(), 201, {"location": location})
    return json_response(result.ticket.to_json())
  2. Python 呼叫 Lua 腳本
    tickets.py 的 QueueStore.join() → sale_redis.py 的 SaleRedis.run()

    join() 產生新的 ticket 編號（ids.py 的 new_id()）、取得目前時間，交給 run()。run() 把活動的 key 前綴 cq:{SALE_ID}: 放在第一個參數，其餘照順序接上。腳本用 redis-py 的 register_script() 包起來：先送 EVALSHA，Redis 還不認得這支腳本時才載入。回覆由 ScriptReply.parse() 解析成「結果代碼 ＋ 欄位」。

    async def run(self, name: str, *args: str | int) -> ScriptReply:
    """Runs a script with the sale prefix as ARGV[1], followed by `args`."""
    return ScriptReply.parse(name, await self._eval(name, args))

async def _eval(self, name: str, args: Sequence[str | int]) -> object:
    return await self._scripts[name](keys=[], args=[self.prefix, *args])
  3. 在 Redis 裡排進隊伍
    shared/lua/join.lua（前面接著 common.lua 的共用函式）

    「查有沒有 ticket → 沒有就建立」在同一支腳本裡，同一個人同時送 20 次排隊也只會拿到一張（test_parallel_joins_from_the_same_user_yield_one_ticket）。

if current and not ended(current) then

    redis.call('HSET', key('ticket', current), 'lastSeenAt', now)
  end
  return reply('existing', ticket_view(current, now))
end

if sold_out() then return reply('sold_out') end

local seq = redis.call('INCR', key('seq'))
redis.call('HSET', key('ticket', newId), 'userId', userId, 'seq', seq, 'status', 'waiting', 'joinedAt', now, 'lastSeenAt', now)
redis.call('ZADD', key('waiting'), seq, newId)
redis.call('ZADD', key('tickets'), seq, newId)
redis.call('SET', key('user', userId), newId)
return reply('created', ticket_view(newId, now))
  4. 輪詢：更新心跳、回報順位
    QueueStore.get_ticket() → shared/lua/ticket.lua → tickets.py 的 TicketView.from_reply()、TicketView.to_json()

    腳本更新 lastSeenAt，回傳 ticket 的狀態、順位（ZRANK ＋ 1）和最近的放行速度 admitRate。from_reply() 用它們算出預估等待秒數，再加上 pollAfterMs；to_json() 轉成 camelCase、拿掉沒有值的欄位。

    改用 SSE 時，客戶端連 /queue/tickets/{ticketId}/events（events.py 的 ticket_events()），之後由 push.py 的 TicketPushWorker 推送：放行靠 Redis pub/sub 即時推（_listen()），順位每秒用 QueueStore.watch()（watch.lua）批次更新一次（_refresh_timer()）。兩個來源都排進同一個 asyncio.Queue，由 _consume() 一個一個處理，跟上次推的不一樣才推（_push()）。

    # events.py：先登記串流再讀 ticket，中間的變化不會漏掉
stream = services.streams.open(tid)
try:
    view = await services.queue.get_ticket(tid)
except BaseException:
    stream.close()
    raise
if view is None:
    stream.close()
    raise ticket_not_found()
return TicketEventStream(stream, view)
  5. 定時任務：先釋放、再放行
    maintenance.py 的 run_maintenance_loop() → SaleMaintenance.run_once() → OrderStore.expire_orders()、QueueStore.admit()

    每台每 TICK_MS 跑一次（clock.sleep_ms()，測試換成假時鐘就由測試決定什麼時候跑）。先跑 expire_orders.lua 放回逾時訂單的庫存，再跑 admit.lua，所以放回的庫存同一輪就能放行。Redis 暫時連不上時只記警告，下一輪重試；其他例外代表程式有 bug，task 結束，app.py 的 _check_crash() 讓整個程式停下來。

    -- admit.lua：從隊頭放行，跳過沒在輪詢的人
local free = math.min(maxActive, stock()) - redis.call('ZCARD', key('active'))
local inLine = redis.call('ZCARD', key('waiting'))
local admitted, abandoned, scanned = 0, 0, 0
local admittedIds = {}
while admitted < free and scanned < maxScan do
  local head = redis.call('ZPOPMIN', key('waiting'))
  if #head == 0 then break end
  scanned = scanned + 1
  local id = head[1]
  local ticketKey = key('ticket', id)
  if now - tonumber(redis.call('HGET', ticketKey, 'lastSeenAt')) > heartbeatMs then
    redis.call('HSET', ticketKey, 'status', 'abandoned')
    abandoned = abandoned + 1
  else
    local deadline = now + windowMs
    redis.call('HSET', ticketKey, 'status', 'admitted', 'admittedAt', now, 'admissionExpiresAt', deadline)
    redis.call('ZADD', key('active'), deadline, id)
    admitted = admitted + 1
    admittedIds[admitted] = id
  end
end

-- 告訴每台 instance 誰剛被放行，連著 SSE 的人馬上就能收到
if admitted > 0 then redis.call('PUBLISH', key('admitted'), table.concat(admittedIds, ' ')) end
  6. 下單：檢查數量，呼叫腳本
    api.py 的 checkout() → orders.py 的 OrderStore.checkout()

    端點先檢查 ticketId 是 32 位小寫 hex（web.py 的 valid_id()）、quantity 是 1 到 MAX_PER_ORDER 的整數（valid_quantity()；Python 的 True 也是 int，所以用 type(value) is int 擋掉）。OrderStore.checkout() 產生新的訂單編號，連同付款期限交給 checkout.lua。

  7. 在 Redis 裡扣庫存、建立訂單
    shared/lua/checkout.lua

    防超賣和防重複下單都在這裡：所有檢查和寫入在同一支腳本，中間不會有別的請求插進來。

4. 啟動時發生什麼

1. 讀設定

__main__.py 的 main() 呼叫 Config.from_env() 讀所有環境變數。數字只接受純 ASCII 數字、超出範圍、SALE_ID 有奇怪字元、心跳逾時小於輪詢間隔 3 倍，都丟 ConfigError（訊息裡有變數名稱），程式以代碼 2 結束。接著把可開的檔案數提高到 10240（raise_open_file_limit()），每個使用者可能對每台都開一條連線。

2. 連 Redis、初始化活動

serve() 用 connect() 建立連線池並 PING，連不上就記錯誤、以代碼 1 結束；連得上就用 warm_up() 把池裡 32 條連線先連好。再用 SaleRedis.initialize() 執行 init.lua：只有活動第一次啟動才設定庫存（SETNX），後啟動的 instance 或重啟時沿用目前的庫存，INITIAL_STOCK 不一樣就記一筆警告。

3. 組裝 app

create_app() 用 Services.build() 建好 SaleRedis、QueueStore、OrderStore、AuditStore、TicketBoardStore、SaleMaintenance、TicketStreams、TicketPushWorker（每場活動一份），掛上錯誤處理、兩個 middleware、/health、排隊和訂單端點、/admin/*、SSE 端點和操作頁 /。FastAPI 的 /docs、/openapi.json 和結尾斜線轉址都關掉。

4. lifespan：先訂閱，再開 port

uvicorn 先跑 lifespan 才開始聽 port：TicketPushWorker.start() 訂閱放行頻道並等 Redis 確認，所以開始接請求之前不會漏掉任何放行通知；接著啟動推送和定時任務兩個背景 task。最後聽 127.0.0.1:PORT，沒有 access log。

Lua 腳本和操作頁放在 PoC 根目錄的 shared/，三種語言版本共用同一份。Python 版不複製，執行時從 sale_redis.py 的 SHARED_DIR（src/checkout_queue/ 往上三層的 shared/）讀：load_scripts() 在 import 時把每支腳本前面接上 common.lua，所以 key()、ticket_view()、expire_order() 這些共用函式每支腳本都能用；操作頁在 create_demo_router() 建立時讀一次。檔案不見會在啟動時就失敗，而不是第一個請求才失敗。

5. 關鍵設計

每個狀態轉換一支 Lua 腳本

超賣和重複扣款的根源都是「檢查」和「寫入」之間被別人插隊。這裡每個狀態轉換（排隊、放行、下單、付款、釋放）都寫成一支腳本，Redis 一次只執行一支，所以不需要鎖、不需要重試，也不需要選主。代價是一場活動的資料必須在同一個 Redis 執行緒上，這就是承載上限。所有 key 都用 cq:{SALE_ID}: 當前綴，大括號是 Redis Cluster 的 hash tag，保證同一場活動的 key 落在同一個 slot。腳本跟 .NET 版是同一份檔案，所以兩個版本的行為不會分岔。

放行規則：名額和庫存取小的

可放行人數 = min(MAX_ACTIVE, 架上庫存) − 已放行、還沒下單的人數

MAX_ACTIVE 就是削峰的旋鈕：外面排了多少人都不影響，同時在結帳的最多就這麼多。被未付款訂單保留的庫存不算架上庫存，等訂單逾時放回，下一輪就會再放人。

截止時間當下就算，定時任務只是收尾

放行和付款的截止時間一到，輪詢、下單、付款就會當成已過期，不用等定時任務。所以就算定時任務慢了或暫時連不上 Redis，使用者看到的狀態也和實際能做的事一致。

-- common.lua：狀態依當下時間判斷
local function ticket_status(t, now)
  if t.status == 'admitted' and now >= tonumber(t.admissionExpiresAt) then return 'expired' end
  if (t.status == 'waiting' or t.status == 'admitted') and sold_out() then return 'sold_out' end
  return t.status
end

時間由各台 instance 傳入，背景工作也睡在同一個時鐘上

腳本不自己讀 Redis 的時鐘，而是由 Python 用 clock.py 的 Clock（now_ms()、sleep_ms()）取得目前時間傳進去。測試換成 tests/support.py 的 FakeClock：時間不會自己走，advance() 才往前，而且會叫醒睡到期的背景工作，所以逾時、定時放行、每秒推送的測試都不用 sleep。代價是各台 instance 的時鐘要同步（NTP）。時鐘差幾毫秒時，admit.lua 算放行速度的時間範圍至少取 1 秒，不會因此出錯（test_admitter_with_a_clock_slightly_behind_still_completes_its_pass）。

Python 版特有的做法

設計做法和理由在哪裡
請求自己解析，不用 Pydantic契約要求 "quantity":"1"、true、1.0 都是 400，錯誤一律是 {error, code}。Pydantic 預設會轉型、錯誤回 422，所以 body 由 json.loads() 讀（NaN、Infinity 也擋掉），欄位逐一檢查型別web.py
連線池而不是 multiplexerredis-py 一個進行中的指令佔一條連線。一個 event loop 同時在 Redis 上的指令很少，所以用 32 條的 BlockingConnectionPool，啟動時就一條一條連好（warm_up()），人潮湧進來時不用臨時開連線（.NET 版是啟動時連好的一條共用連線）。連線斷掉的指令換一條新連線重試，最多 3 次、分別等 0.05、0.1、0.2 秒，Redis 重啟或網路瞬斷時使用者不會察覺；Redis 真的掛了，約 0.35 秒就回 503。逾時（5 秒）不重試，慢的 Redis 不會被拖得更慢sale_redis.py 的 connect()、warm_up()
SSE 自己盯著斷線開著的串流就是心跳，所以客戶端一走就要取消登記。TicketEventStream 一邊寫事件、一邊等 ASGI 的 http.disconnect，哪個先結束就收掉另一個；不用 Starlette 的 StreamingResponse，它在某些 ASGI 版本只有寫入失敗時才發現斷線。不送 Content-Length，uvicorn 用 chunked 一段一段送出events.py
只保留最新的狀態每條串流一個「單格信箱」：新的狀態直接蓋掉還沒送出的舊狀態。全部在同一個 event loop 上跑，不需要鎖streams.py 的 TicketStream.offer()、next()
keep-alive 拉長到 130 秒uvicorn 預設閒置 5 秒就關連線。用 SSE 的客戶端排隊時，原本那條連線一直閒著，被放行後才拿它下單；5 秒會讓下單打到已關閉的連線__main__.py 的 KEEP_ALIVE_S
背景工作有 bug 就停機背景 task 用 spawn() 啟動並掛上 _check_crash()：Redis 錯誤在迴圈裡記警告後重試，其他例外讓 task 結束，on_fatal 叫 uvicorn 收工，程式以代碼 1 結束，不會默默少了放行或推送app.py、__main__.py 的 stop_on_bug()
訂閱失敗或中斷會自己補回啟動時訂閱失敗、或訂閱連線斷了，推送改由每秒的批次更新補上；_consume() 每次處理前發現沒有訂閱就重新訂閱push.py 的 _try_subscribe()、_listen()
