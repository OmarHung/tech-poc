模組化單體轉微服務｜Python 版運作說明

這頁說明 python/ 裡的程式怎麼運作：有哪幾個程式、一個請求怎麼流動、拆分前後差在哪裡。框架是 FastAPI 0.162 ＋ httpx 0.28 ＋ uvicorn（含 uvloop），套件用 uv 管理。

1. 全貌 2. 互動流程圖 3. 一個下單請求的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三個程式

這是一個小型電商：catalog 管商品和庫存，orders 管訂單。原本兩個模組都在同一個程式（模組化單體）裡，這次把 catalog 拆成獨立的微服務。

gateway

127.0.0.1:8080 ・ src/gateway/

所有請求的入口（Strangler Fig 門面）。/products 開頭的請求依目前設定送給 monolith 或 catalog-service，其他一律送 monolith。設定可以在執行中切換。

monolith

127.0.0.1:8081 ・ src/monolith/

原本的模組化單體。orders 模組留在這裡；catalog 模組⚠已轉微服務，但保留在原位，用來對照和回滾。

catalog-service

127.0.0.1:8082 ・ src/catalog_service/

從單體拆出來的微服務。裡面的 catalog 模組跟單體那份是同一套程式碼，現在由它負責商品資料。

2. 互動流程圖：四個階段

點下面的按鈕切換階段，圖上藍色虛線是請求實際走的路徑，紅色是失敗的路徑，半透明的是這個階段沒用到的部分。

階段一：模組化單體

設定
monolith CATALOG_MODE=inprocess；gateway CATALOG_ROUTE=monolith
查商品
gateway → monolith 的 catalog 路由 → InMemoryCatalog.get_product()。全部在同一個程序裡，是一般的函式呼叫。
下單
gateway → orders 模組 → CatalogPort.reserve() → InMemoryCatalog.reserve() 扣庫存 → 建立訂單。
誰回應
X-Served-By: monolith。catalog-service 已經部署，但沒有任何流量。
實測 p50
查商品 0.659 ms、下單 0.653 ms

階段二：拆出 catalog，請求仍經由單體

設定
monolith 改成 CATALOG_MODE=remote 重啟（gateway 不用動）
查商品
gateway → monolith 的 catalog 路由 → HttpCatalogClient.get_product() → HTTP → catalog-service。路由程式碼沒變，只是介面背後換了實作。
下單
orders 模組照樣呼叫 CatalogPort.reserve()，但現在是 HTTP 呼叫 catalog-service 扣庫存。orders 的程式一行都沒改。
重點
單體不再持有商品資料，資料只有 catalog-service 那一份，兩邊看到的庫存一定一致。
實測 p50
查商品 1.397 ms、下單 1.463 ms（每多一跳約 +0.8 ms，三種語言裡最多，主要花在 Python 的 HTTP client 與 server）

階段二：gateway 把 /products 直接切給 catalog-service

設定
PUT /admin/routes {"catalog":"service"}，執行中切換，不用重啟
查商品
gateway 直接送 catalog-service，不經過單體，少一跳。X-Served-By: catalog-service。
下單
不受路由影響，還是 gateway → orders → HTTP → catalog-service。
回滾
再呼叫一次 {"catalog":"monolith"} 就切回去，立即生效。負載下來回切 15 次，2,626 個請求 0 失敗。
實測 p50
查商品 0.927 ms。比拆分前慢約 0.27 ms，單獨重測時兩條路徑沒有差別，是執行順序造成的波動（詳見 PoC README）。

階段三：catalog-service 故障

狀況
catalog-service 停機。這是拆分之後才有的新故障點。
查商品
不管路由指向哪邊都回 502：直連時 gateway 回 upstream unavailable，經單體時 monolith 回 catalog unavailable。
下單
orders 呼叫 catalog-service 失敗，回 502 catalog unavailable。
仍然正常
查既有訂單（GET /orders/1）還是 200，因為訂單建立時已經存了商品名稱和價格的快照，不需要再問 catalog。
錯誤細節
客戶端只看到一句話；連線失敗的細節（網址、原因）只用 logger.warning() 寫進伺服器 log。

3. 一個下單請求的完整旅程

以階段二（CATALOG_MODE=remote）的 POST /orders {"productId":1,"quantity":2} 為例，從進門到回應經過這些程式碼：

  1. gateway 收到請求，決定送去哪裡
    src/gateway/main.py 的 proxy()、src/gateway/routing.py 的 RoutingTable.resolve()

    /orders 不是 catalog 路徑，所以一律送 monolith。用 httpx 轉發，並拿掉 Connection 這類只屬於單一連線的標頭，以及 Host、Content-Length 這類要由轉發端重新產生的標頭。

  2. monolith 解析 JSON
    src/monolith/modules/orders.py 的 create_order()

    FastAPI 把 body 驗證成 CreateOrderRequest。所有模型都繼承 ApiModel（pydantic 嚴格模式），所以 "quantity":"2" 這種字串不會被偷偷轉成數字。驗證失敗時 FastAPI 預設回 422，這裡由 catalog/api.py 的 register_error_handlers() 統一改成 400 {"error": ...}。

  3. orders 模組驗證輸入，再透過介面扣庫存
    src/monolith/modules/orders.py 的 OrderService.place()

    先在本地驗證（數量要在 1–100、商品編號要是正整數），不合格就直接回 400，不會浪費一次網路呼叫。接著呼叫 self._catalog.reserve()，它只知道 CatalogPort 這個介面，不知道背後是本地還是遠端。

    async def place(self, product_id: int, quantity: int) -> Order:
    validate_id(product_id, "productId")
    validate_quantity(quantity)
    product = await self._catalog.reserve(product_id, quantity)
    with self._lock:
        order = Order(
            id=next(self._ids),
            product_id=product_id,
            product_name=product.name,
            unit_price=product.price,
            quantity=quantity,
            total=product.price * quantity,
        )
        self._orders[order.id] = order
    return order
  4. 介面背後是 HTTP client，送出 HTTP 請求
    src/monolith/modules/catalog/remote.py 的 HttpCatalogClient.reserve()

    送出 POST http://127.0.0.1:8082/products/1/reserve {"quantity":2}，逾時 2 秒。httpx.AsyncClient 在 create_app() 建立、在 lifespan 結束時關閉，連線會重複使用。如果是階段一（inprocess），這一步換成直接呼叫 InMemoryCatalog.reserve()，接著跳到第 5 步的邏輯，只是在同一個程序裡執行。

  5. catalog-service 扣庫存
    src/catalog_service/catalog/api.py 的 reserve_product() → store.py 的 InMemoryCatalog.reserve()

    在鎖裡「檢查庫存 → 用 model_copy() 建立一個新的 Product 取代舊的」，所以很多人同時下單也不會超賣（有測試：50 個並行請求搶 10 件，剛好 10 個成功）。Product 是 frozen 模型，舊物件不會被修改。

    async def reserve(self, product_id: int, quantity: int) -> Product:
    validate_quantity(quantity)
    with self._lock:
        current = self._products.get(product_id)
        if current is None:
            raise product_not_found(product_id)
        if current.stock < quantity:
            raise insufficient_stock(product_id, quantity, current.stock)
        updated = current.model_copy(update={"stock": current.stock - quantity})
        self._products[product_id] = updated
        return updated
  6. monolith 把 HTTP 回應還原成原本的結果
    src/monolith/modules/catalog/remote.py 的 _send()、_error_from()

    成功就解析成 Product；400、404、409 還原成跟本地實作一模一樣的例外（InvalidInput、NotFound、InsufficientStock），所以 orders 分不出差別。連不上或其他錯誤一律變成 CatalogUnavailable（502），細節只寫 log。

    看 _send() 和 _error_from() 的程式碼 
    async def _send(self, method: str, path: str, body: dict[str, int] | None = None) -> httpx.Response:
    try:
        response = await self._http.request(method, path, json=body)
    except httpx.HTTPError as exc:
        logger.warning("catalog-service request failed: %r", exc)
        raise CatalogUnavailable("catalog unavailable") from exc
    if response.is_success:
        return response
    raise _error_from(response)


def _error_from(response: httpx.Response) -> CatalogError:
    try:
        message = _ErrorBody.model_validate_json(response.content).error
    except ValidationError:
        message = f"catalog-service returned {response.status_code}"
    error_type = _ERRORS_BY_STATUS.get(response.status_code)
    if error_type is None:
        logger.warning("catalog-service error %s: %s", response.status_code, message)
        return CatalogUnavailable("catalog unavailable")
    return error_type(message)
  7. 建立訂單，回 201
    OrderService.place()（第 3 步那段程式的後半）

    訂單會複製商品名稱和單價（快照），之後 catalog 改價或停機都不影響已成立的訂單。回應由 catalog/api.py 的 ServedByMiddleware 加上 X-Served-By: monolith。

  8. gateway 把回應原樣轉回 client
    src/gateway/main.py 的 proxy() 結尾

    用上游的狀態碼、標頭（含 X-Served-By）和內容組一個新的 Response 傳回。

每種錯誤在哪裡被擋下

狀況在哪裡被擋回應
JSON 格式錯、型別錯、少欄位第 2 步 FastAPI 的 RequestValidationError → register_error_handlers()400
數量不在 1–100、商品編號不是正整數第 3 步 validate_quantity()、validate_id()400
商品不存在第 5 步回 404 → 第 6 步還原成 NotFound404
庫存不足第 5 步回 409 → 第 6 步還原成 InsufficientStock409
catalog-service 連不上、逾時第 6 步 _send()502 catalog unavailable
gateway 連不到 monolith第 1 步 proxy()502 upstream unavailable

每個 catalog 例外都帶著自己的 status_code（定義在 catalog/errors.py），register_error_handlers() 把它統一轉成 {"error": "..."}。

還沒處理的情況：第 5 步扣庫存成功，但回應在第 6 步之前逾時，monolith 會回 502、不建立訂單，可是庫存已經被扣了。正式上線前要補冪等鍵和補償機制（Saga / Outbox）。

4. 啟動時發生什麼

三個程式都由 run.sh 用 uvicorn --factory 啟動：uvicorn 綁定 127.0.0.1 和 $PORT，然後呼叫各自的 create_app() 建立 FastAPI app。

gateway

src/gateway/main.py：GatewayConfig.from_env() 讀 MONOLITH_URL、CATALOG_URL、CATALOG_ROUTE → 建立 httpx client（逾時 5 秒、不跟隨轉址）和 RoutingTable → 註冊 health、admin、萬用轉發路由。

monolith

src/monolith/main.py：MonolithConfig.from_env()（CATALOG_MODE 打錯會直接啟動失敗）→ 依模式決定 catalog 用哪個實作 → 掛上錯誤處理、X-Served-By、catalog 與 orders 路由。

catalog-service

src/catalog_service/main.py：載入三筆種子商品（InMemoryCatalog.seeded()）→ 掛上錯誤處理、X-Served-By、catalog 路由和 health。

整個遷移的開關就在 monolith 的 create_app() 這幾行：同一個 CatalogPort，依環境變數換成不同實作。

settings = config or MonolithConfig.from_env()
http = (
    httpx.AsyncClient(base_url=settings.catalog_url, timeout=REQUEST_TIMEOUT_S)
    if settings.catalog_mode == "remote"
    else None
)
catalog: CatalogPort = HttpCatalogClient(http) if http else InMemoryCatalog.seeded()
# ……
app.include_router(create_catalog_router(catalog))
app.include_router(create_orders_router(OrderService(catalog)))

5. 關鍵設計

介面是拆分的接縫

orders 只依賴 CatalogPort 這個 Protocol，所以 catalog 從「同程序內」搬到「另一個程序」時，只要新增一個有同樣方法的 HttpCatalogClient。Protocol 是結構型別：兩個實作都不用繼承它，只要方法簽章對得上就行。這就是為什麼起點必須是模組化單體：模組之間如果直接存取彼此的資料，就沒有這條接縫可以切。

# src/monolith/modules/catalog/port.py
class CatalogPort(Protocol):
    async def list_products(self) -> list[Product]: ...

    async def get_product(self, product_id: int) -> Product: ...

    async def reserve(self, product_id: int, quantity: int) -> Product:
        """Atomically takes `quantity` units out of stock and returns the updated product."""
        ...

gateway 切換路由：一次賦值，不影響進行中的請求

RoutingTable.switch() 只是把一個屬性換成新值。每個請求進來時呼叫 resolve() 讀一次、決定上游之後就不再看它，所以切換那一瞬間正在處理的請求不會被中斷。

# src/gateway/routing.py
def resolve_upstream(path: str, route: CatalogRoute, upstreams: Upstreams) -> str:
    """Everything goes to the monolith except catalog paths once they are switched over."""
    if route == "service" and is_catalog_path(path):
        return upstreams.catalog
    return upstreams.monolith

其他

設計做法在哪裡
錯誤跨網路後不變形每個例外類別帶 status_code；遠端 client 用 _ERRORS_BY_STATUS 把狀態碼對回同一個類別catalog/errors.py、remote.py
錯誤訊息不外洩客戶端只看到「catalog unavailable」，網址和原因只用 logger.warning() 寫進 logremote.py
嚴格的 JSON 格式ApiModel：camelCase 別名、strict（不自動轉型）、frozen（不可修改）catalog/models.py
標示誰回應ServedByMiddleware 是純 ASGI middleware，比 @app.middleware("http") 少一層開銷catalog/api.py
兩份 catalog 不會走樣兩份 catalog/ 檔案逐字相同（套件內一律用 from .errors import 這種相對匯入）；tests/test_catalog.py 用 fixture 對兩份各跑一次同樣的測試tests/test_catalog.py
只聽本機三個程式都只綁 127.0.0.1；/admin/routes 沒有驗證，正式環境一定要加run.sh、gateway/main.py
