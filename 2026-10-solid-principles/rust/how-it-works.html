SOLID 原則範例｜Rust 版運作說明

這頁說明 rust/ 裡的程式怎麼運作：SOLID 五個原則各用一個電商結帳的小情境，同一個模組裡放「違反版」和「遵守版」，示範程式把兩者的差別印出來。範例用 Rust 1.98、edition 2024，沒有外部 crate（只用標準函式庫的 trait、Result、RefCell），測試用 cargo test（整合測試 ＋ doctest）。

1. 全貌：五個原則各一個模組，一支示範程式，五組測試

這份實作不開任何 port，也沒有外部服務。每個模組對應一個原則，裡面先放違反版（名稱多半以 Legacy 開頭），再放遵守版。示範程式依序跑五個情境，把兩個版本在同一個需求下的結果並排印出來。

src/srp.rs ～ src/dip.rs

五個原則 ・ 由 src/lib.rs 組成 solid_principles crate

每個檔案開頭的 //! 寫情境，接著是 // --- 違反 --- 和 // --- 遵守 --- 兩段。lsp.rs 沿用 ocp.rs 的 DiscountRule trait。

src/main.rs

示範程式 ・ ./run.sh demo

依序呼叫 show_srp() 到 show_dip()。「滿千折百」的新規則 SpendThresholdOff 就定義在這裡，用來證明不用改 ocp.rs。三種語言的輸出逐字相同。

tests/srp.rs ～ tests/dip.rs

22 個測試 ＋ 4 個 doctest ・ ./run.sh test

違反版的錯誤真的會發生，遵守版不會。「貨到付款編譯不過」沒辦法寫成一般測試，所以寫成 src/isp.rs 裡的 compile_fail doctest。

2. 互動流程圖：一個需求進來，漣漪擴散到哪裡

點按鈕切換原則。左半是違反版、右半是遵守版，兩邊處理的是同一個需求。藍色虛線是正常運作的路徑，紅色點線是被連帶影響或出錯的路徑，紅色虛框是有問題的地方，紫框是提出需求的角色。

S：單一職責原則——一個模組只為一種角色改變

需求
財務要求發票金額改成含 5% 營業稅。物流沒有任何新需求，規則還是「未稅小計滿 1000 元免運」。
違反版
LegacyOrder 的 invoice_amount() 和 ships_free() 共用私有方法 amount()。把稅加進 amount() 後，960 元的訂單算成 1008 元，免運判斷跟著變成「是」。編譯器不會有任何意見：型別都對，只是意思變了。
遵守版
財務的 InvoiceCalculator::amount() 和物流的 ShippingPolicy::ships_free() 分開。稅只寫在前者，後者還是拿未稅的 subtotal() 比較，免運維持「否」。兩個都是沒有欄位的 unit struct，示範程式直接寫 InvoiceCalculator.amount(&items)。
重點
可以共用的是「兩邊都認同的事實」（未稅小計），不能共用的是「某一方的規則」（稅）。這不是在算型別有幾個方法，而是看有幾種人會要求它改。
對應測試
tests/srp.rs 的 legacy_order_tax_change_leaks_into_free_shipping、shipping_policy_is_unaffected_by_tax

O：開放封閉原則——加功能是寫新程式，不是改舊程式

需求
原本有 VIP 九折、員工八折，行銷部新增「滿 1000 折 100」。
違反版
legacy_total_after_discount(subtotal, kind) 用 match 比對字串。傳 "threshold" 進去會落到 _ 分支，回傳 Err(UnsupportedDiscount { kind: "threshold" })，印出來是「不支援的折扣：threshold」。要支援就得在這個已經測過的函式裡多加一個分支，示範輸出的「只能回去改這串判斷」指的就是這個 match。
遵守版
total_after_discount(subtotal, rule: &dyn DiscountRule) 只認 trait。新的 SpendThresholdOff 寫在 src/main.rs，加一段 impl DiscountRule for SpendThresholdOff 就能用，1200 元算出 1100 元。main.rs 是另一個 crate（執行檔），根本改不到 ocp.rs，照樣能擴充。
代價
多了一個 trait 和數個小型別。折扣種類固定、很少變的話，match 反而比較好讀；種類若改成 enum，編譯器還會檢查每個 match 有沒有漏掉。
對應測試
tests/ocp.rs 的 legacy_rejects_a_new_kind_until_someone_edits_it、new_rule_works_without_editing_the_module（新規則定義在測試檔裡）、rules_match_legacy_for_existing_kinds（舊的三種折扣兩版結果相同）

L：里氏替換原則——子型別要守住父型別的契約

需求
新增「折 200 元」。小計只有 150 元的訂單套用後，總額應該是多少？
契約
DiscountRule 的 doc comment 寫明 0 <= discount(subtotal) <= subtotal。total_after_discount() 依賴這個契約，才能保證總額不會是負數。
違反版
UncappedAmountOff(200) 不管小計多少都回 200，總額變成 −50 元。型別完全合法，編譯器和 clippy 都沒意見，呼叫端也沒寫錯，錯的是這個實作沒守住契約。
遵守版
FixedAmountOff(200) 回 self.0.min(subtotal)，總額最低是 0 元。
怎麼把關
trait 只規定簽章，契約不在型別系統裡，所以用 contract_violations(rule, &SAMPLE_SUBTOTALS) 拿一組樣本小計檢查，再在 every_shipped_rule_honors_the_contract 裡用迴圈把每個實作跑一次。新加的 SpendThresholdOff 也在示範程式裡過了一次契約檢查。
檢查的是實例
契約檢查只對「這組參數」有效。SpendThresholdOff { threshold: 1000, amount: 100 } 守得住，但 SpendThresholdOff { threshold: 50, amount: 100 } 遇到小計 60 會折 100，一樣違反契約。要一勞永逸，就得像 FixedAmountOff 一樣在 discount() 裡設上限，或把欄位改成私有、提供一個在 amount > threshold 時回 Err 的 new()。
對應測試
tests/lsp.rs 的 uncapped_amount_off_makes_the_total_negative、contract_check_catches_the_uncapped_rule、every_shipped_rule_honors_the_contract

I：介面隔離原則——不要逼實作者依賴用不到的方法

需求
新增貨到付款。它能收款，但不能線上退款，也沒有付款資訊可以記住給下次用。
違反版
肥 trait LegacyPaymentMethod 有 charge()、refund()、remember() 三個方法，後兩個回傳 Result<String, NotSupported>。LegacyCashOnDelivery 只能回 Err(NotSupported("貨到付款不能線上退款"))。示範程式把它存成 &dyn LegacyPaymentMethod：型別上看起來每種付款都能退款，要執行才知道這一個不行。
遵守版
拆成 Chargeable、Refundable、Rememberable 三個 trait，方法都不用 Result，因為做不到的事根本不會出現在型別上。CashOnDelivery 只有 impl Chargeable。refund_order(method: &impl Refundable, amount) 只收實作了 Refundable 的型別。
Rust 的做法
擋下發生在編譯期，不需要另外的工具：refund_order(&CashOnDelivery, 300) 編譯不過（E0277），CashOnDelivery.refund(300)、CashOnDelivery.remember() 也編譯不過（E0599）。「編譯不過」沒辦法寫成一般的 #[test]，所以這三段寫成 src/isp.rs 裡的 compile_fail doctest，cargo test 會確認它們真的編譯失敗。compile_fail 只看「有沒有失敗」不看原因，stable 版的 rustdoc 也不檢查標在後面的錯誤碼，所以旁邊另外放一段能編譯的 refund_order(&CreditCard, 300) doctest 當對照，證明 import 路徑沒寫錯、失敗真的是 trait 不符造成的。反過來，Rust 沒辦法在執行時問「它有沒有實作 Refundable」，所以示範輸出「能退款嗎 → 否」是寫死的字，由這些 doctest 保證。Python 版要靠 mypy 在執行前擋下。
附帶觀察
違反 ISP 常常順便違反 LSP：LegacyCashOnDelivery 回 Err，等於沒守住「付款方式可以退款」的契約。
對應測試
tests/isp.rs 的 legacy_cash_on_delivery_is_forced_to_stub_two_methods、cash_on_delivery_only_implements_charging（轉成 &dyn Chargeable 編得過，就代表有實作）；src/isp.rs 的 3 個 compile_fail doctest

D：依賴反轉原則——高層和低層都依賴抽象

需求
結帳後寄通知給客人。這個環境沒有 SMTP 伺服器（SmtpMailer 的 send() 一定回 Err(ConnectionError)，模擬測試環境的真實狀況）。
違反版
LegacyCheckoutService::new() 自己寫 Self { mailer: SmtpMailer }，欄位型別就是具體的 SmtpMailer，外面換不掉。結帳一定失敗，連「金額算得對不對」都沒辦法測。
遵守版
CheckoutService<'a> 存一個 &'a dyn Notifier，由 CheckoutService::new() 傳進來。測試和示範注入 &RecordingNotifier，不連 SMTP 也能跑完結帳並檢查通知內容；正式環境注入 &SmtpMailer，CheckoutService 一行都不用改。
Rust 的寫法
Python 的 Protocol 看形狀就算符合；Rust 要明寫 impl Notifier for SmtpMailer，這一行就是「低層也依賴抽象」的具體樣子。Notifier::send() 只拿 &self（寄信不該改動寄信的人），所以 RecordingNotifier 把記錄放在 RefCell<Vec<(String, String)>> 裡，send() 用 borrow_mut() 推進去，結帳後用 sent() 拿一份複本。選 &dyn 而不是泛型，是為了讓 CheckoutService 的型別裡不出現具體的通知型別。
跑不到的路徑
這份沒有量覆蓋率，但結論和 Python 版一樣：LegacyCheckoutService::checkout() 的 Ok(receipt) 永遠跑不到，因為前一行 self.mailer.send(email, &receipt)? 一定帶著 Err 提早回傳。編譯器不會警告，因為型別上它是走得到的。換不掉 SmtpMailer 就測不了成功的情況，這正是違反 DIP 的代價。
和其他 PoC 的關係
模組化單體轉微服務能做到「呼叫端不改、把目錄模組換成 HTTP 客戶端」，靠的就是同一招：訂單模組只依賴目錄的介面。
對應測試
tests/dip.rs 的 legacy_checkout_cannot_run_without_an_smtp_server、checkout_with_a_fake_notifier_needs_no_smtp_server、checkout_uses_whatever_notifier_it_is_given

3. 一條新折扣規則的旅程

SOLID 不是「請求進、回應出」的程式，這一節改成追一個改動：行銷部要「滿 1000 折 100」，從寫出新規則、算出總額、檢查契約到測試把關，依序經過這些程式碼。這條路線同時用到 O 和 L。

  1. 在 crate 外面寫新規則
    src/main.rs 的 SpendThresholdOff

    沒有繼承，只要 impl DiscountRule for SpendThresholdOff，就能交給 total_after_discount()。Rust 的規則是「trait 或型別至少有一個是自己的」才能寫 impl，這裡型別是自己的，所以在 lib 外面也能擴充。

    struct SpendThresholdOff {
    threshold: i64,
    amount: i64,
}

impl DiscountRule for SpendThresholdOff {
    fn discount(&self, subtotal: i64) -> i64 {
        if subtotal >= self.threshold {
            self.amount
        } else {
            0
        }
    }
}
  2. 算總額的函式不用改
    src/ocp.rs 的 DiscountRule、total_after_discount()

    示範程式把 &SpendThresholdOff { threshold: 1000, amount: 100 } 傳進去，自動轉成 &dyn DiscountRule。rule.discount(1200) 在執行時查表找到對的實作，拿到 100，回傳 1100。這個函式從頭到尾不知道「滿千折百」存在。

    /// 契約：0 <= discount(subtotal) <= subtotal。lsp 模組會檢查這件事。
pub trait DiscountRule {
    fn discount(&self, subtotal: i64) -> i64;
}

pub fn total_after_discount(subtotal: i64, rule: &dyn DiscountRule) -> i64 {
    subtotal - rule.discount(subtotal)
}
  3. 檢查新規則有沒有守住契約
    src/lsp.rs 的 contract_violations()

    拿樣本小計 SAMPLE_SUBTOTALS（[0, 150, 999, 1000, 5000]）逐一呼叫 discount()，回傳不符合 0 <= 折扣 <= 小計 的那些；(0..=subtotal).contains(..) 就是這個不等式。SpendThresholdOff 小計未滿 1000 時折 0，滿了折 100，全部守住，回傳空的 Vec。Rust 沒有預設參數，所以樣本要明確傳進去。

    pub fn contract_violations(rule: &dyn DiscountRule, subtotals: &[i64]) -> Vec<i64> {
    subtotals
        .iter()
        .copied()
        .filter(|&subtotal| !(0..=subtotal).contains(&rule.discount(subtotal)))
        .collect()
}
  4. 如果新規則沒守住契約
    src/lsp.rs 的 UncappedAmountOff

    型別一樣合法，total_after_discount() 照樣接受，但 150 元的訂單會算出 −50 元。contract_violations(&UncappedAmountOff(200), &SAMPLE_SUBTOTALS) 回傳 vec![0, 150]，指出是哪些小計出事。參數名稱前面的底線 _subtotal 是告訴編譯器「我故意不用它」，剛好也是「根本沒看小計」的線索。

    #[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct UncappedAmountOff(pub i64);

impl DiscountRule for UncappedAmountOff {
    fn discount(&self, _subtotal: i64) -> i64 {
        self.0
    }
}
  5. 測試把每個規則都檢查一次
    tests/lsp.rs、tests/ocp.rs

    沒有用 rstest 這類外部 crate，參數化就是陣列加迴圈；assert_eq! 的第三個參數會在失敗時印出是第幾條規則。tests/ocp.rs 也在測試檔裡自己定義一份 SpendThresholdOff，證明 crate 外面就能擴充。

    #[test]
fn every_shipped_rule_honors_the_contract() {
    let rules: [&dyn DiscountRule; 4] = [
        &NoDiscount,
        &PercentOff(10),
        &PercentOff(20),
        &FixedAmountOff(200),
    ];

    for (index, rule) in rules.into_iter().enumerate() {
        assert_eq!(
            contract_violations(rule, &SAMPLE_SUBTOTALS),
            Vec::<i64>::new(),
            "rules[{index}]"
        );
    }
}
  6. 印出結果
    src/main.rs 的 show_ocp()、show_lsp()

    印出 [遵守] 套 SpendThresholdOff(1000, 100) → 1100 元，以及「契約檢查 NoDiscount、PercentOff(10)、PercentOff(20)、SpendThresholdOff(1000, 100)、FixedAmountOff(200)：全部通過」。型別名稱和參數是手寫的標籤，不靠 Debug（具名欄位的 struct 用 {:?} 會印成 SpendThresholdOff { threshold: 1000, amount: 100 }），這樣三種語言才能印出一樣的字。

每種錯誤在哪裡、什麼時候被發現

狀況在哪裡什麼時候發現結果
違反版遇到新的折扣種類legacy_total_after_discount() 的 _ 分支執行時Err(UnsupportedDiscount { kind: "threshold" })，Display 是「不支援的折扣：threshold」
折扣規則折得比小計還多contract_violations()、every_shipped_rule_honors_the_contract跑測試時列出違反契約的小計；不檢查的話執行時算出負數總額
違反版對貨到付款退款LegacyCashOnDelivery 的 refund()執行時Err(NotSupported("貨到付款不能線上退款"))
遵守版對貨到付款退款refund_order(method: &impl Refundable, ...) 的 trait 限制編譯期E0277，程式根本編不出來。由 src/isp.rs 的 compile_fail doctest 保證；compile_fail 不檢查錯誤碼，所以旁邊另外放一段能編譯的 refund_order(&CreditCard, 300) doctest 當對照
沒有 SMTP 伺服器impl Notifier for SmtpMailer 的 send()執行時Err(ConnectionError)，Display 是「連不到 smtp.example.com:25」；遵守版可以改注入 RecordingNotifier 避開
改了財務規則，物流被連帶影響LegacyOrder 的私有 amount()上線後才發現（沒有任何錯誤）960 元的訂單被判成免運；只有寫了 legacy_order_tax_change_leaks_into_free_shipping 這種測試才抓得到

最難發現的是 SRP 那一列：沒有 Err、沒有編譯錯誤，只是結果悄悄變了。其他原則被違反時，多少還會拿到一個 Err，或是直接編譯不過。

4. 啟動時發生什麼

src/main.rs

fn main() 依序呼叫 show_srp()、show_ocp()、show_lsp()、show_isp()、show_dip()。每個函式自己建立需要的值，彼此不共用狀態。沒有設定檔，也不讀環境變數。main() 不回傳 Result：所有失敗都在 outcome() 裡變成一行字。

五個原則模組

src/lib.rs 只有 pub mod，沒有全域狀態，也沒有初始化。唯一的「組裝」發生在 show_dip()：它決定 CheckoutService::new() 要拿 &recorder 還是 &SmtpMailer，這就是 DIP 說的組裝點（composition root）。

測試

cargo test 依序跑 lib 和 main 的單元測試（都是 0 個）、tests/ 底下 5 個各自獨立編譯的整合測試檔（22 個），最後是 doctest（4 個：1 個正常執行、3 個 compile_fail）。Python 版的 43 個是 parametrize 展開後的數字；Rust 的參數化寫成迴圈，ocp 的 3 組和 15 組、lsp 的 4 組各只算 1 個測試。Python 用 mypy 檢查型別的 2 個測試，在這裡就是 ISP 的 doctest。

fn show_dip() {
    ...
    let recorder = RecordingNotifier::default();
    let receipt = outcome(CheckoutService::new(&recorder).checkout(CUSTOMER_EMAIL, 1080));
    let sent = recorder.sent();
    ...
    let smtp = outcome(CheckoutService::new(&SmtpMailer).checkout(CUSTOMER_EMAIL, 1080));

outcome() 把 Result 轉成字串：Ok 印值，Err 印「錯誤：…」。違反版的失敗也能印成一行，不用 panic，示範程式也不會中斷。

/// 成功印結果，失敗印「錯誤：訊息」
fn outcome<T: Display, E: Display>(result: Result<T, E>) -> String {
    match result {
        Ok(value) => value.to_string(),
        Err(error) => format!("錯誤：{error}"),
    }
}

5. 關鍵設計

違反版和遵守版放在同一個模組

每個檔案上半是違反版、下半是遵守版，打開一個檔案就能對照。名稱撞到時，違反版加 Legacy 前綴（LegacyOrder、LegacyCashOnDelivery、LegacyCheckoutService）。LSP 的違反版不是舊寫法，而是「型別對但行為錯」的新規則，所以叫 UncappedAmountOff。

Rust 用 trait 當介面

DiscountRule、Chargeable、Notifier 都是 trait，要明寫 impl Trait for Type 才算符合，不像 Python 的 Protocol 看形狀就算。好處是沒實作就編譯不過，ISP 的擋下發生在編譯期；限制是 trait 只規定簽章，契約（0 ≤ 折扣 ≤ 小計）一樣沒有東西強迫你守住，所以 LSP 還是要靠 contract_violations() 和測試。需要把不同規則放進同一個陣列時用 &dyn Trait（執行時分派）；refund_order() 用 &impl Refundable（泛型，編譯時決定），兩種都能擋下貨到付款。

例外換成 Result 和錯誤型別

Python 丟例外的地方，這裡都回傳 Result，不用 panic 模擬例外。三個錯誤型別 UnsupportedDiscount（ocp.rs）、NotSupported（isp.rs）、ConnectionError（dip.rs）都實作 Display（訊息和 Python 逐字相同）和 std::error::Error。ISP 的肥 trait 只有 refund()、remember() 回傳 Result，charge() 直接回 String；遵守版的三個 trait 都不用 Result。

輸出只印型別名稱

型別名稱在三種語言都是 PascalCase，方法名稱則不一樣（Rust 和 Python 是 ships_free，C# 是 ShipsFree）。示範輸出只出現型別名稱和中文描述，所以可以和 Python、.NET 版用 diff 逐字比對。trait 名稱也不印，因為 C# 慣例會加 I 前綴。

代價：型別變多了

原則違反版遵守版什麼時候不值得
S1 個 struct2 個 struct ＋ 1 個共用函式只有一種角色會要求它改的時候
O1 個函式 ＋ 1 個錯誤型別1 個 trait ＋ 2 個 struct ＋ 1 個函式，之後每種折扣再 ＋1 個 struct種類固定、幾年才改一次的時候
L1 個 struct1 個 struct ＋ 契約檢查沒有不值得的時候：違反 LSP 就是 bug
I1 個 trait ＋ 2 個 struct ＋ 1 個錯誤型別3 個 trait ＋ 2 個 struct ＋ 1 個函式所有實作都真的做得到每個方法的時候
D1 個 struct1 個 trait ＋ 1 個 struct ＋ 1 個測試替身，外加 impl Notifier for SmtpMailer依賴的東西本身就是純計算、不碰外部的時候

O 和 I 的違反版在 Rust 多了一個錯誤型別：Python 可以直接丟內建的例外，Rust 的 Err 要有一個型別裝著。

其他

設計做法在哪裡
金額都用 i64新台幣元，不會有浮點誤差。用有號整數是因為 LSP 的違反版會算出負數。整數除法：Rust 的 / 往 0 取整，Python 的 // 往下取整，只有負數會不同；所有樣本都不是負數，三種語言算出來一樣srp.rs、ocp.rs
單一欄位用 tuple structPercentOff(10)、UncappedAmountOff(200)、FixedAmountOff(200) 寫起來和輸出的標籤一樣；兩個欄位的 SpendThresholdOff 用具名欄位，免得搞混門檻和折扣ocp.rs、lsp.rs、main.rs
沒有預設參數Python 的 contract_violations(rule)，在 Rust 要寫成 contract_violations(rule, &SAMPLE_SUBTOTALS)lsp.rs
唯一會變的東西規則都是 Copy 的小 struct，方法只拿 &self。RecordingNotifier 的 RefCell 是唯一的內部可變性，因為「記錄收到的通知」本來就是副作用；sent() 回傳複本，不把借用交出去dip.rs
new() 和 Default 都有LegacyCheckoutService 有 new() 就得有 Default（clippy 的 new_without_default）。new() 裡明寫 Self { mailer: SmtpMailer }，讓「自己建立依賴」看得見dip.rs
違反版的錯誤也寫成測試測試斷言「違反版真的會出錯」，避免範例變成只有口頭說明每個 tests/*.rs
沒有外部 crateCargo.toml 沒有 [dependencies]；參數化測試用迴圈，不用 rstestCargo.toml
