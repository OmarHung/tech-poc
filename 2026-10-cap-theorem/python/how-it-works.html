CAP 定理範例｜Python 版運作說明

這頁說明 python/ 裡的程式怎麼運作：怎麼在單一程序裡模擬 3 台節點和網路分區，CP 和 AP 兩種模式在分區、恢復時各發生什麼事。範例只用 Python 3.12 標準函式庫（dataclasses、enum），測試用 pytest 9.2 ＋ pytest-cov 7.1。

1. 全貌 2. 互動流程圖 3. 一筆寫入的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：一個模擬、一支示範程式、一組測試

這份實作沒有真的網路，也不開任何 port。3 台節點 A、B、C 只是記憶體裡的資料，「網路分區」用「節點分組」表示：同一組內可以互相連線，跨組連不到。這樣每次跑的結果都一樣，不會被真實網路的抖動干擾。

cap.py

模擬本體 ・ 被 demo.py 和測試匯入

叢集 Cluster 和五個操作：new_cluster() 建立、partition() 切斷網路、write() 寫入、read() 讀取、heal() 恢復並合併。每個操作都回傳新的叢集，舊的不變。

demo.py

示範程式 ・ ./run.sh demo

依序跑三個情境：3 台 CP、3 台 AP、只有 2 台的 CP，把每一步的結果印出來。三種語言版本的輸出逐字相同。

test_cap.py

14 個測試 ・ ./run.sh test

README 的每一條成功標準都對應一個測試：CP 少數派被拒、AP 兩側分歧、LWW 合併丟掉已確認的寫入、2 台 CP 全停擺等。

2. 互動流程圖：分區前、分區中、恢復後

點下面的按鈕切換情境。藍色虛線是寫入或複製實際走的路徑，紅色是被擋下的路徑，紅色長虛線是網路斷掉的位置。節點方框裡是那一台目前 x 的值。情境順序跟 demo.py 一樣。

正常：沒有分區（CP、AP 都一樣）

呼叫
write(cluster, "A", "x", "1")
結果
成功。A、B、C 都有 x=1（時間戳 1）。
為什麼
沒有分區時只有一個分組，3 台都連得到。write() 把新版本放進同組每一台的 store。這時 CP 和 AP 的行為完全一樣，差別只在網路斷掉之後。
模擬的簡化
同組內的複製是瞬間完成的。真實系統複製要花時間，AP 系統通常是非同步複製。
對應測試
test_write_returns_new_cluster_without_changing_the_original

CP：分區中，少數派那側停止服務

呼叫
partition(cluster, {"A", "B"}, {"C"}) → write(cluster, "A", "x", "2") → write(cluster, "C", "x", "3") → read(cluster, "C", "x")
結果
A 寫入成功，複製到 B。C 的寫入和讀取都回 Result(ok=False, reason="只連得到 1 台，需要 2 台才過半")。
為什麼
_reject_without_quorum() 比較「同組有幾台」和 quorum()（3 台要 2 台）。{A, B} 有 2 台，過半；{C} 只有 1 台，不過半。
代價
C 那側完全不能用。但沒有人讀到舊資料，兩邊的資料也沒有分歧。
對應測試
test_cp_minority_side_rejects_writes_and_reads_during_partition、test_cp_majority_side_keeps_serving_during_partition

CP：恢復後，C 追上進度，沒有遺失

呼叫
heal(cluster)
結果
三台都是 x=2，回傳的 lost 是空的。
為什麼
合併時 x 有兩個版本：A、B 上的 x=2（時間戳 2）和 C 上的 x=1（時間戳 1）。x=2 比較新，勝出。x=1 在分區前（partitioned_at = 1）就存在，輸掉只算「落後」，不算遺失。
對應測試
test_cp_heal_loses_no_acknowledged_write

AP：分區中，兩邊照常服務，但資料分歧

呼叫
跟 CP 一樣：write(cluster, "A", "x", "2") → write(cluster, "C", "x", "3")
結果
兩筆寫入都成功。read(cluster, "A", "x") 讀到 2，read(cluster, "C", "x") 讀到 3。
為什麼
AP 模式下 _reject_without_quorum() 直接放行。寫入只會複製給同組的節點，所以兩組各有各的值。
代價
同一個 key 在兩邊的值不一樣。在 C 寫入之前讀 C，會讀到分區前的舊值 1。
對應測試
test_ap_both_sides_accept_writes_during_partition、test_ap_reads_diverge_during_partition、test_ap_minority_side_reads_stale_value_during_partition

AP：恢復後，last-write-wins 默默丟掉一筆已確認的寫入

呼叫
heal(cluster)
結果
三台都是 x=3。回傳的 lost 裡有 A 寫入的 x=2。
為什麼
x=2（時間戳 2）和 x=3（時間戳 3）都是分區期間寫的，last-write-wins 選時間戳大的 x=3。x=2 的時間戳 2 大於 partitioned_at（1），所以算遺失。
代價
client1 早就收到「寫入成功」，之後 x=2 被蓋掉，沒有任何通知。
對應測試
test_ap_heal_with_last_write_wins_drops_an_acknowledged_write

延伸：只有 2 台的 CP，分區時整個服務停擺

呼叫
partition(new_cluster(Mode.CP, nodes=("A", "B")), {"A"}, {"B"}) → A、B 各寫一次
結果
兩邊都被拒絕：只連得到 1 台，需要 2 台才過半。
為什麼
quorum() 是 len(nodes) // 2 + 1，2 台需要 2 台。網路一斷，哪一邊都湊不到。
意義
雙機備援如果選 CP，就要加一個第三方仲裁（witness）湊出第三票，見雙機備援 PoC。
對應測試
test_cp_with_two_nodes_cannot_serve_on_either_side_of_a_partition

3. 一筆寫入的旅程

以分區中「client1 在 A 寫 x=2」為例，也就是 demo.py 裡的 write_and_show(cluster, "A", "2", "分區")。從呼叫到印出結果，經過這些程式碼：

  1. 示範程式發出寫入
    demo.py 的 write_and_show()

    呼叫 write()，拿回新的叢集和結果，再把結果印出來。被拒絕時 write() 回傳的是原本那個叢集，所以照樣接回來用就好。

    def write_and_show(cluster: Cluster, node: str, value: str, stage: str) -> Cluster:
    cluster, result = write(cluster, node, "x", value)
    show_write(f"[{stage}] {node} 寫 x={value}", result)
    return cluster
  2. 找出 A 連得到哪些節點
    cap.py 的 write() → _reachable()

    在 cluster.groups 裡找出 A 所在的分組，這裡是 frozenset({"A", "B"})。節點名稱不存在時直接丟 ValueError。

    def _reachable(cluster: Cluster, node: str) -> frozenset[str]:
    group = next((group for group in cluster.groups if node in group), None)
    if group is None:
        raise ValueError(f"不存在的節點：{node}")
    return group
  3. CP 檢查有沒有過半，AP 直接放行
    cap.py 的 _reject_without_quorum()、quorum()

    CP 模式下，{A, B} 有 2 台，quorum() 是 2，過半，放行。如果是 C 寫入，{C} 只有 1 台，這裡就回傳拒絕的 Result，write() 原封不動回傳舊叢集。CP 和 AP 的差別只有這一個判斷。

    def _reject_without_quorum(cluster: Cluster, peers: frozenset[str]) -> Result | None:
    if cluster.mode is Mode.AP or len(peers) >= quorum(cluster):
        return None
    return Result(
        ok=False, reason=f"只連得到 {len(peers)} 台，需要 {quorum(cluster)} 台才過半"
    )
  4. 產生新版本，複製給同組節點
    cap.py 的 write() 後半

    時鐘加 1，建立 Version(value="2", timestamp=2, origin="A")。同組的 A、B 各拿到一個「多了這筆」的新 dict；C 在另一組，沿用原本的 dict，所以 C 還是 x=1。最後用 replace() 產生新的 Cluster，舊的不受影響。

        clock = cluster.clock + 1
    version = Version(value=value, timestamp=clock, origin=node)
    stores = {
        name: {**store, key: version} if name in peers else store
        for name, store in cluster.stores.items()
    }
    return replace(cluster, stores=stores, clock=clock), Result(ok=True)
  5. 印出結果
    demo.py 的 show_write()

    印出 [分區] A 寫 x=2 → 成功。被拒絕時印出 拒絕：加上 reason。

  6. 網路恢復時合併
    cap.py 的 heal()

    把每個 key 在各節點上的不同版本收集起來，時間戳最大的勝出，寫回每一台。輸掉的版本如果是分區期間寫入的（時間戳大於 partitioned_at），就放進 lost 回傳。

    看 heal() 的程式碼 
    def heal(cluster: Cluster) -> tuple[Cluster, tuple[Version, ...]]:
    keys = sorted({key for store in cluster.stores.values() for key in store})
    candidates = {
        key: {store[key] for store in cluster.stores.values() if key in store}
        for key in keys
    }
    merged = {key: max(versions, key=_by_time) for key, versions in candidates.items()}

    # 分區前就存在的舊版本輸掉只是「落後」，分區期間寫入的版本輸掉才是「遺失」。
    since = cluster.clock if cluster.partitioned_at is None else cluster.partitioned_at
    lost = tuple(
        version
        for key, versions in candidates.items()
        for version in sorted(versions, key=_by_time)
        if version != merged[key] and version.timestamp > since
    )
    healed = replace(
        cluster,
        stores={node: dict(merged) for node in cluster.nodes},
        groups=(frozenset(cluster.nodes),),
        partitioned_at=None,
    )
    return healed, lost

每種結果在哪一步決定

狀況在哪裡決定結果
節點名稱不存在第 2 步 _reachable()ValueError
CP，連得到的節點沒過半第 3 步 _reject_without_quorum()Result(ok=False)，叢集不變
AP，分區中第 3 步直接放行成功，但另一組看不到這筆寫入
分組沒有剛好涵蓋每個節點一次（漏掉、重複、不存在）partition()ValueError
分區期間的寫入在恢復時輸給較新的版本第 6 步 heal()出現在回傳的 lost 裡

模擬刻意簡化了兩件事：同組內的複製是瞬間完成的，以及時間戳來自一個全域邏輯時鐘。真實的 AP 系統常用各台機器自己的時間做 last-write-wins，時間不準時，「誰被丟掉」會更難預測。

4. 啟動時發生什麼

demo.py

if __name__ == "__main__": 依序呼叫 run_three_nodes(Mode.CP)、run_three_nodes(Mode.AP)、run_two_nodes()。每個情境都從 new_cluster() 重新開始，互不影響。沒有設定檔，也不讀環境變數。

new_cluster()

cap.py：每個節點一個空的 store，只有一個分組（全部連通），clock=0、partitioned_at=None。節點預設是 A、B、C，2 台的情境傳 nodes=("A", "B")。

test_cap.py

pytest 收集 12 個測試函式，其中分組驗證用 @pytest.mark.parametrize 拆成 3 個案例，共 14 個。共用情境由 partitioned()、written_on_both_sides() 組出來。

def new_cluster(mode: Mode, nodes: tuple[str, ...] = ("A", "B", "C")) -> Cluster:
    return Cluster(
        mode=mode,
        nodes=nodes,
        stores={node: {} for node in nodes},
        groups=(frozenset(nodes),),
    )

5. 關鍵設計

叢集不可變：每一步都是一張快照

Cluster、Version、Result 都是 @dataclass(frozen=True)。每個操作都用 replace() 回傳新的叢集，所以示範程式每一步都要接回新叢集；寫入被拒絕時拿回的就是原本那個。測試也因此可以同時拿「寫入前」和「寫入後」的叢集比較。

@dataclass(frozen=True)
class Cluster:
    mode: Mode
    nodes: tuple[str, ...]
    stores: Mapping[str, Mapping[str, Version]]  # 節點 -> (key -> 版本)
    groups: tuple[frozenset[str], ...]  # 目前連得到彼此的節點分組
    clock: int = 0
    partitioned_at: int | None = None  # 分區發生時的時鐘；沒有分區時為 None

「落後」和「遺失」靠 partitioned_at 分開

恢復時輸掉的版本有兩種：分區前就存在、只是沒收到新資料的（CP 的 C 上的 x=1），以及分區期間被確認過、卻被蓋掉的（AP 的 A 上的 x=2）。partition() 記下當時的時鐘，heal() 只把時間戳比它大的輸家算成遺失。

過半的算法，決定了 2 台不夠

quorum() 是 len(nodes) // 2 + 1：3 台要 2 台，2 台也要 2 台。所以 3 台切成 2 和 1 時多數派還能服務，2 台切成 1 和 1 時兩邊都不行。這就是雙機備援要加 witness 的原因。

def quorum(cluster: Cluster) -> int:
    return len(cluster.nodes) // 2 + 1

其他

設計做法在哪裡
讀本地就等於讀到這一組的最新值寫入會同步複製給同組每一台，所以同組節點的資料永遠一致，不用再問其他節點read()
CP 連讀取也拒絕少數派手上的可能是舊資料，回舊資料就破壞一致性，所以讀寫都要過半read() 也呼叫 _reject_without_quorum()
輸入驗證分組要剛好涵蓋每個節點一次、節點名稱要存在，否則丟 ValueErrorpartition()、_reachable()
沒有外部套件範例只用標準函式庫，複製下來就能跑；pytest 只放在 dev 群組pyproject.toml
三種語言結果一致.NET、Rust 版本照同一個模型實作，demo 的輸出用 diff 比對逐字相同PoC 的 README「怎麼跑」
