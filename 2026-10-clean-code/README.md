# Clean Code 重構範例

- 狀態：已完成
- 開始日期：2026-10-31
- 結論：有條件可行：先用 characterization test 守住行為，再重構，可以證明沒改壞，複雜度也降到門檻以下；但總行數變多，而且只證明得了測過的輸入

## 背景與目標

Clean Code 的規則（有意義的命名、函式短小、參數少、不要魔術數字、不要重複……）大家都同意。真正卡住的是面對一段沒有測試的舊程式時，兩個疑慮：「重構會不會改壞？」和「改完到底好在哪？說得出數字嗎？」

這個 PoC 拿一段典型的髒程式（電商運費計算），驗證這兩件事都能回答：用 characterization test 證明行為沒變，用工具量出可讀性的改善。結果可以拿來決定：舊模組要不要重構、重構前要先準備什麼、CI 要不要加複雜度門檻。

## 要驗證的假設

把一段典型的髒程式照 Clean Code 原則重構，可以在行為不變（characterization test 窮舉 728 組輸入，結果全部相同）的前提下，讓每個函式的循環複雜度和認知複雜度都 ≤ 5、長度 ≤ 15 行、參數 ≤ 2 個。

## 待釐清問題

- [x] 舊程式用 `-1` 當錯誤碼，重構版改成丟例外，這樣還算「行為不變」嗎？→ 不算純重構，是唯一刻意的行為改變。比對時把兩者都視為「無效輸入」，並在 README 和說明頁明列
- [x] 怎麼確定比對本身沒寫錯（永遠回「全部相同」）？→ 比對可以傳入要比較的版本，測試傳入「離島冷藏多收 1 元」的版本，斷言剛好抓到 132 組不一致
- [x] 三種語言量出來的指標能直接比較嗎？→ 循環複雜度和認知複雜度可以（三種語言幾乎一樣）；行數不行，受大括號和格式化工具影響很大
- [ ] 換成真實專案的舊模組，輸入空間沒辦法窮舉時，取樣要多少才夠？

## 成功標準

用 [lizard](https://github.com/terryyin/lizard) 1.24（`-Ecognitive`）量每個函式。實測值依序是 Python／.NET／Rust。

| 指標 | 目標值 | 實測值 |
|------|--------|--------|
| 窮舉 728 組輸入，新舊版結果不同的組數 | 0 | 0／0／0 |
| 比對抓得到 1 元的差異（離島冷藏多收 1 元） | 132 組全部抓到 | 132／132／132 |
| 最大循環複雜度（CCN，舊版 15） | ≤ 5 | 3／3／3 |
| 最大認知複雜度（CogC，舊版 45） | ≤ 5 | 2／2／2 |
| 最長函式（NLOC，舊版 37／82／49） | ≤ 15 | 9／13／10 |
| 最多參數（舊版 5） | ≤ 2 | 2／2／2（對外的進入點都只有 1 個） |
| 比較式裡的魔術數字（ruff PLR2004，只有 Python 有這個檢查） | 0（舊版 8） | 0 |
| 三種語言的示範輸出 | 逐字相同 | 相同（`diff` 比對） |

## 技術選型

| 項目 | 選擇 | 理由 |
|------|------|------|
| 語言 | Python、.NET、Rust 各寫一份 | 同一套規則三種語言實作，輸出逐字相同；順便看指標在不同語言能不能比 |
| 題材 | 運費計算：重量級距、離島加價、免運門檻、冷藏費 | 電商常見，規則互相交錯，很容易寫出巢狀 if；金額用整數，三種語言結果一致 |
| 證明行為不變 | characterization test（golden master），窮舉 13 種重量 × 2 種地區 × 2 種會員 × 7 種金額 × 2 種溫層 ＝ 728 組 | 舊程式沒有規格，拿舊程式本身當標準答案；每個門檻都取「剛好、少 1、多 1」 |
| 量化可讀性 | lizard 1.24 的 NLOC、CCN、PARAM、CogC | 一個工具支援三種語言，數字可以並排；認知複雜度會把巢狀深度算進去 |
| 魔術數字 | ruff 0.17 的 PLR2004（只有 Python） | 另外兩種語言沒有現成對應的檢查 |
| 外部套件 | 範例本身都不用（只有測試和量測工具需要） | 不用裝東西就能跑 |
| 測試 | Python：pytest + pytest-cov；.NET：xUnit + coverlet；Rust：`cargo test` | 跟其他 PoC 一致 |

## 做法

每種語言都有三個部分：

- **舊版**：一個 `calc(w, r, m, a, c)`，故意保留常見的壞味道：縮寫命名、5 個位置參數、5 層巢狀、魔術數字、重量級距抄了 3 次、用 `-1` 當錯誤碼、註解只重複程式在做什麼
- **重構版**：參數物件 `Parcel`、`Region` 和 `Membership` 兩個 enum、具名常數、一個對外的運費函式，加上 7 個都不超過 15 行的私有函式，錯誤改成例外（Rust 是 `Result`）
- **裁判**：窮舉 728 組輸入，比對兩版結果。舊版的 `-1` 和重構版的錯誤都視為「無效輸入」

運費規則：1000 公克以內 60 元、5000 公克以內 100 元，超過的部分每 1000 公克（不足也算）加 20 元；離島加 80 元；本島訂單滿門檻免運（一般會員 1000 元、金卡會員 500 元），離島不免運；冷藏另收本島 50 元、離島 100 元，免運也照收。

每個實作資料夾的運作說明頁（有可以切換訂單的互動流程圖，左邊是舊版的決策樹、右邊是重構版的函式管線，並追到各檔案和函式）：

- [.NET 版](./dotnet/how-it-works.html)
- [Rust 版](./rust/how-it-works.html)

### 怎麼跑

需要：Python 3.12 以上加 uv、.NET 10 SDK、Rust 1.85 以上。`metrics` 會用 `uvx` 自動下載 lizard（和 Python 版的 ruff）。

```bash
python/run.sh demo      # 5 筆訂單的新舊對照，加上 728 組的比對結果（dotnet/、rust/ 用法相同）
python/run.sh test      # 跑單元測試和比對測試
python/run.sh metrics   # 量每個函式的行數、複雜度、參數數量

# 確認三種語言的輸出完全相同
diff <(python/run.sh demo) <(dotnet/run.sh demo) && diff <(python/run.sh demo) <(rust/run.sh demo)
```

| 內容 | Python | .NET | Rust |
|------|--------|------|------|
| 舊版 | `python/legacy.py` | `dotnet/src/CleanCode/Legacy.cs` | `rust/src/legacy.rs` |
| 重構版 | `python/shipping.py` | `dotnet/src/CleanCode/Shipping.cs` 等 | `rust/src/shipping.rs` |
| 窮舉比對 | `python/characterization.py` | `dotnet/src/CleanCode/Characterization.cs` | `rust/src/characterization.rs` |

| 測試 | `python/test_*.py` | `dotnet/tests/CleanCode.Tests/` | `rust/tests/*.rs` |

## 實驗紀錄

### 2026-10-31：三種語言重構並比對

5 筆示範訂單，兩版結果相同：

| 訂單 | 舊版 | 重構版 |
|------|------|--------|
| 本島、一般會員、800 元、2500 公克、常溫 | 100 | 100 |
| 本島、一般會員、1000 元、800 公克、常溫 | 0 | 0 |
| 本島、金卡會員、600 元、2500 公克、冷藏 | 50 | 50 |
| 離島、金卡會員、3000 元、7200 公克、冷藏 | 340 | 340 |
| 本島、一般會員、800 元、0 公克、常溫 | -1 | 錯誤：重量必須大於 0 公克，收到 0 |

728 組窮舉：有效輸入 528 組運費相同，無效輸入 200 組（舊版回 -1、重構版回報錯誤），不同 0 組。

lizard 量到的數字（重構版取最大的那個函式）：

| 指標 | Python 舊版 → 重構版 | .NET 舊版 → 重構版 | Rust 舊版 → 重構版 |
|------|------|------|------|
| 函式數 | 1 → 8 | 1 → 8 | 1 → 9（`Display` 的 `fmt` 也被算成一個） |
| 最長函式 NLOC | 37 → 9 | 82 → 13 | 49 → 10 |
| 最大 CCN | 15 → 3 | 15 → 3 | 15 → 3 |
| 最大 CogC | 45 → 2 | 45 → 2 | 45 → 2 |
| 最多參數 | 5 → 2 | 5 → 2 | 5 → 2 |

| 語言 | 測試 | 覆蓋率 | 格式與靜態檢查 |
|------|------|--------|----------------|
| Python | 24 個全部通過 | 重構版和比對 100% | ruff 通過 |
| .NET | 24 個全部通過 | 扣掉示範程式 98.9%；重構版、比對、舊版都是 100% | `dotnet format` 通過，警告視為錯誤 |
| Rust | 13 個全部通過 | 沒量（本機沒有 cargo-llvm-cov） | `cargo fmt`、`clippy -D warnings` 通過 |

發現：

- **只有一個刻意的行為改變：錯誤碼變成例外。** 這不是純重構，呼叫端的寫法要跟著改。比對時把舊版的 `-1` 和重構版的錯誤都換成「無效輸入」再比，並在說明頁明列。
- **窮舉只證明得了測過的輸入。** 舊版把任何不是 `"main"` 的字串都當離島、不是 `"gold"` 的都當一般會員，拼錯字也照算。重構版用 enum，拼錯字在建立 `Parcel` 前就報錯。這個差異不在 728 組網格裡（網格只放合法字串），比對證明不到，而且是重構版比較對。
- **裁判也要被測。** 如果比對本身寫錯、永遠回「全部相同」，728 組相同就沒有意義。所以加了一個「離島冷藏多收 1 元」的版本當對照，三種語言都剛好抓到 132 組。示範程式一開始也有一個計數問題：用「總數減無效數」當「運費相同的組數」，有不一致時會算錯，已改成再扣掉不一致的組數。
- **跨語言比較用複雜度，不要用行數。** 舊版 `calc` 的 CCN（15）和 CogC（45）三種語言完全一樣，但 NLOC 從 37（Python）到 82（C#，大括號各佔一行）差了一倍多。lizard 也有工具本身的問題：巢狀深度擴充（`-ENS`）在 Python 會把前面函式的深度累加到後面；C# 的三元運算子有時不算進 CogC。
- **代價是總行數變多。** Python 從 37 行變成 57 行，多出來的是具名常數、兩個 enum、`Parcel` 和錯誤型別。換來的是每一段都讀得懂，不是程式變短。

## 結論

- 結果：有條件可行
- 條件或限制：要先有能當標準答案的舊程式，以及能窮舉或大量取樣的輸入空間；刻意的行為改變（例如錯誤碼變例外）要明列，並在比對時對應；窮舉證明不到網格外的輸入；跨語言或跨專案比較可讀性，用 CCN 和 CogC，不要用行數
- 如果要正式導入，下一步是：在 CI 加上 `lizard -Ecognitive -C 5` 之類的複雜度門檻；挑一個真實專案的舊模組，先寫 characterization test 再重構，並研究輸入空間無法窮舉時的取樣方式
