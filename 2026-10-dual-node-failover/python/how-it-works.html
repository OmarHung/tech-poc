雙機備援機制｜Python 版運作說明

這頁說明 python/ 裡的程式怎麼運作。裡面有三種雙機備援架構：A. 主備＋資料同步（兩台資料節點怎麼決定誰是主機、一筆寫入怎麼複寫到另一台）、B. 熱熱備援（兩台不通訊、都處理每一筆）、C. 上游指派（兩台不通訊、上游把工作派給其中一台）。框架是 FastAPI 0.162 跑在 uvicorn 0.54（uvloop、httptools）上，程序之間的呼叫和 gateway 轉發都用 httpx 0.28，Python 3.12，套件由 uv 管理。規則、時間和 HTTP 介面跟 .NET 版一模一樣，用同一支 verify/ 驗證。

1. 全貌 2. 互動流程圖 3. 一筆資料怎麼流動 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三種架構、六種程式

每個程序都是單一的 uvicorn 程序、單一個 asyncio event loop，背景迴圈（選主、複寫、gateway 輪詢、租約回收、worker 的工作迴圈）都是同一個 loop 上的 task。

架構 A：主備＋資料同步

兩台資料節點跑的是同一個套件（node），誰當主機是執行時決定的。第三個程序 witness 不存資料，只負責仲裁。client 只認得 gateway。

Gateway

127.0.0.1:8100 ・ src/gateway/

client 的唯一入口。每 100 ms 問兩台節點的 /health，把請求轉給回報 role = primary 的那台（兩台都說是主機時選 epoch 較新的）。

Node a / Node b

127.0.0.1:8101、8102 ・ src/node/

資料節點。主機接受讀寫，並把每筆寫入同步複寫給備機；備機只接收複寫，同時注意主機是不是還活著。資料存在只能附加的 log 檔。

Witness

127.0.0.1:8103 ・ src/witness/

第三票。一次只把租約（lease）發給一台，每換一次主機 epoch 就加 1；另外記住「備機是不是同步中」，不同步就不准它升格。只存四個欄位。

架構 B、C：兩台不通訊

兩台 worker 跑同一個套件（worker），用 MODE 決定是熱熱備援還是被指派。兩台之間沒有任何連線，只認得上游和下游。

Upstream

127.0.0.1:8120 ・ src/upstream/

工作的來源。架構 B 用它的事件流水帳：只能附加、可以從任何位置重讀。架構 C 用它的任務佇列：每件任務租給一台 worker，租約到期就改派。

Worker a / Worker b

127.0.0.1:8121、8122 ・ src/worker/

MODE=hothot：讀全部事件、算帳戶餘額、送結果、存檢查點。MODE=dispatch：租任務、定時心跳、做事、寫結果、回報完成。

Sink

127.0.0.1:8123 ・ src/sink/

下游。以事件或任務編號去重：第一份結果套用（副作用發生），其他的只計數，分成重複、衝突（內容不同）、過期（attempt 比較舊）。

2. 互動流程圖：正常、故障與恢復

架構 A：主備＋資料同步

點按鈕切換情境。藍色虛線是正在發生的流量，紅色是失敗的連線，半透明是這個情境沒用到的部分；外框加粗、底色是主機。下方的數字來自 verify/ 對 Python 版的實測（verify/results/python-*.json）。

正常運作：a 是主機

選主
a 每 0.5 秒向 witness 續約一次（ElectionWorker._renew()），租約 3 秒。b 一直收到 a 的複寫和心跳，所以不會去搶。
寫入
client → gateway → a。a 寫進自己的 log，再送給 b；b 回覆收到後，a 才回 200 給 client。
witness 記錄
租約在 a，epoch 1，備機同步中（b 可以接手）。
實測
本機寫入 p50 3.48 ms、p99 7.10 ms；兩台之間加 10 ms 單程延遲時 p50 46.4 ms（跟 .NET 的比較見第 5 節「延遲」）。

主機崩潰（kill -9）：b 接手

偵測
b 超過 3 秒沒聽到 a（NodeState.try_begin_candidacy()），向 witness 要租約。a 最後一次續約的租約這時也到期了，b 又是同步中，witness 就把租約交給 b，epoch 變 2。
切換
b 升格，複寫迴圈一開始就請 witness 記下「a 不同步」（PrimaryTerm.request_solo()），之後就能單獨確認寫入（Solo）。gateway 下一次輪詢就改送 b。
資料
a 確認過的每一筆，b 都已經收到過（同步複寫的規則），所以沒有遺失。
實測
RTO 3.11 秒（租約 3 秒＋續約間隔＋gateway 輪詢），3,285 筆確認的寫入遺失 0 筆。租約改 1 秒時 RTO 1.18 秒。

舊主機加回來：a 變成備機

重新加入
a 重啟後一律以備機身分啟動，馬上收到 b 的複寫。請求裡的 epoch 2 比 a 記得的 1 新，a 就接受 b 是主機（NodeState.handle_replicate()）。
對齊資料
b 用 (index, epoch) 跟 a 的 log 比對。a 崩潰前寫進本機、但還沒送到 b 的幾筆（從沒回過 200）會被丟掉，再補上 b 的新資料（ReplicatedLog.append_from()）。
恢復可接手
a 追上後，b 用最新的版本號告訴 witness「備機同步中」（PrimaryTerm.try_mark_in_sync()），a 就又能接手了。
實測
從啟動到追上 0.37 秒（含程式啟動），丟掉 1 筆從沒確認過的寫入。接著再砍 b，a 3.41 秒接手，兩次切換共 5,363 筆寫入遺失 0 筆。

網路分區：a 跟 b、witness 都斷了，但 client 還連得到 a

a 那邊
寫入送不到 b，等 1 秒後想請 witness 允許單獨確認，但 witness 也連不到，只能回 503。2.7 秒後 a 的租約到期，連讀取都停止。
b 那邊
3 秒沒聽到 a，向 witness 要到租約（epoch 2），開始服務。
網路恢復
a 看到 epoch 2，轉成備機，丟掉 8 筆從沒確認過的寫入，0.19 秒內兩邊資料一致。
實測
舊主機在斷線後確認了 0 筆，同時有兩台主機確認寫入 0 次，遺失 0 筆，b 3.05 秒接手。

同樣的分區，但沒有 witness（ARBITER=none，對照組）

a 那邊
只覺得「備機連不到」，沒有人可以問（NoArbiter 一律同意），就自己繼續確認寫入。
b 那邊
3 秒＋1.5 秒的優先權延遲沒聽到 a，就自己升格成 epoch 2（ElectionWorker.tick_without_witness()，實測 4.65 秒）。現在兩台都是主機。
網路恢復
a 看到 epoch 2 而下台，它在分區期間確認的寫入跟 b 的 log 對不上，整批被丟掉，client 不會收到任何通知。
實測
兩台同時確認寫入 1,417 筆，恢復後 3,231 筆已確認的寫入消失。這就是需要 witness 的原因。

witness 掛掉 6 秒

為什麼沒事
a 有兩種租約：witness 給的，和 b 給的「承諾」（b 每次接受複寫，就承諾 3 秒內不搶主）。只要其中一個有效，a 就能繼續服務，等於 3 票中拿到 2 票。
寫入
照常同步複寫到 b，不需要 witness 參與。
witness 回來
從 witness.json 讀回狀態（租約在 a），a 下一次續約就恢復。
實測
4,384 筆寫入 0 失敗，最長空窗 0.02 秒，a 從沒下台。

備機落後時主機又掛：寧可停機也不丟資料

第一步
b 先掛。a 的寫入等 b 等了 1 秒（實測 1014 ms），請 witness 記下「b 不同步」後單獨確認（Solo），共 1,253 筆只有 a 有。
第二步
a 也掛了，接著 b 先回來。b 向 witness 要租約，witness 拒絕：「b 可能缺少已確認的寫入，等 a 回來」。gateway 找不到主機，回 503。
a 回來
witness 把租約還給 a（同一個 epoch），a 繼續服務，b 再從 a 追上。
實測
停機 11.46 秒（等 a 回來），遺失 0 筆。代價是可用性：要強制讓 b 接手只能人工介入並接受遺失。

架構 B、C：兩台不通訊

同一張圖，上游是事件流水帳（B）或任務佇列（C）。兩台 worker 之間沒有線。數字來自 verify/independent.py 對 Python 版的實測。

架構 B 正常運作：兩台都做每一筆

上游
事件流水帳，只能附加，可以從任何位置重讀（EventLog.read()）。
worker
各自從自己的位置往後讀，依序更新帳戶餘額，每筆送一個結果（event-<編號> → 帳戶:餘額）。一批送完才存檢查點（HotHotWorker.run()）。
下游
同一個事件收到兩份，第一份套用、第二份記成重複（ResultStore.record()）。
實測
1,574 筆事件下游收到 2,735 份：沒有去重的話，副作用會多發生 1,161 次。

架構 B：a 被砍

發生什麼
什麼都不用做。b 本來就在處理每一筆，沒有偵測、沒有切換。
實測
下游最長 13 ms 沒有新結果，跟平常一樣；1,574 筆全部有結果、全部正確，兩台 0 次不一致。

架構 B：a 重啟，從檢查點補讀

補讀
a 讀回 checkpoint.json（讀到哪、各帳戶餘額），從那裡往後讀，停機期間的事件一筆不漏。
重送
被砍時已經送出、但還沒存進檢查點的那批會再送一次，下游當成重複忽略。
實測
停機 3 秒間的約 600 筆，從下重啟指令算起 0.54 秒補完（含程式啟動）；之後再砍 b，a 獨自繼續，最後的餘額跟正確答案完全一樣。網路斷 3 秒的情況，恢復後 0.60 秒補完（.NET 0.11 秒：每筆結果都是一次 HTTP 呼叫，Python 每次多花一點）。

架構 B 的錯誤做法：重啟時直接從最新的事件開始（START_FROM=latest）

發生什麼
a 的餘額少了停機期間的事件，之後每一筆受影響帳戶的結果都跟 b 不同。下游先收到誰的就用誰的。
實測
不一致 422 筆；b 掛掉之後，下游套用了 625 筆錯誤結果。另一種錯是結果帶本機時鐘（DETERMINISTIC=false）：555 筆只有 22 筆（4%）不一致，偶發，最難發現。

架構 C 正常運作：上游把每件任務租給一台

租任務
worker 向上游要任務（TaskQueue.lease()），拿到 {id, input, attempt, ttlMs}，租約 2 秒。
做事
每 1/3 個租約送一次心跳延長租約，做完先寫結果到下游，再向上游回報完成（DispatchWorker.run_task()）。
實測
每秒 5 件、每件 300 ms，兩台輪流接，任務延遲 p50 約 0.9 秒。每件做 3 秒（比租約長）時靠心跳延長，0 次被誤判改派。

架構 C：a 做到一半被砍

發生什麼
a 不再心跳，租約到期後上游把那件任務放回佇列最前面（TaskQueue.expire_overdue()），attempt 變 2，b 接手。其他任務不受影響。
實測
那件任務 2.34 秒後完成（租約 2 秒＋做事 0.3 秒），50 件全部正確。

架構 C：a 被凍結 4 秒（長時間 GC、VM 暫停）

發生什麼
任務改派給 b。a 恢復後還以為任務是自己的，但寫結果前先檢查自己的租約（LeaseTracker.is_valid）：從送出請求的時間起算、提早 10% 結束，早就過期了，於是放棄。
實測
有檢查時 0 次重複寫入，a 記了 1 次放棄。不檢查的對照組（LEASE_CHECK=off）多寫 1 次；這次剛好 b 的結果先到，下游才認得出那是過期的 attempt，上游也收到 1 次過期的完成回報。
還剩的空窗
寫結果的逾時不超過剩下的租約，但如果剛好在「檢查完、請求已經送出」之後才被凍結，還是會晚到。所以下游的去重不能省。

架構 C：a 連不到下游，但心跳照常送到上游

問題
心跳一直成功，租約一直被延長，上游以為 a 好好的，另一台永遠接不到這件任務。心跳只證明 worker 活著，不證明它做得完。
解法
a 寫不出結果超過一個租約就放手（DispatchWorker._deliver()），心跳跟著停，租約到期後改派給 b。放手後先不接新工作，直到下游恢復：每 0.1 秒問一次下游的 /health（DispatchWorker._sink_back()），否則 a 會接下一件、又卡住它，甚至把剛放掉的那件又拿回來。
實測
那件任務 4.55 秒後由 b 完成：a 先試 2 秒，租約再 2 秒到期。只改派 1 次，a 只放棄這 1 件，下游恢復後才又開始接任務。沒有這個斷路器時，a 放手後馬上接了下一件，也卡了 2 秒才放掉。放手時如果主動通知上游，還能再快約 2 秒。

架構 C：a 做完、寫了結果，但回報不出去

發生什麼
a 到上游的連線斷了。上游收不到心跳和完成回報，租約到期後改派給 b，b 再做一次。
為什麼避免不了
先寫結果、再回報完成，兩步之間任何中斷都會這樣：這就是 at-least-once。所以下游一定要以任務編號去重。
實測
那件任務下游收到兩份，只套用一份；a 恢復後的完成回報被上游記成過期。

3. 一筆資料怎麼流動

架構 A：一筆寫入怎麼複寫到另一台

以正常運作時的 PUT /kv/order-1 {"value":"paid"} 為例（a 是主機、同步複寫），從進門到回 200 經過這些程式碼：

  1. Gateway 轉給目前的主機
    src/gateway/main.py 的 forward()、src/gateway/tracker.py 的 PrimaryTracker.current

    PrimaryTracker.run() 在背景每 100 ms 輪詢兩台的 /health，choose() 挑出回報 primary 且 epoch 最大的；回應不是 JSON 或型別不對，只把那台當成「不知道」，輪詢照常。forward() 用 httpx 把 method、原始路徑（保留百分比編碼）、query 和 body 送過去，回傳節點的狀態碼、body 和 X-Served-By；節點回 503 或連不上時立刻再輪詢一次（nudge()）。

  2. 主機檢查自己的租約，寫進本機 log

    .NET 版在這裡用一把鎖。Python 版整個節點只有一個 event loop，兩個 await 之間的程式碼不會被別的請求插隊，所以「我是主機而且租約還有效」和「附加到 log」寫成一段沒有 await 的同步函式，效果等同同一把鎖。下台（_step_down()）也是同步的，不可能夾在中間。

    def append_as_primary(self, key: str, value: str) -> tuple[LogEntry, PrimaryTerm]:
    """Checks the lease and appends in one atomic step, so a node can never append after it stopped serving."""
    term = self.serving_term()
    if term is None:
        raise not_primary()
    entry = self.log.append(term.epoch, key, value)
    term.notify_appended()
    return entry, term

    ReplicatedLog.append()（storage/replicated_log.py）給它下一個 index 和目前的 epoch，由 LogFile.append() 寫成一行 JSON，用不經過 Python 緩衝的 os.write 交給作業系統，程序被砍掉也不會不見。寫入失敗（例如磁碟滿了）時把檔案截回上一行結尾，不會留下半行讓下一筆黏在後面。這是在 event loop 上直接做的阻塞 I/O，但一行只有幾十 byte，耗時是微秒等級，不會拖到心跳。

  3. 複寫迴圈被叫醒，送出這一批
    src/node/cluster/replication.py 的 ReplicationWorker.replicate_term()

    notify_appended() 觸發一個 asyncio.Event，叫醒等待中的複寫迴圈（每次觸發後就換一個新的 Event，等待的一方先拿 Event 再讀 log，所以不會漏掉中間的寫入）。迴圈從 next_index 讀最多 256 筆，連同前一筆的 (index, epoch) 送到 b 的 POST /internal/replicate。一次只送一批，回來才送下一批；沒有新資料時每 0.5 秒送一次空的當心跳。

  4. 備機檢查 epoch 和前一筆，寫進自己的 log
    b 的 NodeState.handle_replicate() → ReplicatedLog.append_from()

    epoch 比自己知道的舊 → 拒絕（被換掉的舊主機就是這樣被擋下的）。前一筆對不上 → 回 mismatch，主機往回找。對得上 → 附加，並記下「剛聽到主機」：這等於承諾 3 秒內不搶主，回覆裡的 promiseMs 就是這個承諾。這整段同樣沒有 await。

  5. 主機收到回覆：延長租約、推進進度
    ReplicationWorker.replicate_term() 後半 → PrimaryTerm.record_replicated()

# ……

    租約從「送出請求的時間」（time.monotonic()）起算，再提早 10% 結束，所以主機一定比備機先放手。

  6. 等待中的寫入確認已經安全，回 200
    KvService.put() 等在 PrimaryTerm.wait_durable()

    這筆的 index 小於等於 b 已確認的 match_index，就可以回覆。如果 b 超過 1 秒都沒確認，改請 witness 同意「單獨確認」（try_go_solo()）；所有卡住的寫入共用同一個請求，各自用 asyncio.shield() 等它，一個 client 斷線不會把大家共用的請求取消掉。witness 同意後 b 就不能升格，這時只存在 a 的寫入也算安全了。

    看 wait_durable() 的程式碼 
    async def wait_durable(self, index: int, timeout: float, clock: Clock) -> None:
    deadline = clock.now() + timeout
    while True:
        if index <= self._match_index or self._peer_state is PeerState.SOLO:
            return
        if self._ended:
            raise Unavailable("lost the primary role before the write reached the standby")
        progress = self._progress.current
        remaining = deadline - clock.now()
        if remaining <= 0:
            if not await self.try_go_solo():
                raise Unavailable("standby unreachable and the witness did not allow going on alone")
            continue
        try:
            async with asyncio.timeout(remaining):
                await progress.wait()
        except TimeoutError:
            pass  # deadline reached; the loop asks the witness

架構 B：一筆事件怎麼被兩台各自處理

  1. verify 把事件加進上游的流水帳
    POST /events → src/upstream/main.py 的 append_event() → src/upstream/event_log.py 的 EventLog.append()

    read_body(request, NewEvent.from_wire) 用嚴格 JSON 讀出 {account, amount}（"amount": "2"、2.0、true 都是 400）。append() 是同步函式：檢查帳戶和金額、給下一個編號、附加，最後觸發目前的 asyncio.Event 並換一個新的，叫醒所有正在等新事件的讀取。流水帳只能附加，不會刪。

  2. 兩台 worker 各自讀到它
    src/worker/hothot.py 的 HotHotWorker.run() → src/worker/client.py 的 WorkClient.read_events() → 上游的 EventLog.read()

    每台用自己的位置讀（GET /events?after=…&limit=100&waitMs=500），沒有新事件時上游會等一下再回。read() 先看有沒有新事件、沒有就拿起目前的 Event 再 await，兩步之間沒有 await，所以不會漏掉剛好插進來的附加。兩台不知道彼此存在。

  3. 更新餘額、送出結果，整批送完才存檢查點
    Ledger.apply()（src/worker/ledger.py）、HotHotWorker._deliver()、_save()

    key = f"event-{logged.seq}"

    Ledger 是 frozen dataclass，apply() 回傳新的 ledger，只依事件和順序計算，兩台看到同樣的事件就算出同樣的餘額。送結果會一直重試到下游回應為止。_save() 用 state_file.save() 寫暫存檔再 os.replace()，被砍時只會留下舊的或新的檢查點。上游的 last 比自己的位置還小（上游重啟、編號從頭開始）時記 ERROR、不處理，等 0.5 秒再看。

  4. 下游去重
    POST /results → src/sink/result_store.py 的 ResultStore.record()

    第一份套用（201），內容一樣的第二份是重複（200），內容不同的是衝突（409，保留第一份並計數），attempt 比看過的舊是過期（409）。record() 也是同步函式，同一個 key 的兩份不可能同時被當成「第一份」。

架構 C：一件任務怎麼被指派

  1. worker 租到任務
    src/worker/dispatch.py 的 DispatchWorker.run() → WorkClient.lease_task() → src/upstream/main.py 的 lease_task() → src/upstream/task_queue.py 的 TaskQueue.lease()

    先把到期的租約放回佇列最前面，再把最前面的任務交給這台 worker：attempt 加 1，租約從現在起 2 秒。佇列空的話最多等 0.5 秒（waitMs，上限 10 秒）。路由用 until_disconnected() 包住這個等待：worker 先掛斷（被砍、自己逾時放棄），等待就被取消，任務不會被租給一個已經不在聽的 worker。worker 自己記下送出請求的時間，算出自己的租約終點。

  2. 邊做邊心跳，寫結果前先檢查租約
    DispatchWorker.run_task()、_heartbeat()、_still_holds()；src/worker/lease_tracker.py

    if not self._still_holds(lease, tracker, "before writing the result"):
        return
    status.task_phase(lease.id, "delivering")

    status.task_phase(lease.id, "completing")
    completed = await self._complete(lease, tracker)
    status.task_finished("completed" if completed else "stale")

    worker 自己算租約（lease_end()）：從送出請求的時間起算，90% 的 TTL 就結束，所以一定比上游先放手。心跳是同一個 event loop 上的另一個 task，用 PeriodicTimer 固定每 1/3 個 TTL 送一次，每次最多等一個間隔，成功就從那次的送出時間延長；上游回 409 或 404 就立刻作廢。寫結果的逾時不超過剩下的租約，寫不出來超過一個租約就放手，而且放手後先不接新工作，直到下游恢復（run() 開頭的 _sink_back()）；每次重試前再檢查一次租約。

    看 _heartbeat() 的程式碼 
    async def _heartbeat(self, lease: TaskLease, tracker: LeaseTracker) -> None:
    interval = lease.ttl_ms / 3 / 1000
    timer = PeriodicTimer(interval)
    while True:
        await timer.tick()
        sent_at = self._clock.now()
        extended = await self._client.heartbeat(lease, interval)
        if extended is True:
            tracker.extend_to(lease_end(sent_at, lease.ttl_ms))
        elif extended is False:
            tracker.revoke()
            return
  3. 先寫結果，再回報完成
    WorkClient.deliver() → ResultStore.record()；WorkClient.complete() → TaskQueue.complete()

    回報會一直重試到上游回應。如果租約已經不是自己的（被改派了），上游回 409 並記成過期的完成回報；同一個 worker、同一個 attempt 重複回報（第一次的回覆掉了）則照樣回 200。兩步之間斷掉，任務會被改派再做一次，下游以任務編號去重。結束時（不論成功、放棄或程序要關）finally 取消心跳 task；心跳 task 如果是自己出錯而不是被取消，錯誤會往上拋，讓 tasks.supervise() 停掉整個程序。

4. 啟動時發生什麼

run.sh 用 exec .venv/bin/uvicorn --factory <套件>.main:create_app --app-dir src --host 127.0.0.1 --loop uvloop --http httptools --lifespan on --no-access-log 啟動。用 exec 是因為 verify 腳本拿到的 PID 必須就是伺服器本身（它會直接 SIGKILL）；單一程序，沒有 reload、沒有多 worker。--lifespan on 讓背景迴圈啟動失敗時整個程序跟著失敗，而不是被 uvicorn 當成「不支援 lifespan」默默略過。

Witness

src/witness/main.py 的 create_app()：WitnessConfig.from_env() 讀 PORT、DATA_DIR、NODES、LEASE_TTL_MS → 建立 LeaseTable。LeaseTable 從 witness.json 讀回上次的狀態；如果之前有人持有租約，就當作它還持有一個完整的 TTL，因為重啟期間那台可能還在服務。

Node

src/node/main.py 的 create_app()：NodeConfig.from_env()（設定互相矛盾會直接啟動失敗，例如租約短於 3 次續約，訊息會點名變數）→ NodeRuntime：開啟 log.jsonl（最後一行寫到一半就丟掉，中間壞掉就拒絕啟動）、建立 NodeState（從 epoch.json 讀回 epoch）。lifespan 啟動時用 tasks.supervise() 包著 ElectionWorker.run() 和 ReplicationWorker.run() 兩個 task。一律以備機身分啟動，先等一個 TTL 才可能去搶主。

Gateway

src/gateway/main.py 的 create_app()：GatewayConfig.from_env() 讀 PORT、NODE_URLS、POLL_INTERVAL_MS → 建立 httpx client 和 PrimaryTracker，lifespan 啟動輪詢 task。剛啟動還沒輪詢到主機時，所有請求回 503。

Upstream

src/upstream/main.py 的 create_app()：UpstreamConfig.from_env() 讀 PORT、TASK_LEASE_TTL_MS → 建立 EventLog 和 TaskQueue，lifespan 用 tasks.supervise() 啟動 reap()。資料只在記憶體。

Worker

src/worker/main.py 的 create_app()：WorkerConfig.from_env() 讀 MODE 等設定 → WorkerRuntime 依模式只建立 HotHotWorker 或 DispatchWorker 其中一個，lifespan 用 tasks.supervise() 啟動它的 run()。熱熱模式啟動時讀回 checkpoint.json（壞掉就拒絕啟動）；START_FROM=latest 時改成跳到上游最新的事件。

Sink

src/sink/main.py 的 create_app()：SinkConfig.from_env() 讀 PORT → 建立 ResultStore。資料只在記憶體。

「重啟後先等一個 TTL」很關鍵：備機重啟前可能剛承諾過主機「3 秒內不搶」，重啟後記憶體裡的承諾不見了，所以把啟動當成「剛聽到主機」來處理。

# src/node/cluster/node_state.py: NodeState.__init__()
self._last_heard_from_primary = clock.now()

def try_begin_candidacy(self) -> bool:
    silence = self.clock.now() - self._last_heard_from_primary
    if self._term is not None or self._candidate or silence < self._config.lease_ttl + self._config.election_delay:

    self._candidate = True
    return True

5. 關鍵設計

witness 只在三種情況下換主機

現任主機續約永遠成功；別人要拿租約，必須「租約已到期」而且「自己是同步中的備機」。換手時 epoch 加 1，成為 fencing token。

# src/witness/lease_table.py
def acquire(self, node: str | None) -> LeaseReply:
    self._require_known(node)
    now = self._clock.now()
    holder = self._state.holder
    if holder == node:
        # Also after expiry: nobody else took over in between, so the holder still has the newest data.
        self._expires_at = now + self._config.lease_ttl
        return self._reply(granted=True)
    if holder is not None and now < self._expires_at:
        return self._reply(granted=False, reason=f"lease held by {holder}")
    if holder is not None and not self._state.standby_in_sync:
        return self._reply(granted=False, reason=f"{node} may be missing acknowledged writes; waiting for {holder} to return")
    # …… 換手：先寫進 witness.json 再生效，epoch + 1，新的備機（舊主機）先標成不同步

從 .NET 搬過來的規則

設計為什麼在哪裡
兩種租約：witness 的，和備機的承諾只要拿到 3 票中的 2 票就能服務，witness 單獨掛掉或備機單獨掛掉都不會停NodeState._lease_until()、extend_peer_lease()
備機在向 witness 要租約時拒絕所有複寫否則它可能一邊被 witness 授權，一邊又承諾舊主機「不搶主」，兩台會同時有權服務NodeState.handle_replicate() 的 _candidate
witness 的同步狀態帶版本號逾時放棄的 HTTP 請求還是可能晚到。「備機同步中」必須附上最新版本才會被接受，晚到的舊訊息蓋不掉後來的「備機不同步」LeaseTable.set_standby_in_sync()、PrimaryTerm.try_mark_in_sync()
對 witness 的呼叫一次只送一個同一個任期內的兩個報告不會互相超車PrimaryTerm 的 _witness_calls（asyncio.Lock）
Raft 式 log 比對用 (index, epoch) 認出分歧的資料；只截掉比目前主機舊的 epoch，所以晚到的舊心跳不會誤刪新資料ReplicatedLog.append_from()
讀取也等到安全才回不讓 client 看到「切換後會消失」的值KvService.get()
單調時鐘租約和逾時都用 time.monotonic()，不會因為系統時間被調整而變長或變短src/shared/clock.py
沒有 witness 的對照組同一份程式，ARBITER=none 時備機 3 秒沒聽到主機就自己升格，用來實測腦裂的代價ElectionWorker.tick_without_witness()、NoArbiter

C：改派的任務排最前面它已經等最久了TaskQueue._expire()
C：心跳固定間隔、每次有上限一次卡住的心跳不會把下一次推到租約之後DispatchWorker._heartbeat()
C：做不完就放手，放手後先不接新工作，直到下游恢復心跳只證明活著，不證明做得完；連不到下游還一直心跳，任務會卡住。放手後如果馬上再租，下一件（甚至剛放掉的那件）也會卡住，所以先當成斷路器打開，問到下游的 /health 回應了才再租DispatchWorker._deliver()、_sink_back()
B、C：下游以編號去重重複無法完全避免（at-least-once），只能讓它無害；內容不同的重複當成衝突記下來ResultStore.record()

換成 asyncio 之後要注意的地方

.NET 的做法Python 版的對應在哪裡
lock (_gate) 保護「檢查再動作」不用鎖：一個 event loop、所有狀態只在 loop 上改。規則是「檢查到動作之間不能有 await」，所以 NodeState、ReplicatedLog、LeaseTable 的方法全部是同步函式。所有端點都是 async def，因為一般的 def 會被 FastAPI 丟到 thread pool 執行，就會跟 loop 搶狀態。node_state.py、replicated_log.py、lease_table.py
任期結束時取消 Ended token屬於一個任期的背景工作（複寫迴圈、請 witness 單獨確認、回報同步中）都用 PrimaryTerm.spawn() 建立，end() 時一起 cancel()。複寫 task 被取消時，外層用 Task.cancelling() 分辨是「任期結束」還是「程序要關了」。PrimaryTerm.spawn()、ReplicationWorker.run()
TaskCompletionSource 當訊號Signal：觸發就換一個新的 asyncio.Event。等待的一方先拿 Event 再檢查狀態，之後的變化一定會叫醒它。primary_term.py 的 Signal
CancelAfter(RENEW_INTERVAL)asyncio.timeout() 包住整個 httpx 呼叫（連線到最後一個 byte），逾時回 None；外層的取消照樣往上傳，不會被吞掉。httpx 設 trust_env=False，環境裡的 proxy 設定不會影響程序之間的呼叫。RpcClient.post()
BackgroundService 丟例外就停掉整個 hosttasks.supervise() 記錄 CRITICAL 後送 SIGTERM 給自己，讓 uvicorn 正常關閉；不是衝著自己來的 CancelledError 也算異常。選主迴圈死掉的節點如果繼續活著，會一直被當成主機卻不續約也不下台，不如直接停掉讓備機接手。一般的背景 task 失敗也一定會記錄（tasks.spawn()）。src/shared/tasks.py
SocketsHttpHandler 沒有連線數上限gateway 的 httpx client 設 httpx.Limits(max_connections=None)。httpx 預設最多 100 條連線，健康檢查和轉發共用同一個連線池，寫入一慢，健康檢查就排不到連線、逾時，gateway 會誤以為沒有主機。src/gateway/main.py 的 UPSTREAM_LIMITS
Kestrel 預設 request body 上限 30 MBread_capped_body() 邊讀邊算，超過就回 413，不會把整個程序的記憶體吃光。src/shared/http.py
System.Text.Json 嚴格模式自己寫的 JsonObject：欄位名稱不分大小寫，數字要是整數（"2"、2.0、true 都不算），型別錯就回 invalid JSON body at $.欄位；.NET 是 int 的欄位（attempt、waitMs、ttlMs）用 int32() 讀，超過 231 也是 400。value 長度用 UTF-16 code unit 算，跟 .NET 的 string.Length 一樣。src/shared/wire.py、node/kv.py、sink/result_store.py
長輪詢收到 RequestAborted 就取消uvicorn 不會因為 client 斷線就取消處理中的請求。until_disconnected() 把租任務的等待放進一個 task，另一個 task 等 receive() 回 http.disconnect，誰先完成就取消另一個。沒有這個，被砍的 worker 留下的長輪詢在剩下的等待時間（最多 0.5 秒）內還是會把新任務租走，那件任務要等 2 秒租約到期才會改派。src/shared/http.py、upstream/main.py 的 lease_task()
TaskCompletionSource 叫醒長輪詢跟架構 A 的 Signal 同一招：EventLog 每次附加、TaskQueue 每次加任務或回收租約，就觸發目前的 asyncio.Event 再換一個新的。等待的一方先檢查、再拿起 Event，中間沒有 await，不會漏叫。EventLog.append()、TaskQueue._pulse()
一個沒有連線上限的 HttpClientworker 的 WorkClient 開三個 httpx client：長輪詢一個、上游的心跳和完成回報一個、下游一個，都不設連線上限。長輪詢可能占著連線 0.5 秒，不能讓心跳排在它後面（gateway 那次學到的教訓）。src/worker/client.py
PeriodicTimershared.clock.PeriodicTimer：固定的時間格線，錯過的一格立刻補一次，不會連續補好幾次。心跳和租約回收都用它。src/shared/clock.py
await heartbeating 讓心跳的例外往上拋asyncio.gather(..., return_exceptions=True) 會把例外吞掉。run_task() 的 finally 先取消心跳 task、等它結束，如果它不是被取消而是自己出錯，就把錯誤再拋出去。DispatchWorker.run_task()
租約回收後誰拿到任務：thread pool 上的競爭asyncio 依「開始等待的先後」叫醒等待者，最早開始等的那台一定先拿到。移植時的同一程序測試裡只有一件任務，連不到下游而放手的那台 worker 常常剛好是最早開始等的，同一件任務多半又回到它手上（有一次 10 秒內連續 10 輪都是它）。這是設計上的缺陷，三種語言都有（真實負載下則是放手後馬上接走下一件、又卡住），所以加了斷路器：放手後先不接新工作，直到下游恢復。端到端測試維持只有一件任務，並檢查只改派 1 次。DispatchWorker._sink_back()、tests/test_work.py

延遲：跟 .NET 比

本機 loopback 上同步寫入 p50 約 3.48 ms（.NET 0.94 ms），差距是 Python 處理 HTTP 本身的成本。兩台之間加 10 ms 單程延遲的 crash-slow，p50 是 46.4 ms（.NET 40.5 ms）：網路延遲占了絕大部分，語言的差距只剩幾 ms。

  • 兩種語言都要約 2 個來回（約 40 ms），不是 1 個：複寫一次只送一批，寫入如果在一批送出途中到達，要等這批回來再等下一批。
  • httpx 把一個請求的 header 和 body 分成兩次寫入 socket，uvicorn 回覆時也一樣。verify/chaos.py 的代理一開始對每一次寫入各延遲一次，把這裡量成 71 ms；改成真實網路的行為（每段資料都晚 10 ms 到，但連續送出的仍連續到達）之後，才是 46 ms。

還沒處理：斷電（log 只寫進作業系統，沒有 fsync）、gateway 本身的備援、各程序之間的身分驗證。複寫一次只送一批，所以同步寫入要 1 到 2 個網路來回。
