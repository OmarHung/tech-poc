模組化單體轉微服務｜.NET 版運作說明

這頁說明 dotnet/ 裡的程式怎麼運作：有哪幾個程式、一個請求怎麼流動、拆分前後差在哪裡。框架是 ASP.NET Core 10 Minimal API，gateway 用 YARP 2.3 轉發。

1. 全貌 2. 互動流程圖 3. 一個下單請求的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三個程式

這是一個小型電商：Catalog 管商品和庫存，Orders 管訂單。原本兩個模組都在同一個程式（模組化單體）裡，這次把 Catalog 拆成獨立的微服務。

Gateway

127.0.0.1:8080 ・ src/Gateway/

所有請求的入口（Strangler Fig 門面）。/products 開頭的請求依目前設定送給 Monolith 或 CatalogService，其他一律送 Monolith。設定可以在執行中切換。

Monolith

127.0.0.1:8081 ・ src/Monolith/

原本的模組化單體。Orders 模組留在這裡；Catalog 模組⚠已轉微服務，但保留在原位，用來對照和回滾。

CatalogService

127.0.0.1:8082 ・ src/CatalogService/

從單體拆出來的微服務。裡面的 Catalog 模組跟單體那份是同一套程式碼（只差 namespace），現在由它負責商品資料。

2. 互動流程圖：四個階段

點下面的按鈕切換階段，圖上藍色虛線是請求實際走的路徑，紅色是失敗的路徑，半透明的是這個階段沒用到的部分。

階段一：模組化單體

設定
Monolith CATALOG_MODE=inprocess；Gateway CATALOG_ROUTE=monolith
查商品
Gateway → Monolith 的 Catalog 路由 → InMemoryCatalog.GetAsync()。全部在同一個程序裡，是一般的方法呼叫。
下單
Gateway → Orders 模組 → ICatalog.ReserveAsync() → InMemoryCatalog.ReserveAsync() 扣庫存 → 建立訂單。
誰回應
X-Served-By: monolith。CatalogService 已經部署，但沒有任何流量。
實測 p50
查商品 0.150 ms、下單 0.156 ms

階段二：拆出 Catalog，請求仍經由單體

設定
Monolith 改成 CATALOG_MODE=remote 重啟（Gateway 不用動）
查商品
Gateway → Monolith 的 Catalog 路由 → HttpCatalogClient.GetAsync() → HTTP → CatalogService。路由程式碼沒變，只是 DI 注入的實作換了。
下單
Orders 模組照樣呼叫 ICatalog.ReserveAsync()，但現在是 HTTP 呼叫 CatalogService 扣庫存。Orders 的程式一行都沒改。
重點
單體不再持有商品資料，資料只有 CatalogService 那一份，兩邊看到的庫存一定一致。
實測 p50
查商品 0.254 ms、下單 0.240 ms（每多一跳約 +0.08 ms）

階段二：Gateway 把 /products 直接切給 CatalogService

設定
PUT /admin/routes {"catalog":"service"}，執行中切換，不用重啟
查商品
Gateway 直接送 CatalogService，不經過單體，少一跳。X-Served-By: catalog-service。
下單
不受路由影響，還是 Gateway → Orders → HTTP → CatalogService。
回滾
再呼叫一次 {"catalog":"monolith"} 就切回去，立即生效。負載下來回切 15 次，34,633 個請求 0 失敗。
實測 p50
查商品 0.141 ms（跟拆分前差不多）

階段三：CatalogService 故障

狀況
CatalogService 停機。這是拆分之後才有的新故障點。
查商品
不管路由指向哪邊都回 502：直連時 Gateway 回 upstream unavailable，經單體時 Monolith 回 catalog unavailable。
下單
Orders 呼叫 CatalogService 失敗，回 502 catalog unavailable。
仍然正常
查既有訂單（GET /orders/1）還是 200，因為訂單建立時已經存了商品名稱和價格的快照，不需要再問 Catalog。
錯誤細節
客戶端只看到一句話；連線失敗的細節（網址、例外）只用 ILogger.LogWarning() 寫進伺服器 log。

3. 一個下單請求的完整旅程

以階段二（CATALOG_MODE=remote）的 POST /orders {"productId":1,"quantity":2} 為例，從進門到回應經過這些程式碼：

  1. Gateway 收到請求，決定送去哪裡
    src/Gateway/Program.cs 的萬用路由 app.Map("/{**path}")、RoutingTable.cs 的 Resolve()

    /orders 不是 catalog 路徑，所以一律送 Monolith。實際轉發交給 YARP 的 IHttpForwarder.SendAsync()，連線專屬的標頭、串流都由它處理。

  2. Monolith 解析 JSON
    Modules/Orders/OrderEndpoints.cs 的 POST /orders → HostingExtensions.cs 的 ReadJsonAsync<CreateOrderRequest>()

    不是 JSON、格式錯、型別錯都會變成 InvalidInputException（400）。ASP.NET 預設會把 "quantity":"2" 這種字串當成數字接受，這裡用 AddStrictJson() 關掉了，行為才跟 Rust、Python 版一致。錯誤訊息只帶 JSON 欄位位置，不帶 .NET 型別名稱。

  3. Orders 模組驗證輸入，再透過介面扣庫存
    Modules/Orders/OrderService.cs 的 PlaceAsync()

    先在本地驗證（數量要在 1–100、商品編號要是正整數），不合格就直接回 400，不會浪費一次網路呼叫。接著呼叫 catalog.ReserveAsync()，它只知道 ICatalog 這個介面，不知道背後是本地還是遠端。

    public async Task<Order> PlaceAsync(long productId, long quantity, CancellationToken cancellationToken = default)
{
    CatalogRules.ValidateId(productId, "productId");
    CatalogRules.ValidateQuantity(quantity);
    var product = await catalog.ReserveAsync(productId, quantity, cancellationToken);
    var order = new Order(
        Interlocked.Increment(ref _lastId),
        productId,
        product.Name,
        product.Price,
        quantity,
        product.Price * quantity);
    _orders[order.Id] = order;
    return order;
}
  4. 介面背後是 HTTP client，送出 HTTP 請求
    Modules/Catalog/HttpCatalogClient.cs 的 ReserveAsync()

    送出 POST http://127.0.0.1:8082/products/1/reserve {"quantity":2}，HttpClient.Timeout 是 2 秒。HttpClient 只建立一次（DI singleton），連線會重複使用。如果是階段一（inprocess），DI 注入的是 InMemoryCatalog，這一步換成直接呼叫它的 ReserveAsync()，接著跳到第 5 步的邏輯，只是在同一個程序裡執行。

  5. CatalogService 扣庫存
    src/CatalogService/Catalog/CatalogEndpoints.cs 的 POST /products/{id}/reserve → InMemoryCatalog.cs 的 ReserveAsync()

    商品放在 ImmutableSortedDictionary 裡。扣庫存時在鎖裡「檢查庫存 → 用 with 建立新的 Product → 換上一整份新的字典」，所以很多人同時下單也不會超賣（有測試：50 個並行請求搶 10 件，剛好 10 個成功）；查詢則完全不需要鎖。

    public Task<Product> ReserveAsync(long id, long quantity, CancellationToken cancellationToken = default)
{
    CatalogRules.ValidateQuantity(quantity);
    lock (_writeGate)
    {
        if (!_products.TryGetValue(id, out var current))
        {
            throw CatalogErrors.ProductNotFound(id);
        }
        if (current.Stock < quantity)
        {
            throw CatalogErrors.InsufficientStock(id, quantity, current.Stock);
        }
        var updated = current with { Stock = current.Stock - quantity };
        Volatile.Write(ref _products, _products.SetItem(id, updated));
        return Task.FromResult(updated);
    }
}
  6. Monolith 把 HTTP 回應還原成原本的結果
    Modules/Catalog/HttpCatalogClient.cs 的 SendAsync()、ToApiExceptionAsync()

    成功就解析成 Product；400、404、409 還原成跟本地實作一模一樣的例外（InvalidInputException、NotFoundException、InsufficientStockException），所以 Orders 分不出差別。連不上、逾時（HttpRequestException、TaskCanceledException）或其他錯誤一律變成 CatalogUnavailableException（502），細節只寫 log。

    看 ToApiExceptionAsync() 的程式碼 
    private async Task<ApiException> ToApiExceptionAsync(HttpResponseMessage response, CancellationToken cancellationToken)
{
    var message = await ReadErrorMessageAsync(response, cancellationToken);
    switch (response.StatusCode)
    {
        case HttpStatusCode.BadRequest:
            return new InvalidInputException(message);
        case HttpStatusCode.NotFound:
            return new NotFoundException(message);
        case HttpStatusCode.Conflict:
            return new InsufficientStockException(message);
        default:
            logger.LogWarning("catalog-service returned {Status}: {Message}", (int)response.StatusCode, message);
            return new CatalogUnavailableException();
    }
}
  7. 建立訂單，回 201
    OrderService.PlaceAsync()（第 3 步那段程式的後半）、OrderEndpoints.cs 的 Results.Created()

    訂單會複製商品名稱和單價（快照），之後 Catalog 改價或停機都不影響已成立的訂單。回應由 UseServedBy("monolith") 加上 X-Served-By 標頭。

  8. Gateway 把回應轉回 client
    YARP 的 IHttpForwarder

    狀態碼、標頭（含 X-Served-By）和內容由 YARP 串流回 client。

每種錯誤在哪裡被擋下

狀況在哪裡被擋回應
不是 JSON、格式錯、型別錯（含字串數字）第 2 步 ReadJsonAsync()400
數量不在 1–100、商品編號不是正整數第 3 步 CatalogRules.ValidateQuantity()、ValidateId()400
商品不存在第 5 步回 404 → 第 6 步還原成 NotFoundException404
庫存不足第 5 步回 409 → 第 6 步還原成 InsufficientStockException409
CatalogService 連不上、逾時第 6 步 SendAsync() 的 catch502 catalog unavailable
Gateway 連不到 Monolith第 1 步，YARP 回報 ForwarderError502 upstream unavailable

所有業務錯誤都是 ApiException 的子類別，帶著自己的 StatusCode；HostingExtensions.cs 的 UseApiErrors() middleware 把它統一轉成 {"error": "..."}。

還沒處理的情況：第 5 步扣庫存成功，但回應在第 6 步之前逾時，Monolith 會回 502、不建立訂單，可是庫存已經被扣了。正式上線前要補冪等鍵和補償機制（Saga / Outbox）。

4. 啟動時發生什麼

Gateway

src/Gateway/Program.cs：GatewayConfig.FromEnvironment() 讀 PORT、MONOLITH_URL、CATALOG_URL、CATALOG_ROUTE → 註冊 YARP 的 AddHttpForwarder() 和 RoutingTable（singleton）→ 建立轉發用的 HttpMessageInvoker（不跟隨轉址、不解壓縮、不帶 cookie，閒置逾時 5 秒）→ 綁定 127.0.0.1:8080。

Monolith

src/Monolith/Program.cs：MonolithConfig.FromEnvironment()（CATALOG_MODE 打錯會直接啟動失敗）→ 用 DI 依模式註冊 ICatalog 的實作 → 掛上 UseServedBy、UseApiErrors middleware 和三組路由 → 綁定 127.0.0.1:8081。

CatalogService

src/CatalogService/Program.cs：讀 PORT → 把載入三筆種子商品的 InMemoryCatalog 註冊成 ICatalog → 掛上 middleware、Catalog 路由和 health → 綁定 127.0.0.1:8082。

整個遷移的開關就在 Monolith 的 Program.cs 這幾行：同一個 ICatalog，依環境變數註冊不同實作。Catalog 路由和 Orders 都從 DI 拿 ICatalog，所以會一起切換。

var config = MonolithConfig.FromEnvironment();
// ……
builder.Services.AddSingleton<ICatalog>(services => config.CatalogMode == CatalogMode.Remote
    ? HttpCatalogClient.Create(config.CatalogUrl, services.GetRequiredService<ILogger<HttpCatalogClient>>())
    : InMemoryCatalog.Seeded());
builder.Services.AddSingleton<OrderService>();

5. 關鍵設計

介面是拆分的接縫

Orders 只依賴 ICatalog 這個介面，所以 Catalog 從「同程序內」搬到「另一個程序」時，只要新增一個用 HTTP 實作同一個介面的 HttpCatalogClient，再改 DI 註冊。這就是為什麼起點必須是模組化單體：模組之間如果直接存取彼此的資料，就沒有這條接縫可以切。

// src/Monolith/Modules/Catalog/ICatalog.cs
public interface ICatalog
{
    Task<IReadOnlyList<Product>> ListAsync(CancellationToken cancellationToken = default);

    Task<Product> GetAsync(long id, CancellationToken cancellationToken = default);

    /// <summary>Atomically takes <paramref name="quantity"/> units out of stock and returns the updated product.</summary>
    Task<Product> ReserveAsync(long id, long quantity, CancellationToken cancellationToken = default);
}

Gateway 切換路由：一次寫入，不影響進行中的請求

目前的路由存在一個 volatile 欄位裡。PUT /admin/routes 呼叫 Switch() 寫入新值；每個請求進來時讀一次、決定上游之後就交給 YARP，所以切換那一瞬間正在處理的請求不會被中斷。

// src/Gateway/RoutingTable.cs
private volatile CatalogRoute _catalogRoute = initialRoute;

public void Switch(CatalogRoute route) => _catalogRoute = route;

public string Resolve(PathString path) =>
    _catalogRoute == CatalogRoute.Service && IsCatalogPath(path) ? upstreams.Catalog : upstreams.Monolith;

其他

設計做法在哪裡
錯誤跨網路後不變形錯誤都是帶 StatusCode 的 ApiException；遠端 client 依狀態碼還原成同一個類別ApiException.cs、HttpCatalogClient.cs
錯誤訊息不外洩客戶端只看到「catalog unavailable」；JSON 錯誤只回欄位位置，不回 .NET 型別名稱；細節寫進 ILoggerHttpCatalogClient.cs、HostingExtensions.cs
嚴格的 JSON 格式AddStrictJson() 把 NumberHandling 設成 StrictHostingExtensions.cs
標示誰回應Monolith、CatalogService 用 UseServedBy()；Gateway 自己的回應用 endpoint filter 加上 X-Served-By: gatewayHostingExtensions.cs、Gateway/Program.cs
兩份 Catalog 不會走樣兩份 Catalog/ 的檔案只差 namespace；同一套測試在 Monolith.Tests/CatalogModule/ 和 CatalogService.Tests/ 各一份tests/
只聽本機三個程式都用 UseUrls("http://127.0.0.1:…")；/admin/routes 沒有驗證，正式環境一定要加各自的 Program.cs

6. 怎麼跑

# 在 dotnet/ 底下
./run.sh build                     # dotnet build -c Release
./run.sh test                      # 81 個單元測試

# 手動啟動（三個終端機分別執行），這是階段二的設定
PORT=8082 ./run.sh catalog-service
PORT=8081 CATALOG_MODE=remote CATALOG_URL=http://127.0.0.1:8082 ./run.sh monolith
PORT=8080 CATALOG_ROUTE=monolith ./run.sh gateway

# 打打看
curl -i http://127.0.0.1:8080/products/1
curl -i -X POST http://127.0.0.1:8080/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":2}'
curl -i -X PUT  http://127.0.0.1:8080/admin/routes -H 'Content-Type: application/json' -d '{"catalog":"service"}'
