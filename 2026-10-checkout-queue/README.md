# 結帳排隊機制

- 狀態：已完成
- 開始日期：2026-10-30
- 結論：有條件可行（.NET / Python / Rust 三種實作結果一致）：排隊確實能削峰，而且不超賣、不重複扣款；但一場活動受單一 Redis 執行緒限制，前面要有負載平衡器接住連線，條件見文末

## 背景與目標

驗證在高併發結帳（例如限量搶購）時，能不能用排隊機制控制流量，讓系統不崩潰、商品不超賣，使用者也能看到合理的等待狀態。

## 要驗證的假設

在結帳前加一層排隊機制，可以把瞬間湧入的流量削平成系統承受得住的速度，同時保證庫存扣減正確（不超賣、不重複扣）。

## 待釐清問題

- [x] 排隊模型：在進入結帳前排（虛擬等候室），還是把結帳請求放進 queue 非同步處理？→ 虛擬等候室。取號排隊，同時在結帳中的人數有上限，有空位才放下一位進來。理由見「設計」
- [x] 防超賣：庫存扣減用什麼方式保證原子性？→ Redis Lua script。每個狀態轉換（排隊、放行、下單扣庫存、付款、逾時釋放）各是一支腳本，檢查和寫入在同一個原子步驟完成
- [x] 前端體驗：排隊順位和預估等待時間怎麼即時回傳？→ 用 SSE（server-sent events）推送，polling 留著當退路。實測同一條隊伍：放行後使用者知道的延遲從 polling 的約 0.5 秒降到 3 ms，打到 app 的請求從每秒約 930 次降到 9 次，同樣的名額每秒能放行的人數多一倍；三種語言結果一致（見實驗紀錄）。WebSocket 沒做：狀態只需要 server 單向推給使用者，用不到雙向，SSE 走一般 HTTP、瀏覽器會自動重連
- [x] 例外狀況：使用者中途離開、排到但逾時未付款、重複點擊怎麼處理？→ 見下表
- [x] 承載能力：每秒多少請求下仍然穩定？瓶頸在哪一層？→ 單機實測兩台 instance 每秒輪詢：Rust 6.8 萬次、.NET 5.6 萬次、Python 1.3 萬次（每個 Python 程序受 GIL 限制只用滿一個核心）。瓶頸依序是：同一瞬間大量新建連線、app 本身（Python）、Redis 單執行緒（一場活動約每秒 9 萬次腳本，.NET 和 Rust 峰值時已用到 65%）。數字是筆電單機量的，壓測端和服務沒有分開，用專業工具分機器量列在「下一步」

| 例外狀況 | 處理方式 |
|----------|----------|
| 排隊中離開（關分頁、手機休眠） | 輪詢就是心跳；改用 SSE 時，串流開著就算在線上。超過 `HEARTBEAT_TIMEOUT_MS` 沒有心跳，輪到時會被跳過（`abandoned`），名額給下一位。可以重新排，但排到最後 |
| 被放行了但沒下單 | 放行有時限（`ADMISSION_WINDOW_MS`），到期名額收回（`expired`）。可以重新排，排到最後 |
| 下單了但沒付款 | 訂單保留庫存到 `PAYMENT_WINDOW_MS`，到期庫存放回，下一位可以買到。可以重新排 |
| 重複點「結帳」（連點、重試、兩個分頁） | ticket 本身就是 idempotency key。同一張 ticket、同樣數量再送一次，回傳原本那張訂單（200），庫存只扣一次；數量不同回 409 `ticket_used` |
| 重複點「付款」 | 扣款紀錄和「待付款 → 已付款」在同一個原子步驟。第一個請求回 201（這次扣的），之後都回 200（之前已扣），不會再扣 |
| 同一人開兩個分頁排隊 | 一人只有一張有效 ticket，第二次排隊拿到同一張 |

## 範圍外

- 串接真實金流：付款在 Redis 內模擬
- 完整的購物車與訂單系統：一場活動只賣一種商品，每筆最多買 `MAX_PER_ORDER` 件
- 身分驗證：`userId` 直接由 request 帶入，當作已登入的使用者。`ticketId` 是 128-bit 隨機值，拿到它就能結帳
- 正式的前端頁面：附的操作頁（`GET /`）只是用來手動試的示範工具
- 防機器人、每個 IP 限流（通常放在 CDN / WAF）
- Redis 高可用：failover 時的資料遺失留給[雙機備援](../2026-10-dual-node-failover/)那邊處理
- 活動結束後清理 Redis 資料（現在不會刪，見實驗紀錄）

## 設計

### 三種語言共用什麼

排隊、放行、扣庫存、付款、釋放這些規則全部寫在 `shared/lua/` 的 Lua 腳本裡，三種語言送的是同一份腳本。各語言只負責外殼：讀設定、檢查輸入、呼叫腳本、把結果翻成 HTTP、跑兩個背景迴圈（定時放行、SSE 推送）。所以三種語言在正確性上的表現一樣，差別只在效能和資源。

### 流程

```
POST /queue/join ─▶ waiting ──(輪到你)──▶ admitted ──POST /checkout──▶ ordered
     取號            │  每秒輪詢               │ 時限內沒下單              │
                     │  GET /queue/tickets/id  ▼                           ▼
                     ├─(沒在輪詢)─▶ abandoned  expired           訂單 pending_payment
                     └─(全部賣完)─▶ sold_out                       │          │
                                                       POST /orders/id/pay   時限內沒付
                                                                   ▼          ▼
                                                                 paid      expired（庫存放回）
```

### 放行規則

每次定時任務（`TICK_MS`）會算：

> 可放行人數 = min(`MAX_ACTIVE`, 剩餘庫存) − 目前已放行、還沒下單的人數

- `MAX_ACTIVE` 就是削峰的旋鈕：不管外面排了多少人，同時在結帳的最多就這麼多
- 不放行超過剩餘庫存的人數。放進來卻一定買不到，只是換個方式告訴他「賣完了」
- 被未付款訂單保留的庫存不算剩餘庫存。等訂單逾時、庫存放回，下一輪就會再放人

### 為什麼不需要選主

每台 instance 都跑同一個定時任務，而且每一步都是一支 Lua script，在 Redis 裡原子執行。十台同時放行，結果跟一台一樣（有測試驗證）。任何一台掛掉，其他台照常放行。

### 狀態推送（SSE）

`GET /queue/tickets/{id}/events` 連上後先送一次目前狀態，之後有變化才推，ticket 進入終局（下單、逾時、被跳過、賣完）就結束串流。

- **放行要即時**：`admit.lua` 放行時用 Redis pub/sub 廣播被放行的 ticket。每台 instance 訂閱一次，收到後只推給連在自己身上的人（`TicketPushWorker`）
- **順位每秒更新一次**：每台 instance 每個 `POLL_INTERVAL_MS` 用一支批次腳本（`watch.lua`）取回所有連線者的狀態，有變才推。推送頻率不會超過 polling
- **串流就是心跳**：`watch.lua` 順便更新排隊中的人的 `lastSeenAt`；關掉分頁、串流斷了，心跳就停
- **不會漏**：pub/sub 訊息漏掉（例如 Redis 重連）時，最晚下一次每秒更新就補上；串流 15 秒沒東西送就送一行註解，避免被負載平衡器當成閒置連線切掉

### 時間

截止時間用各台 instance 的時鐘（`TimeProvider`）算，傳進腳本。好處是測試可以用假時鐘，不用 sleep；代價是各台時鐘要同步（NTP），誤差會直接變成截止時間的誤差。時限都是秒到分鐘等級，毫秒級的誤差可以接受。

## HTTP 介面

所有語言版本都照這份介面實作，`verify/scenario.py` 才能共用。JSON 欄位用 camelCase，狀態值用 snake_case，時間是 epoch 毫秒，沒有值的欄位不輸出。

| 方法與路徑 | 用途 | 成功 | 錯誤 |
|------------|------|------|------|
| `GET /health` | 健康檢查（含 Redis） | 200 `{status, instance, saleId}` | 503 |
| `POST /queue/join` `{userId}` | 排隊 | 201 新 ticket／200 已有 ticket | 400、409 `sold_out` |
| `GET /queue/tickets/{ticketId}` | 查狀態（兼心跳） | 200 ticket | 400、404 |
| `GET /queue/tickets/{ticketId}/events` | 同上，改用 SSE 推送（串流開著就算心跳） | 200 `text/event-stream`，每個事件的 `data` 是 ticket JSON | 400、404 |
| `POST /checkout` `{ticketId, quantity}` | 下單、保留庫存 | 201 新訂單／200 同一張 ticket 已下過的單 | 400、403 `not_admitted`、404、409 `sold_out`/`insufficient_stock`/`ticket_used`、410 `admission_expired` |
| `GET /orders/{orderId}` | 查訂單 | 200 order | 400、404 |
| `POST /orders/{orderId}/pay` | 付款（模擬） | 201 這次扣款／200 之前已扣 | 400、404、410 `order_expired` |
| `GET /admin/audit` | 對帳數字（只給 PoC 用，沒有驗證） | 200 | |
| `GET /admin/config` | 活動規則：同時放行人數、每單上限、各種時限（不含 Redis 位址） | 200 | |
| `GET /admin/tickets` | 每位顧客目前的號碼牌和訂單，最新的 300 位（唯讀，不算心跳） | 200 `[{ticket, order?}]` | |
| `GET /` | 操作頁（`shared/demo/index.html`，每次請求換新的 CSP nonce） | 200 HTML | |

- 錯誤一律是 `{"error": "給人看的訊息", "code": "給程式判斷的代碼"}`。Redis 連不上回 503 `unavailable`
- `sold_out` 是終局：架上沒有，也沒有未付款訂單保留庫存，客戶端可以停止。`insufficient_stock` 只是架上暫時不夠（可能是 0，因為還有未付款訂單），放行期間可以重試
- ticket：`ticketId, userId, seq, status, position?, estimatedWaitSeconds?, admittedAtMs?, admissionExpiresAtMs?, orderId?, pollAfterMs`
- order：`orderId, ticketId, userId, quantity, status, createdAtMs, paymentExpiresAtMs, paidAtMs?`
- 每個回應都帶 `X-Served-By` header，標示哪台 instance 回的

| 變數 | 預設 | 說明 |
|------|------|------|
| `PORT` | 8090 | 只聽 127.0.0.1 |
| `REDIS_URL` | 127.0.0.1:6379 | |
| `INSTANCE_NAME` | checkout-queue | 放進 `X-Served-By` |
| `SALE_ID` | demo | 同一個 Redis、同一個 `SALE_ID` 的 instance 共同服務同一場活動 |
| `INITIAL_STOCK` | 100 | 只有活動第一次啟動時生效 |
| `MAX_PER_ORDER` | 2 | |
| `MAX_ACTIVE` | 50 | 同時在結帳的人數上限 |
| `ADMISSION_WINDOW_MS` | 120000 | 放行後多久內要下單 |
| `PAYMENT_WINDOW_MS` | 300000 | 下單後多久內要付款 |
| `HEARTBEAT_TIMEOUT_MS` | 15000 | 多久沒心跳算離開；至少要是輪詢間隔的 3 倍 |
| `POLL_INTERVAL_MS` | 1000 | 叫客戶端多久輪詢一次；SSE 也用它決定多久更新一次順位 |
| `TICK_MS` | 200 | 定時任務間隔 |

## 實驗紀錄

### 2026-10-30：.NET 版，兩台 instance 共用一個 Redis

環境：MacBook（12 核），Redis 7.4 跑在 Docker，兩台 instance 跟壓測程式都在同一台機器。下面的搶購數字是 2026-10-31 三種語言都完成後，.NET 版重跑的最新一次（`verify/results/dotnet-*.json`）。

**1. 搶購情境（正確性）**

1000 人搶 200 件，每人最多 2 件，`MAX_ACTIVE=20`。為了讓每條逾時路徑都在幾秒內發生，時限故意設很短（放行 4 秒、付款 3 秒、心跳 5 秒）。請求在兩台 instance 間輪流送，像沒有黏著（sticky session）的負載平衡器：排隊在 A、輪詢在 B，連點兩次結帳時兩個請求分別打到 A 和 B。

使用者分成幾種：一般買家（60%）、兩個分頁同時排隊（10%）、排隊後離開（10%）、被放行但不下單（10%）、下單但不付款（10%）。三分之一的人連點結帳，四分之一連點付款。

20 項檢查全部通過：

| 項目 | 結果 |
|------|------|
| 超賣 | 0 |
| 重複扣款 | 0（扣款 132 次 = 已付款訂單 132 筆） |
| 庫存守恆（架上 ＋ 保留中 ＋ 已售 = 200） | 成立 |
| 連點結帳、打到不同 instance，拿到同一張訂單 | 是 |
| 兩個分頁同時排隊，拿到同一張 ticket | 是 |
| 客戶端統計的已付款件數 = server 對帳的件數 | 是 |
| 最後 200 件全部付款，沒有卡在未付款訂單 | 是（17 筆未付款訂單逾時，庫存放回後又賣掉） |
| 依取號順序放行 | 是（166 次放行） |
| 離開的人被跳過、沒下單的人被收回名額 | 是 |
| 兩台 instance 都分到流量 | 是（各約一半） |

正確性是由 `/admin/audit` 從訂單本身重新加總，再和客戶端自己記錄的結果互相對照，不是只看 server 自己的計數器。另外用「故意弄壞」驗證測試有效：拿掉 Lua 裡的庫存檢查、或拿掉「已付款就不再扣」的判斷，各有對應的測試失敗。

**2. 尖峰 join 延遲：一開始看到好幾秒，原因不在排隊邏輯**

Python 驗證腳本量到 1000 人同時 join 的 p50 介於 0.8 到 3.4 秒，每次跑都不一樣，而且延遲集中在約 1 秒和約 3 秒附近。但吞吐量測試裡 join 只要 3 ms。為了找出原因，另外用 .NET 單檔程式當客戶端做對照（診斷用，沒有放進 repo）：

| 客戶端與連線方式 | 1000 人同時 join |
|------------------|------------------|
| Python，同一瞬間新建 1000 條連線 | p50 0.8～3.4 秒 |
| Python，連線先建好 | p50 2.5 秒 |
| .NET，同一瞬間新建 1000 條連線 | 部分連線被 server 端 reset |
| .NET，連線先分批建好 | **全部完成 32 ms**，p50 15 ms；3000 人 91 ms |

結論：

- 排隊本身吸收尖峰沒有問題，兩台 instance 32 ms 內就把 1000 人排進隊伍
- 同一瞬間大量「新建連線」才是第一個瓶頸。推測是 macOS 的 `kern.ipc.somaxconn=128` 把 listen backlog 壓到 128：Python 端的 1 秒、3 秒剛好是 TCP SYN 重送的間隔，.NET 端則直接收到 reset。正式環境要靠負載平衡器 / CDN 先接住連線，這也是等候室通常放在 edge 的原因
- 連線先建好時 Python 反而更慢，是因為 1000 條 thread 同時醒來搶 GIL。Python 驗證腳本量到的延遲有很大一部分是壓測端自己造成的，看正確性沒問題，看延遲要打折

**3. 瓶頸在哪一層**

用 .NET 客戶端開 128 條並行連線狂打輪詢（等候室裡量最大的請求）：

| 層 | 每秒 5.8 萬次輪詢時 |
|----|---------------------|
| 兩台 instance | 各約 2 核 CPU |
| Redis（單執行緒） | 66% CPU，每次腳本約 11 µs |
| 回應時間 | p50 2 ms、p99 5.4 ms |

- 加 instance 可以線性擴充；Python 驗證腳本只打得到 1.27 萬次/秒，是壓測端的上限
- 下一個天花板是 Redis。一場活動的 key 都在同一個 hash slot（Lua 才能保證原子性），等於鎖在一個 Redis 執行緒上，換算約每秒 9 萬次腳本
- 輪詢是最大宗：能同時排隊的人數大約是「Redis 每秒腳本數 × 輪詢間隔（秒）」。輪詢 1 秒時約 9 萬人，要更多就要讓排在後面的人輪詢慢一點

**4. 預估等待時間**

第一版用指數移動平均（EWMA，時間常數 10 秒）算放行速度，誤差中位數 41.5 秒，估得太長。原因是平均值從 0 開始爬，而整場搶購只有 20 幾秒，還沒收斂就賣完了。改成「最近 10 秒的平均放行速度，從開始有人排隊起算」之後，誤差中位數降到 1.5～3.4 秒（不同次執行）。先寫了一個固定放行速度的測試（每秒放 2 人、排第 10 位應該估 5 秒），舊算法估 12 秒、測試失敗，改完才通過。

搶購情境下，預估等待時間的意義有限：排在後面的人大多等不到，最後拿到的是「賣完了」。比起時間，「前面還有幾人、剩幾件」可能更實用。

**5. 狀態更新延遲**

使用者每秒輪詢一次，從 server 放行到使用者知道，中位數約 0.5 秒，符合預期（輪詢間隔的一半）。p95 有時到 1.5～3 秒，那是 Python 壓測端在同一秒同步輪詢、搶 GIL 造成的（實驗 8 改用 asyncio 客戶端後就沒有這個現象）。這也提醒兩件事：

- 放行時限要遠大於「輪詢間隔 ＋ 客戶端可能的延遲」。這次時限只有 4 秒，每次執行都有 2～3 位買家因為太晚看到放行，來不及下單就過期了
- 同一瞬間排隊的人會在同一個節奏輪詢，形成每秒一次的尖峰。`pollAfterMs` 加一點隨機抖動可以打散

**6. 獨立 review 找到的兩個問題（已修正）**

請另一個 agent 在沒看過我的設計理由的情況下，只看程式碼找正確性問題。它確認了超賣、重複扣款、FIFO、名額上限這幾個不變量在任何交錯順序下都成立，另外找到兩個問題，都先寫測試重現再修正：

- 「賣完」的意思前後不一致：下單時只要架上是 0 就回 `sold_out`，但排隊端的 `sold_out` 是「架上是 0，而且沒有未付款訂單」。客戶端看到 `sold_out` 可能就放棄了，其實未付款的訂單逾時後庫存還會回來。改成 `sold_out` 一律代表終局，暫時不夠時回 `insufficient_stock`
- 各台時鐘差幾毫秒時，放行腳本會在中途出錯：A 台先跨過整秒並記下起算時間，B 台還在前一秒，算出來的時間範圍是 0 秒，Redis 指令收到 0 個參數就報錯。前面已寫入的資料不會壞（狀態一致），但那一次的放行結果和速度更新會遺失。改成範圍至少 1 秒

**7. 售完後的資料**

賣完後，看到「賣完了」就離開的人，ticket 還留在 Redis 的等候清單裡（這次 816 筆）。量不大，但百萬人等級的活動要在結束後設 TTL 清掉。

### 2026-10-31：操作頁與 polling／SSE 對照

**8. polling 與 SSE 對照**

（.NET 版的數字；三種語言的對照見實驗 10。）同一條隊伍跑兩次：1000 人排隊，同時放行 5 人，被放行的人想 0.5 秒後下單，空出的名額再放下一位。第一次每個人每秒 polling 一次，第二次改連 SSE。兩次都在隊伍形成後量 20 秒。客戶端改用 asyncio 單執行緒（`verify/push.py`），避免壓測端自己拖慢延遲數字。

| 項目 | polling（每秒一次） | SSE |
|------|---------------------|-----|
| 放行到使用者知道 | p50 485 ms、p95 518 ms | **p50 3 ms、p95 10 ms、最慢 24 ms** |
| 每秒放行人數（同樣 5 個名額） | 5.0 | **9.2** |
| 打到 app 的請求 | 927 次/秒 | 9 次/秒（只剩下單） |
| 推給使用者的事件 | — | 862 次/秒（順位每秒更新一次） |
| app CPU（兩台合計，單核百分比） | 46.8% | 15.4% |
| app 記憶體（兩台合計） | 263 MB | 218 MB（約 950 條串流開著） |
| Redis 腳本 | 968 次/秒，忙碌 5.6% | 55 次/秒，忙碌 2.9% |

- **延遲**：polling 最多要等一個輪詢間隔才知道；SSE 是放行那一刻透過 pub/sub 直接推，只差幾毫秒
- **放行速度翻倍是最意外的發現**：名額要等被放行的人下單才會空出來。polling 時，被放行的人平均晚 0.5 秒才知道，這段時間名額空轉。改用 SSE 後，同樣 `MAX_ACTIVE` 每秒能放行的人數多一倍。也就是說，用 polling 時要把名額開大一點，才能有同樣的消化速度
- **負載**：請求少了一百倍，app CPU 降到三分之一左右。Redis 的工作只少一半，因為每秒還是要算每個人的順位，只是從一人一次變成一批一次
- **代價**：SSE 是長連線。負載平衡器的閒置逾時要夠長（每 15 秒送一行註解保活）、反向代理不能緩衝（回應帶 `X-Accel-Buffering: no`）。瀏覽器在 HTTP/1.1 下同一個網域最多開 6 條連線，同一個人開很多分頁會卡住，用 HTTP/2 就沒有這個限制。所以 polling 保留，當 SSE 被擋時的退路
- **WebSocket 沒做**：排隊狀態只需要 server 單向推給使用者，SSE 已經夠用

**9. 操作頁：兩個分頁要看到同一條隊伍**

加了操作頁（`GET /`）之後，第一版每個分頁只顯示自己加的顧客，所以 :8091 和 :8092 兩個分頁看起來不同步。改成每秒從 `GET /admin/tickets` 拿整場活動的所有顧客，通道只從這份資料畫，兩個分頁就一致了。這個端點是唯讀的、不算心跳，不然旁觀的分頁會幫別人的顧客續命，「關掉分頁就被跳過」就看不到了。

另外，瀏覽器會放慢背景分頁的計時器。放在背景的分頁，顧客的輪詢（心跳）可能因此中斷，輪到時被跳過。這不只是操作頁的問題：真實使用者切到別的分頁時也一樣，所以 `HEARTBEAT_TIMEOUT_MS` 不能設太短，或改用 SSE：計時器降頻不影響已經開著的串流（不過某些省電模式會整個凍結背景分頁，那時串流也會斷）。

### 2026-10-31：Python、Rust 版

**10. 三種語言的對照**

Python（FastAPI）和 Rust（axum）版照同一份 HTTP 介面實作，送同一份 `shared/lua/` 腳本，跑同一支 `verify/run.sh`。三種語言的黑箱驗證都全部通過（搶購 20 項、吞吐量 5 項、polling 3 項、SSE 3 項），超賣和重複扣款都是 0。

| | .NET | Python | Rust |
|---|---|---|---|
| 測試數／行覆蓋率 | 87／91.8% | 129／98% | 122／約 94% |
| polling：放行到知道 p50 | 485 ms | 484 ms | 460 ms |
| SSE：放行到知道 p50／p95 | 3／10 ms | 4／10 ms | 3／6 ms |
| 同樣負載（約 930 次輪詢/秒）的 app CPU | 46.8% | 27.2% | **10.5%** |
| 同樣負載的 app 記憶體（兩台合計） | 263 MB | 117 MB | **46 MB** |
| SSE（約 950 條串流）的 app CPU／記憶體 | 15.4%／218 MB | 9.2%／161 MB | **3.2%／36 MB** |
| 峰值：每秒輪詢（.NET 診斷客戶端，128 條並行連線） | 56,000（p99 4.7 ms） | 13,000（p99 113 ms） | **68,000（p99 3.4 ms）** |
| 峰值時 app CPU（兩台合計）／Redis CPU | 562%／65% | 189%／30% | 280%／65% |

- **正確性一樣，因為規則都在 Lua 裡**。三種語言只差在外殼，所以「不超賣、不重複扣」的保證不會因為換語言而改變
- **延遲由設計決定，不由語言決定**：polling 都是約 0.5 秒，SSE 都是幾毫秒
- **Python 的上限是單核**：每個 uvicorn 程序受 GIL 限制只能用滿一個核心，兩台合計 189% CPU 時就到頂（每台約 6,500 次/秒）。要更多就多開程序或 instance。中等負載下反而比 .NET 省 CPU
- **Rust 最省**：峰值最高，CPU 是 .NET 的一半、記憶體約 1/20。.NET 和 Rust 峰值時都把 Redis 推到 65%，再往上就是 Redis 的天花板
- 吞吐量情境（`verify/scenario.py`）三種語言都是每秒 1～1.7 萬次，那是 Python 壓測端的上限，比不出語言差異；峰值另外用 .NET 單檔客戶端量（診斷用，沒有放進 repo）

**11. 交叉實作和審查找到的問題**

照同一份規格寫第二、三種語言，等於把規格重新檢查一遍：

- **.NET 版的 bug**：`userId`、`SALE_ID` 的正規表達式用 `^…$`，.NET 的 `$` 會接受結尾多一個換行，`"alice\n"` 能通過。Python 版的實作者比對時發現，改用 `\z` 並補測試
- **Rust 版**：沒有調高可開檔案數。.NET 執行環境會自己調，Rust 標準函式庫不會。軟上限 256 時（macOS 預設；Linux 常見 1024），600 條連線只有 247 條接得進來；修正後 600 條全部成功
- **Python 版**：請求本文沒有大小上限（改成 2 MiB，跟 Rust 一樣）；JSON 欄位名稱大小寫敏感，跟 .NET 不一致（改成不分大小寫）；超長的數字設定值啟動失敗時沒有寫出變數名稱

審查也指出三個三種語言共有、這次沒有修的限制，只在特殊情況下出現：

- SSE 剛連上的那一瞬間，如果剛好同時有一次每秒更新，可能先推新狀態、再推一次舊狀態，下一秒就自動更正（不會從終局倒退）
- Redis 長時間連不上時，每秒更新的請求會在佇列裡越積越多，恢復後一次補跑
- Python 和 Rust 版的 pub/sub 連線如果被防火牆或 NAT 無聲切斷，不會發現，放行通知只能靠每秒更新（Redis 在本機時不會發生；.NET 的 StackExchange.Redis 會定期 ping）

## 結論

- 結果：有條件可行（.NET / Python / Rust 結果一致）
- 條件或限制：
  - 一場活動受單一 Redis 執行緒限制，約每秒 9 萬次腳本。輪詢是主要負載，同時排隊的人數上限約為「9 萬 × 輪詢間隔（秒）」
  - 大量同時新建連線是第一個瓶頸，前面要有負載平衡器 / CDN 接住
  - Redis 要高可用，而且 failover 可能遺失最後幾筆寫入（複寫是非同步的），需要對帳機制
  - 各台 instance 的時鐘要同步
  - 狀態推送用 SSE 時，負載平衡器和反向代理要支援長連線、不緩衝；最好走 HTTP/2
  - 用 Python 實作時，每個程序只能用一個核心，要靠多程序或多 instance 撐量；Rust 和 .NET 單台就能把 Redis 推到接近上限
  - 串真實金流時，付款要改成「待付款 → 付款中 → 已付款」，把訂單編號當成金流商的 idempotency key，並且處理「付款中」卡住的訂單（對帳）
- 如果要正式導入，下一步是：
  1. 用 k6 之類的工具、分開機器壓測，取得不受壓測端限制的數字
  2. 實際瀏覽器、HTTP/2、經過負載平衡器時的 SSE 行為（重連、閒置逾時）；polling 退路加上隨機抖動
  3. Redis failover 測試（跟雙機備援 PoC 一起做）
  4. 金流狀態機與對帳
