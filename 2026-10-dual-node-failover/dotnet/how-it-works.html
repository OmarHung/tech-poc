雙機備援機制｜.NET 版運作說明

這頁說明 dotnet/ 裡的程式怎麼運作。裡面有三種雙機備援架構：A. 主備＋資料同步（兩台資料節點怎麼決定誰是主機、一筆寫入怎麼複寫到另一台）、B. 熱熱備援（兩台不通訊、都處理每一筆）、C. 上游指派（兩台不通訊、上游把工作派給其中一台）。框架是 ASP.NET Core 10 Minimal API，gateway 用 YARP 2.3 轉發。

1. 全貌 2. 互動流程圖 3. 一筆資料怎麼流動 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三種架構、六種程式

架構 A：主備＋資料同步

兩台資料節點跑的是同一支程式（Node），誰當主機是執行時決定的。第三個程序 witness 不存資料，只負責仲裁。client 只認得 gateway。

Gateway

127.0.0.1:8100 ・ src/Gateway/

client 的唯一入口。每 100 ms 問兩台節點的 /health，把請求轉給回報 role = primary 的那台（兩台都說是主機時選 epoch 較新的）。

Node a / Node b

127.0.0.1:8101、8102 ・ src/Node/

資料節點。主機接受讀寫，並把每筆寫入同步複寫給備機；備機只接收複寫，同時注意主機是不是還活著。資料存在只能附加的 log 檔。

Witness

127.0.0.1:8103 ・ src/Witness/

第三票。一次只把租約（lease）發給一台，每換一次主機 epoch 就加 1；另外記住「備機是不是同步中」，不同步就不准它升格。只存四個欄位。

架構 B、C：兩台不通訊

兩台 worker 跑同一支程式（Worker），用 MODE 決定是熱熱備援還是被指派。兩台之間沒有任何連線，只認得上游和下游。

Upstream

127.0.0.1:8120 ・ src/Upstream/

工作的來源。架構 B 用它的事件流水帳：只能附加、可以從任何位置重讀。架構 C 用它的任務佇列：每件任務租給一台 worker，租約到期就改派。

Worker a / Worker b

127.0.0.1:8121、8122 ・ src/Worker/

MODE=hothot：讀全部事件、算帳戶餘額、送結果、存檢查點。MODE=dispatch：租任務、定時心跳、做事、寫結果、回報完成。

Sink

127.0.0.1:8123 ・ src/Sink/

下游。以事件或任務編號去重：第一份結果套用（副作用發生），其他的只計數，分成重複、衝突（內容不同）、過期（attempt 比較舊）。

2. 互動流程圖：正常、故障與恢復

架構 A：主備＋資料同步

點按鈕切換情境。藍色虛線是正在發生的流量，紅色是失敗的連線，半透明是這個情境沒用到的部分；外框加粗、底色是主機。下方的數字來自 verify/ 的實測。

正常運作：a 是主機

選主
a 每 0.5 秒向 witness 續約一次（ElectionWorker.RenewAsync()），租約 3 秒。b 一直收到 a 的複寫和心跳，所以不會去搶。
寫入
client → gateway → a。a 寫進自己的 log，再送給 b；b 回覆收到後，a 才回 200 給 client。
witness 記錄
租約在 a，epoch 1，備機同步中（b 可以接手）。
實測
本機寫入 p50 0.94 ms、p99 2.03 ms；兩台之間加 10 ms 單程延遲時 p50 41 ms。

主機崩潰（kill -9）：b 接手

偵測
b 超過 3 秒沒聽到 a（NodeState.TryBeginCandidacy()），向 witness 要租約。a 最後一次續約的租約這時也到期了，b 又是同步中，witness 就把租約交給 b，epoch 變 2。
切換
b 升格，先請 witness 記下「a 不同步」，之後就能單獨確認寫入（Solo）。gateway 下一次輪詢就改送 b。
資料
a 確認過的每一筆，b 都已經收到過（同步複寫的規則），所以沒有遺失。
實測
RTO 3.29 秒（租約 3 秒＋續約間隔＋gateway 輪詢），4,065 筆確認的寫入遺失 0 筆。租約改 1 秒時 RTO 1.14 秒。

舊主機加回來：a 變成備機

重新加入
a 重啟後一律以備機身分啟動，馬上收到 b 的複寫。請求裡的 epoch 2 比 a 記得的 1 新，a 就接受 b 是主機（NodeState.HandleReplicate()）。
對齊資料
b 用 (index, epoch) 跟 a 的 log 比對。a 崩潰前寫進本機、但還沒送到 b 的幾筆（從沒回過 200）會被丟掉，再補上 b 的新資料（ReplicatedLog.AppendFrom()）。
恢復可接手
a 追上後，b 用最新的版本號告訴 witness「備機同步中」，a 就又能接手了。
實測
從啟動到追上 0.39 秒（含程式啟動）。接著再砍 b，a 3.49 秒接手，兩次切換共 6,598 筆寫入遺失 0 筆。

網路分區：a 跟 b、witness 都斷了，但 client 還連得到 a

a 那邊
寫入送不到 b，等 1 秒後想請 witness 允許單獨確認，但 witness 也連不到，只能回 503。2.7 秒後 a 的租約到期，連讀取都停止。
b 那邊
3 秒沒聽到 a，向 witness 要到租約（epoch 2），開始服務。
網路恢復
a 看到 epoch 2，轉成備機，丟掉 8 筆從沒確認過的寫入，0.3 秒內兩邊資料一致。
實測
舊主機在斷線後確認了 0 筆，同時有兩台主機確認寫入 0 次，遺失 0 筆，b 3.28 秒接手。

同樣的分區，但沒有 witness（ARBITER=none，對照組）

a 那邊
只覺得「備機連不到」，沒有人可以問，就自己繼續確認寫入。
b 那邊
3 秒＋1.5 秒的優先權延遲沒聽到 a，就自己升格成 epoch 2（實測 4.80 秒）。現在兩台都是主機。
網路恢復
a 看到 epoch 2 而下台，它在分區期間確認的寫入跟 b 的 log 對不上，整批被丟掉，client 不會收到任何通知。
實測
兩台同時確認寫入 1,376 筆，恢復後 3,344 筆已確認的寫入消失。這就是需要 witness 的原因。

witness 掛掉 6 秒

為什麼沒事
a 有兩種租約：witness 給的，和 b 給的「承諾」（b 每次接受複寫，就承諾 3 秒內不搶主）。只要其中一個有效，a 就能繼續服務，等於 3 票中拿到 2 票。
寫入
照常同步複寫到 b，不需要 witness 參與。
witness 回來
從檔案讀回狀態（租約在 a），a 下一次續約就恢復。
實測
5,481 筆寫入 0 失敗，最長空窗 0.02 秒，a 從沒下台。

備機落後時主機又掛：寧可停機也不丟資料

第一步
b 先掛。a 的寫入等 b 等了 1 秒，請 witness 記下「b 不同步」後單獨確認（Solo），共 1,572 筆只有 a 有。
第二步
a 也掛了，接著 b 先回來。b 向 witness 要租約，witness 拒絕：「b 可能缺少已確認的寫入，等 a 回來」。gateway 找不到主機，回 503。
a 回來
witness 把租約還給 a（同一個 epoch），a 繼續服務，b 再從 a 追上。
實測
停機 11.7 秒（等 a 回來），遺失 0 筆。代價是可用性：要強制讓 b 接手只能人工介入並接受遺失。

架構 B、C：兩台不通訊

同一張圖，上游是事件流水帳（B）或任務佇列（C）。兩台 worker 之間沒有線。

架構 B 正常運作：兩台都做每一筆

上游
事件流水帳，只能附加，可以從任何位置重讀（EventLog.ReadAsync()）。
worker
各自從自己的位置往後讀，依序更新帳戶餘額，每筆送一個結果（event-<編號> → 帳戶:餘額）。一批送完才存檢查點。
下游
同一個事件收到兩份，第一份套用、第二份記成重複（ResultStore.Record()）。
實測
1,748 筆事件下游收到 3,039 份：沒有去重的話，副作用會多發生 1,291 次。

架構 B：a 被砍

發生什麼
什麼都不用做。b 本來就在處理每一筆，沒有偵測、沒有切換。
實測
下游最長 24 ms 沒有新結果，跟平常一樣；1,748 筆全部有結果、全部正確。

架構 B：a 重啟，從檢查點補讀

補讀
a 讀回 checkpoint.json（讀到哪、各帳戶餘額），從那裡往後讀，停機期間的事件一筆不漏。
重送
被砍時已經送出、但還沒存進檢查點的那批會再送一次，下游當成重複忽略。
實測
停機 3 秒間的約 600 筆，從下重啟指令算起 0.47 秒補完（含程式啟動）；之後再砍 b，a 獨自繼續，最後的餘額跟正確答案完全一樣。網路斷 3 秒的情況，恢復後 0.12 秒補完。

架構 B 的錯誤做法：重啟時直接從最新的事件開始（START_FROM=latest）

發生什麼
a 的餘額少了停機期間的事件，之後每一筆受影響帳戶的結果都跟 b 不同。下游先收到誰的就用誰的。
實測
不一致 473 筆；b 掛掉之後，下游套用了 505 筆錯誤結果。另一種錯是結果帶本機時鐘（DETERMINISTIC=false）：只有 4% 不一致，偶發，最難發現。

架構 C 正常運作：上游把每件任務租給一台

租任務
worker 向上游要任務（TaskQueue.LeaseAsync()），拿到 {id, input, attempt, ttlMs}，租約 2 秒。
做事
每 1/3 個租約送一次心跳延長租約，做完先寫結果到下游，再向上游回報完成（DispatchWorker.RunAsync()）。
實測
每秒 5 件、每件 300 ms，兩台輪流接，任務延遲 p50 約 1 秒。每件做 3 秒（比租約長）時靠心跳延長，0 次被誤判改派。

架構 C：a 做到一半被砍

發生什麼
a 不再心跳，租約到期後上游把那件任務放回佇列最前面（TaskQueue.ExpireOverdue()），attempt 變 2，b 接手。其他任務不受影響。
實測
那件任務 2.34 秒後完成（租約 2 秒＋做事 0.3 秒），51 件全部正確。

架構 C：a 被凍結 4 秒（長時間 GC、VM 暫停）

發生什麼
任務改派給 b。a 恢復後還以為任務是自己的，但寫結果前先檢查自己的租約（LeaseTracker.IsValid）：從送出請求的時間起算、提早 10% 結束，早就過期了，於是放棄。
實測
有檢查時 0 次重複寫入。不檢查的對照組（LEASE_CHECK=off）多寫 1 次；這次剛好 b 的結果先到，下游才認得出那是過期的 attempt。
還剩的空窗
寫結果的逾時不超過剩下的租約，但如果剛好在「檢查完、請求已經送出」之後才被凍結，還是會晚到。所以下游的去重不能省。

架構 C：a 連不到下游，但心跳照常送到上游

問題
心跳一直成功，租約一直被延長，上游以為 a 好好的，另一台永遠接不到這件任務。心跳只證明 worker 活著，不證明它做得完。
解法
a 寫不出結果超過一個租約就放手（DispatchWorker.DeliverAsync()），心跳跟著停，租約到期後改派給 b。
實測
那件任務 4.48 秒後由 b 完成：a 先試 2 秒，租約再 2 秒到期。放手時如果主動通知上游，還能再快約 2 秒。

架構 C：a 做完、寫了結果，但回報不出去

發生什麼
a 到上游的連線斷了。上游收不到心跳和完成回報，租約到期後改派給 b，b 再做一次。
為什麼避免不了
先寫結果、再回報完成，兩步之間任何中斷都會這樣：這就是 at-least-once。所以下游一定要以任務編號去重。
實測
那件任務下游收到兩份，只套用一份。

3. 一筆資料怎麼流動

架構 A：一筆寫入怎麼複寫到另一台

以正常運作時的 PUT /kv/order-1 {"value":"paid"} 為例（a 是主機、同步複寫），從進門到回 200 經過這些程式碼：

  1. Gateway 轉給目前的主機
    src/Gateway/GatewayHosting.cs 的 MapGateway()、PrimaryTracker.cs 的 Current

    PrimaryTracker 背景每 100 ms 輪詢兩台的 /health，Choose() 挑出回報 primary 且 epoch 最大的。轉發交給 YARP 的 IHttpForwarder.SendAsync()；節點回 503 或連不上時立刻再輪詢一次（Nudge()）。

  2. 主機檢查自己的租約，寫進本機 log
    NodeHosting.cs 的 PUT /kv/{key} → Kv/KvService.cs 的 PutAsync() → Cluster/NodeState.cs 的 AppendAsPrimary()

    在同一把鎖裡確認「我是主機而且租約還有效」，再附加到 log。下台（step down）也要拿這把鎖，所以不可能在下台之後還寫進去。

    public LogEntry AppendAsPrimary(string key, string value, out PrimaryTerm term)
{
    lock (_gate)
    {
        term = ServingTermLocked() ?? throw NotPrimary();
        var entry = Log.Append(term.Epoch, key, value);
        term.NotifyAppended();
        return entry;
    }
}

    Log.Append()（Storage/ReplicatedLog.cs）給它下一個 index 和目前的 epoch，由 LogFile.Append() 寫成一行 JSON，透過沒有緩衝的 FileStream 直接交給作業系統，程序被砍掉也不會不見。寫入失敗時會把寫到一半的資料截掉；啟動時也會丟掉最後一行寫到一半的殘骸、補上少掉的換行，下一筆才不會黏在半行後面。

  3. 複寫迴圈被叫醒，送出這一批
    Cluster/ReplicationWorker.cs 的 ReplicateTermAsync()

    NotifyAppended() 叫醒等待中的複寫迴圈。它從 nextIndex 讀最多 256 筆，連同前一筆的 (index, epoch) 送到 b 的 POST /internal/replicate。一次只送一批，回來才送下一批；沒有新資料時每 0.5 秒送一次空的當心跳。

  4. 備機檢查 epoch 和前一筆，寫進自己的 log
    b 的 NodeState.HandleReplicate() → ReplicatedLog.AppendFrom()

    epoch 比自己知道的舊 → 拒絕（被換掉的舊主機就是這樣被擋下的）。前一筆對不上 → 回 mismatch，主機往回找。對得上 → 附加，並記下「剛聽到主機」：這等於承諾 3 秒內不搶主，回覆裡的 promiseMs 就是這個承諾。

  5. 主機收到回覆：延長租約、推進進度
    ReplicationWorker.ReplicateTermAsync() 後半 → PrimaryTerm.RecordReplicated()
    // The standby accepted this node as primary and promised not to seek the lease for a while.
state.ExtendPeerLease(term, sentAt + TimeSpan.FromMilliseconds(reply.PromiseMs) - config.LeaseSafetyMargin);
// ……
nextIndex = reply.MatchIndex + 1;
if (term.RecordReplicated(reply.MatchIndex) && inSyncCall.IsCompleted)
{
    inSyncCall = term.TryMarkInSyncAsync(ct);
}

    租約從「送出請求的時間」起算，再提早 10% 結束，所以主機一定比備機先放手。

  6. 等待中的寫入確認已經安全，回 200
    KvService.PutAsync() 等在 PrimaryTerm.WaitDurableAsync()

    這筆的 index 小於等於 b 已確認的 MatchIndex，就可以回覆。如果 b 超過 1 秒都沒確認，改請 witness 同意「單獨確認」（TryGoSoloAsync()）；witness 同意後 b 就不能升格，這時只存在 a 的寫入也算安全了。

    看 WaitDurableAsync() 的程式碼 
    public async Task WaitDurableAsync(long index, TimeSpan timeout, MonotonicClock clock, CancellationToken ct)
{
    var deadline = clock.Now + timeout;
    while (true)
    {
        Task progress;
        lock (_gate)
        {
            if (index <= _matchIndex || _peerState == PeerState.Solo)
            {
                return;
            }
            if (_ended.IsCancellationRequested)
            {
                throw new UnavailableException("lost the primary role before the write reached the standby");
            }
            progress = _progress.Task;
        }
        var remaining = deadline - clock.Now;
        if (remaining <= TimeSpan.Zero)
        {
            if (!await TryGoSoloAsync())
            {
                throw new UnavailableException("standby unreachable and the witness did not allow going on alone");
            }
            continue;
        }
        try
        {
            await progress.WaitAsync(remaining, clock.Time, ct);
        }
        catch (TimeoutException)
        {
            // Deadline reached; the loop asks the witness.
        }
    }
}

架構 B：一筆事件怎麼被兩台各自處理

  1. verify 把事件加進上游的流水帳
    POST /events → src/Upstream/EventLog.cs 的 Append()

    事件拿到下一個編號，叫醒所有正在等新事件的讀取。流水帳只能附加，不會刪。

  2. 兩台 worker 各自讀到它
    src/Worker/HotHot/HotHotWorker.cs 的 ExecuteAsync() → WorkClient.ReadEventsAsync()

    每台用自己的位置讀（GET /events?after=…&waitMs=500），沒有新事件時上游會等一下再回。兩台不知道彼此存在。

  3. 更新餘額、送出結果，整批送完才存檢查點
    Ledger.Apply()、DeliverAsync()、Save()
    foreach (var logged in page.Events)
{
    var (next, balance) = ledger.Apply(logged);
    await DeliverAsync(new ResultRecord($"event-{logged.Seq}", config.WorkerId, 0, Format(logged, balance)), stoppingToken);
    ledger = next;
}
if (page.Events.Count > 0)
{
    // After delivering: a crash before this line means re-sending the batch, never skipping it.
    Save(ledger);
    status.Ledger = ledger;
}

    Ledger 只依事件和順序計算，兩台看到同樣的事件就算出同樣的餘額。送結果會一直重試到下游回應為止。

  4. 下游去重
    src/Sink/ResultStore.cs 的 Record()

    第一份套用（201），內容一樣的第二份是重複（200），內容不同的是衝突（409，保留第一份並計數）。

架構 C：一件任務怎麼被指派

  1. worker 租到任務
    src/Upstream/TaskQueue.cs 的 LeaseAsync()

    先把到期的租約放回佇列最前面，再把最前面的任務交給這台 worker：attempt 加 1，租約從現在起 2 秒。佇列空的話最多等 0.5 秒。

  2. 邊做邊心跳，寫結果前先檢查租約
    src/Worker/Dispatch/DispatchWorker.cs 的 RunAsync()、HeartbeatAsync()；LeaseTracker.cs
    await Task.Delay(config.WorkTime, time, ct); // the work itself
if (!StillHolds(lease, tracker, "before writing the result"))
{
    return;
}
status.TaskPhase(lease.Id, "delivering");
var result = new ResultRecord($"task-{lease.Id}", config.WorkerId, lease.Attempt, Compute(lease.Input));
if (!await DeliverAsync(lease, tracker, result, ct))
{
    return;
}
status.TaskPhase(lease.Id, "completing");
var completed = await CompleteAsync(lease, tracker, ct);

    worker 自己算租約：從送出請求的時間起算，提早 10% 結束，所以一定比上游先放手。心跳用固定間隔（PeriodicTimer），每次最多等一個間隔，成功就延長；上游回 409 就立刻作廢。寫結果的逾時不超過剩下的租約，寫不出來超過一個租約就放手。

  3. 先寫結果，再回報完成
    WorkClient.DeliverAsync() → ResultStore.Record()；WorkClient.CompleteAsync() → TaskQueue.Complete()

    回報時如果租約已經不是自己的（被改派了），上游回 409 並記成過期的完成回報。兩步之間斷掉，任務會被改派再做一次，下游以任務編號去重。

架構 B、C 的狀況在哪裡被處理

狀況在哪裡結果
熱熱 worker 被砍另一台本來就在做；重啟後 HotHotWorker 讀檢查點補讀不中斷、不漏；重送的結果被下游當成重複
兩台算出不同的結果ResultStore.Record()409 衝突，保留第一份並計數

指派的 worker 連不到下游DispatchWorker.DeliverAsync()超過一個租約就放手；心跳停止，租約到期後改派
上游重啟、事件從頭編號HotHotWorker.ExecuteAsync()發現上游比自己的進度短就停下來報錯，不送錯的結果

4. 啟動時發生什麼

Witness

src/Witness/Program.cs：WitnessConfig.FromEnvironment() 讀 PORT、DATA_DIR、NODES、LEASE_TTL_MS → AddWitness() 註冊 LeaseTable。LeaseTable 從 witness.json 讀回上次的狀態；如果之前有人持有租約，就當作它還持有一個完整的 TTL，因為重啟期間那台可能還在服務。

Node

src/Node/Program.cs：NodeConfig.FromEnvironment()（設定互相矛盾會直接啟動失敗，例如租約短於 3 次續約）→ AddNode()：開啟 log.jsonl（最後一行寫到一半就丟掉）、建立 NodeState（從 epoch.json 讀回 epoch），啟動 ElectionWorker 和 ReplicationWorker。一律以備機身分啟動，先等一個 TTL 才可能去搶主。

Gateway

src/Gateway/Program.cs：GatewayConfig.FromEnvironment() 讀 PORT、NODE_URLS、POLL_INTERVAL_MS → AddGateway() 註冊 YARP 和 PrimaryTracker（背景服務）→ MapGateway()。剛啟動還沒輪詢到主機時，所有請求回 503。

Upstream

src/Upstream/Program.cs：UpstreamConfig.FromEnvironment() 讀 PORT、TASK_LEASE_TTL_MS → AddUpstream() 註冊 EventLog、TaskQueue 和背景的 LeaseReaper。資料只在記憶體。

Worker

src/Worker/Program.cs：WorkerConfig.FromEnvironment() 讀 MODE 等設定 → AddWorker() 依模式只註冊 HotHotWorker 或 DispatchWorker 其中一個背景服務。熱熱模式啟動時讀回 checkpoint.json；START_FROM=latest 時改成跳到上游最新的事件。

Sink

src/Sink/Program.cs：讀 PORT → AddSink() 註冊 ResultStore。資料只在記憶體。

「重啟後先等一個 TTL」很關鍵：備機重啟前可能剛承諾過主機「3 秒內不搶」，重啟後記憶體裡的承諾不見了，所以把啟動當成「剛聽到主機」來處理。

// src/Node/Cluster/NodeState.cs 的建構子
_lastHeardFromPrimary = Clock.Now;

public bool TryBeginCandidacy()
{
    lock (_gate)
    {
        if (_term is not null || _candidate || Clock.Now - _lastHeardFromPrimary < _config.LeaseTtl + _config.ElectionDelay)
        {
            return false;
        }
        _candidate = true;
        return true;
    }
}

5. 關鍵設計

witness 只在三種情況下換主機

現任主機續約永遠成功；別人要拿租約，必須「租約已到期」而且「自己是同步中的備機」。換手時 epoch 加 1，成為 fencing token。

// src/Witness/LeaseTable.cs
public LeaseReply Acquire(string? node)
{
    RequireKnown(node);
    lock (_gate)
    {
        var now = _clock.Now;
        if (_state.Holder == node)
        {
            // Also after expiry: nobody else took over in between, so the holder still has the newest data.
            _expiresAt = now + _config.LeaseTtl;
            return Reply(granted: true, reason: null);
        }
        if (_state.Holder is not null && now < _expiresAt)
        {
            return Reply(granted: false, $"lease held by {_state.Holder}");
        }
        if (_state.Holder is not null && !_state.StandbyInSync)
        {
            return Reply(granted: false, $"{node} may be missing acknowledged writes; waiting for {_state.Holder} to return");
        }
        // …… 換手：epoch + 1，新的備機（舊主機）先標成不同步
    }
}

其他

設計為什麼在哪裡
兩種租約：witness 的，和備機的承諾只要拿到 3 票中的 2 票就能服務，witness 單獨掛掉或備機單獨掛掉都不會停NodeState.LeaseUntilLocked()、ExtendPeerLease()
備機在向 witness 要租約時拒絕所有複寫否則它可能一邊被 witness 授權，一邊又承諾舊主機「不搶主」，兩台會同時有權服務NodeState.HandleReplicate() 的 _candidate
witness 的同步狀態帶版本號逾時放棄的 HTTP 請求還是可能晚到。「備機同步中」必須附上最新版本才會被接受，晚到的舊訊息蓋不掉後來的「備機不同步」LeaseTable.SetStandbyInSync()、PrimaryTerm.TryMarkInSyncAsync()
對 witness 的呼叫一次只送一個同一個任期內的兩個報告不會互相超車PrimaryTerm 的 _witnessCalls
Raft 式 log 比對用 (index, epoch) 認出分歧的資料；只截掉比目前主機舊的 epoch，所以晚到的舊心跳不會誤刪新資料ReplicatedLog.AppendFrom()
讀取也等到安全才回不讓 client 看到「切換後會消失」的值KvService.GetAsync()
單調時鐘租約不會因為系統時間被調整而變長或變短src/Shared/MonotonicClock.cs
沒有 witness 的對照組同一份程式，ARBITER=none 時備機 3 秒沒聽到主機就自己升格，用來實測腦裂的代價ElectionWorker.TickWithoutWitness()、NoArbiter
B：先送結果、再存檢查點被砍時最多重送一批，絕不會跳過；重送的部分由下游去重HotHotWorker.ExecuteAsync()
B：處理是決定性的結果只依事件和順序計算，兩台才會逐字相同；DETERMINISTIC=false 是反例Ledger.Apply()、HotHotWorker.Format()
C：worker 自己算租約跟架構 A 的主機一樣，從送出請求的時間起算、提早 10% 結束，所以一定比上游先放手LeaseTracker
C：改派的任務排最前面它已經等最久了TaskQueue.ExpireLocked()
C：心跳固定間隔、每次有上限一次卡住的心跳不會把下一次推到租約之後DispatchWorker.HeartbeatAsync()
C：做不完就放手心跳只證明活著，不證明做得完；連不到下游還一直心跳，任務會卡住DispatchWorker.DeliverAsync()
B、C：下游以編號去重重複無法完全避免（at-least-once），只能讓它無害；內容不同的重複當成衝突記下來ResultStore.Record()

還沒處理：斷電（log 只寫進作業系統，沒有 fsync）、gateway 本身的備援、各程序之間的身分驗證。複寫一次只送一批，所以同步寫入要 1 到 2 個網路來回。
