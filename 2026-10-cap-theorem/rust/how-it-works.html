CAP 定理範例｜Rust 版運作說明

這頁說明 rust/ 裡的程式怎麼運作：怎麼在單一程序裡模擬 3 台節點和網路分區，CP 和 AP 兩種模式在分區、恢復時各發生什麼事，以及 AP 怎麼用 version vector 或 CRDT 合併才不會丟資料。Rust edition 2024（本機 rustc 1.98），只用標準函式庫（std::collections::{BTreeMap, BTreeSet}），沒有任何 crate 相依，測試用內建的 cargo test。

1. 全貌 2. 互動流程圖 3. 一筆寫入的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：兩個模組、一支示範程式、兩組測試

這份實作沒有真的網路，也不開任何 port。3 台節點 A、B、C 只是記憶體裡的資料，「網路分區」用「節點分組」表示：同一組內可以互相連線，跨組連不到。這樣每次跑的結果都一樣，不會被真實網路的抖動干擾。

src/lib.rs

模擬本體 ・ crate cap_theorem，被 main.rs 和測試使用

叢集 Cluster 和五個操作：Cluster::new() 建立、partition() 切斷網路、write() 寫入、read() 讀取、heal() 恢復並合併。方法都只拿 &self、回傳新的叢集，舊的不變。

src/merge.rs

AP 不丟資料的合併方式 ・ 模組 cap_theorem::merge

version vector：compare() 判斷兩個版本誰先誰後或並行，reconcile() 保留並行的兄弟版本，next_version() 寫入新版本取代它們。CRDT：G-Counter 的 add()、merge_counters()、total()。在 lib.rs 用 pub mod merge; 掛上。

src/main.rs

示範程式 ・ ./run.sh demo

依序跑四段：3 台 CP、3 台 AP、只有 2 台的 CP、AP 不丟資料的兩種合併方式，把每一步的結果印出來。三種語言版本的輸出逐字相同。

tests/cap.rs、tests/merge.rs

12 ＋ 10 個整合測試 ・ ./run.sh test

README 的每一條成功標準都對應一個測試，包括 version vector 保留並行寫入、G-Counter 合併不丟累加。「分組不合法」的三種情況和 compare() 的 5 個案例都在同一個測試裡用迴圈跑，所以總數 22 個比 Python、.NET 少，測的情境其實一樣。

2. 互動流程圖：分區前、分區中、恢復後

點下面的按鈕切換情境。藍色虛線是寫入或複製實際走的路徑，紅色是被擋下的路徑，紅色長虛線是網路斷掉的位置。節點方框裡是那一台目前 x 的值。情境順序跟 src/main.rs 一樣。

正常：沒有分區（CP、AP 都一樣）

呼叫
cluster.write("A", "x", "1")
結果
Ok(新的 Cluster)。A、B、C 都有 x=1（時間戳 1）。
為什麼
沒有分區時只有一個分組，3 台都連得到。write() 把新版本放進同組每一台的 Store。這時 CP 和 AP 的行為完全一樣，差別只在網路斷掉之後。
模擬的簡化
同組內的複製是瞬間完成的。真實系統複製要花時間，AP 系統通常是非同步複製。
對應測試
write_returns_new_cluster_without_changing_the_original

CP：分區中，少數派那側停止服務

呼叫
cluster.partition(&[&["A", "B"], &["C"]]) → cluster.write("A", "x", "2") → cluster.write("C", "x", "3") → cluster.read("C", "x")
結果
A 寫入回 Ok，複製到 B。C 的寫入和讀取都回 Err(CapError::NoQuorum { reachable: 1, quorum: 2 })，印出來是「只連得到 1 台，需要 2 台才過半」。
為什麼
require_quorum() 比較「同組有幾台」和 quorum()（3 台要 2 台）。{A, B} 有 2 台，過半；{C} 只有 1 台，不過半。
代價
C 那側完全不能用。但沒有人讀到舊資料，兩邊的資料也沒有分歧。
對應測試
cp_minority_side_rejects_writes_and_reads_during_partition、cp_majority_side_keeps_serving_during_partition

CP：恢復後，C 追上進度，沒有遺失

呼叫
cluster.heal()，回傳 (Cluster, Vec<Version>)
結果
三台都是 x=2，回傳的 lost 是空的 Vec。
為什麼
合併時 x 有兩個版本：A、B 上的 x=2（時間戳 2）和 C 上的 x=1（時間戳 1）。x=2 比較新，勝出。x=1 在分區前（partitioned_at = Some(1)）就存在，輸掉只算「落後」，不算遺失。
對應測試
cp_heal_loses_no_acknowledged_write

AP：分區中，兩邊照常服務，但資料分歧

呼叫
跟 CP 一樣：cluster.write("A", "x", "2") → cluster.write("C", "x", "3")
結果
兩筆寫入都回 Ok。cluster.read("A", "x") 回 Ok(Some("2"))，cluster.read("C", "x") 回 Ok(Some("3"))。
為什麼
AP 模式下 require_quorum() 的 Mode::Ap => Ok(()) 直接放行。寫入只會複製給同組的節點，所以兩組各有各的值。
代價
同一個 key 在兩邊的值不一樣。在 C 寫入之前讀 C，會讀到分區前的舊值 Ok(Some("1"))。
對應測試
ap_both_sides_accept_writes_during_partition、ap_reads_diverge_during_partition、ap_minority_side_reads_stale_value_during_partition

AP：恢復後，last-write-wins 默默丟掉一筆已確認的寫入

呼叫
cluster.heal()
結果
三台都是 x=3。回傳的 lost 裡有 A 寫入的 Version { value: "2", timestamp: 2, origin: "A" }。
為什麼
x=2（時間戳 2）和 x=3（時間戳 3）都是分區期間寫的，last-write-wins 選時間戳大的 x=3。x=2 的時間戳 2 大於 partitioned_at（1），所以算遺失。
代價
client1 早就收到「寫入成功」，之後 x=2 被蓋掉，沒有任何通知。
對應測試
ap_heal_with_last_write_wins_drops_an_acknowledged_write

延伸：只有 2 台的 CP，分區時整個服務停擺

呼叫
Cluster::new(Mode::Cp, &["A", "B"]).partition(&[&["A"], &["B"]])? → A、B 各寫一次
結果
兩邊都回 Err(CapError::NoQuorum { reachable: 1, quorum: 2 })：只連得到 1 台，需要 2 台才過半。
為什麼
quorum() 是 self.nodes.len() / 2 + 1，2 台需要 2 台。網路一斷，哪一邊都湊不到。
意義
雙機備援如果選 CP，就要加一個第三方仲裁（witness）湊出第三票，見雙機備援 PoC。
對應測試
cp_with_two_nodes_cannot_serve_on_either_side_of_a_partition

延伸：AP 恢復時改用 version vector，並行寫入兩個都留下

呼叫
src/merge.rs：merge::next_version(std::slice::from_ref(&x1), "A", "2")、merge::next_version(std::slice::from_ref(&x1), "C", "3") → merge::reconcile(&[x2.clone(), x2, x3])
結果
兩個版本都保留：x=2（時鐘 {A:2}）和 x=3（時鐘 {A:1, C:1}）。回傳的 Vec<Sibling> 有兩個兄弟版本，讀 x 會拿到 2、3。
為什麼
每個版本記下「各節點寫過幾次」。merge::compare() 發現 {A:2} 在 A 那格比較大、{A:1, C:1} 在 C 那格比較大，兩邊互相沒看過對方，回傳 Order::Concurrent，誰都不能蓋掉誰。
接下來
應用層讀到兩個值，自己決定怎麼合併（例如合成 x=5），再用 merge::next_version(&siblings, "A", "5") 寫回。新時鐘 {A:3, C:1} 涵蓋兩個兄弟版本，下一次 merge::reconcile() 就只剩它。
代價
不會默默丟資料，但衝突沒有消失，只是交給應用層處理。Dynamo、Riak 是這種做法。
對應測試
reconcile_keeps_both_concurrent_writes、resolved_version_replaces_the_siblings_after_another_reconcile（tests/merge.rs）

延伸：AP 恢復時改用 CRDT 計數器（G-Counter），自動合併

情境
x 是一個計數器（例如按讚數）。分區期間 A 那側 +2、C 那側 +3。
呼叫
merge::add(&GCounter::new(), "A", 2)?、merge::add(&GCounter::new(), "C", 3)? → merge::merge_counters(&[&on_a, &on_c])
結果
{A:2, C:3}，merge::total() 是 5。如果把總數當一般值、用 Cluster::heal() 的 last-write-wins 合併（src/main.rs 的 last_write_wins_total()），結果是 3，A 的 +2 不見了。
為什麼
每台只累加自己那一格，合併時每格取最大值，總數是各格相加。合併的順序、次數都不影響結果，所以不用人決定，也不會丟。
限制
只適用於能設計成 CRDT 的資料型別（計數器、集合等）。「把 x 設成某個值」這種覆寫操作沒辦法自動合併，還是要用 version vector。
對應測試
counter_increments_on_both_sides_merge_without_loss、last_write_wins_on_a_counter_total_loses_an_increment（tests/merge.rs）

3. 一筆寫入的旅程

以分區中「client1 在 A 寫 x=2」為例，也就是 src/main.rs 裡的 write_and_show(cluster, "A", "2", "分區")。從呼叫到印出結果，經過這些程式碼：

  1. 示範程式發出寫入
    src/main.rs 的 write_and_show()

    呼叫 cluster.write()。Ok 時拿回新的叢集往下傳；Err 時印出原因，把原本那個 cluster 原樣傳回去。寫入失敗不會改到任何東西，所以沿用舊的就好。

    fn write_and_show(cluster: Cluster, node: &str, value: &str, stage: &str) -> Cluster {
    let label = format!("[{stage}] {node} 寫 x={value}");
    match cluster.write(node, "x", value) {
        Ok(next) => {
            println!("  {label} → 成功");
            next
        }
        Err(error) => {
            println!("  {label} → 拒絕：{error}");
            cluster
        }
    }
}
  2. 找出 A 連得到哪些節點
    src/lib.rs 的 Cluster::write() → reachable()

    在 self.groups 裡找出 A 所在的分組，這裡是 {"A", "B"} 這個 BTreeSet。節點名稱不存在時回 Err(CapError::UnknownNode)，write() 用 ? 直接往上傳。

        fn reachable(&self, node: &str) -> Result<&BTreeSet<String>, CapError> {
        self.groups
            .iter()
            .find(|group| group.contains(node))
            .ok_or_else(|| CapError::UnknownNode(node.to_owned()))
    }
  3. CP 檢查有沒有過半，AP 直接放行
    src/lib.rs 的 require_quorum()、quorum()

    CP 模式下，{A, B} 有 2 台，quorum() 是 2，過半，回 Ok(())。如果是 C 寫入，{C} 只有 1 台，這裡回 Err(CapError::NoQuorum { .. })，write() 用 ? 提早結束，呼叫端手上的叢集完全沒被動過。match 把三種情況都列出來，沒有用 _ 萬用分支。CP 和 AP 的差別只有這一個判斷。

        fn require_quorum(&self, peers: &BTreeSet<String>) -> Result<(), CapError> {
        match self.mode {
            Mode::Ap => Ok(()),
            Mode::Cp if peers.len() >= self.quorum() => Ok(()),
            Mode::Cp => Err(CapError::NoQuorum {
                reachable: peers.len(),
                quorum: self.quorum(),
            }),
        }
    }
  4. 產生新版本，複製給同組節點
    src/lib.rs 的 Cluster::write() 後半、with_entry()

    時鐘加 1，建立 Version { value: "2", timestamp: 2, origin: "A" }。同組的 A、B 各拿到 with_entry() 做出來的新 Store；C 在另一組，拿到原本的複本，所以 C 還是 x=1。最後用 Self { stores, clock, ..self.clone() } 組出新的 Cluster，&self 指向的舊叢集不受影響。

            let clock = self.clock + 1;
        let version = Version {
            value: value.to_owned(),
            timestamp: clock,
            origin: node.to_owned(),
        };
        let stores = self
            .stores
            .iter()
            .map(|(name, store)| {
                let store = if peers.contains(name) {
                    with_entry(store, key, &version)
                } else {
                    store.clone()
                };
                (name.clone(), store)
            })
            .collect();
        Ok(Self {
            stores,
            clock,
            ..self.clone()
        })

/// 回傳多了這一筆的新 Store，原本的不變
fn with_entry(store: &Store, key: &str, version: &Version) -> Store {
    let mut updated = store.clone();
    updated.insert(key.to_owned(), version.clone());
    updated
}
  5. 印出結果
    src/main.rs 的 write_and_show()

    印出 [分區] A 寫 x=2 → 成功。被拒絕時印出 拒絕：加上 CapError 的 Display 訊息。

  6. 網路恢復時合併
    src/lib.rs 的 Cluster::heal()、versions_by_time()

    把每個 key 在各節點上的不同版本收集起來，依時間戳由舊到新排好，最後一個勝出，寫回每一台。其他輸家如果是分區期間寫入的（時間戳大於 partitioned_at），就放進回傳的 Vec<Version>。

    看 heal() 和 versions_by_time() 的程式碼 
        pub fn heal(&self) -> (Self, Vec<Version>) {
        let keys: BTreeSet<&String> = self.stores.values().flat_map(Store::keys).collect();
        // 每個 key 在各節點上的不同版本，依時間由舊到新排好；最後一個就是 LWW 的贏家
        let candidates: Vec<(&String, Vec<&Version>)> = keys
            .into_iter()
            .map(|key| (key, versions_by_time(self.stores.values(), key)))
            .collect();
        let merged: Store = candidates
            .iter()
            .filter_map(|(key, versions)| {
                versions
                    .last()
                    .map(|winner| ((*key).clone(), (*winner).clone()))
            })
            .collect();

        // 分區前就存在的舊版本輸掉只是「落後」，分區期間寫入的版本輸掉才是「遺失」。
        let since = self.partitioned_at.unwrap_or(self.clock);
        let lost = candidates
            .iter()
            .flat_map(|(_, versions)| &versions[..versions.len().saturating_sub(1)])
            .filter(|version| version.timestamp > since)
            .map(|version| (*version).clone())
            .collect();

        let healed = Self {
            stores: self
                .nodes
                .iter()
                .map(|node| (node.clone(), merged.clone()))
                .collect(),
            groups: vec![self.nodes.iter().cloned().collect()],
            partitioned_at: None,
            ..self.clone()
        };
        (healed, lost)
    }

fn versions_by_time<'a>(stores: impl Iterator<Item = &'a Store>, key: &str) -> Vec<&'a Version> {
    let mut versions: Vec<&Version> = stores.filter_map(|store| store.get(key)).collect();
    versions.sort_by_key(|version| version.timestamp);
    versions.dedup();
    versions
}

每種結果在哪一步決定

狀況在哪裡決定結果
節點名稱不存在第 2 步 reachable()Err(CapError::UnknownNode("Z"))
CP，連得到的節點沒過半第 3 步 require_quorum()Err(CapError::NoQuorum { .. })，叢集不變
AP，分區中第 3 步 Mode::Ap => Ok(()) 直接放行成功，但另一組看不到這筆寫入
分組沒有剛好涵蓋每個節點一次（漏掉、重複、不存在）partition()Err(CapError::InvalidPartition)
分區期間的寫入在恢復時輸給較新的版本第 6 步 heal()出現在回傳的 Vec<Version> 裡

模擬刻意簡化了兩件事：同組內的複製是瞬間完成的，以及時間戳來自一個全域邏輯時鐘。真實的 AP 系統常用各台機器自己的時間做 last-write-wins，時間不準時，「誰被丟掉」會更難預測。

4. 啟動時發生什麼

src/main.rs

main() 回傳 Result<(), Box<dyn Error>>，依序呼叫 run_three_nodes(Mode::Cp)?、run_three_nodes(Mode::Ap)?、run_two_nodes()?、run_lossless_merges()。每段都從新的叢集或空的時鐘開始，互不影響。回傳型別用 Box<dyn Error>，是因為最後一段可能遇到 CapError，也可能遇到 MergeError。沒有設定檔，也不讀環境變數。

Cluster::new()

src/lib.rs：每個節點一個空的 Store，只有一個分組（全部連通），clock: 0、partitioned_at: None。3 台的情境傳 &["A", "B", "C"]，2 台的情境傳 &["A", "B"]。

tests/cap.rs、tests/merge.rs

cargo test 把每個檔案各編成一個獨立的測試執行檔，只能用 crate 公開的 API。cap.rs 12 個、merge.rs 10 個 #[test]，共 22 個。共用情境由 partitioned()、written_on_both_sides() 和 merge.rs 開頭的 x1()、x2_on_a()、x3_on_c() 組出來，values_on_every_node() 收集每台讀到的值。

fn main() -> Result<(), Box<dyn Error>> {
    run_three_nodes(Mode::Cp)?;
    run_three_nodes(Mode::Ap)?;
    run_two_nodes()?;
    run_lossless_merges()
}

5. 關鍵設計

叢集不可變：每一步都是一張快照

Cluster 的欄位全是私有的，對外只有方法。改變狀態的方法（partition()、write()、heal()）都只拿 &self，用 Self { .., ..self.clone() } 回傳新的 Self。寫入失敗時回的是 Err，呼叫端手上的叢集本來就沒被動過。測試也因此可以同時拿「寫入前」和「寫入後」的叢集比較。

#[derive(Debug, Clone)]
pub struct Cluster {
    mode: Mode,
    nodes: Vec<String>,
    stores: BTreeMap<String, Store>,
    /// 目前連得到彼此的節點分組
    groups: Vec<BTreeSet<String>>,
    clock: u64,
    /// 分區發生時的時鐘；沒有分區時為 None
    partitioned_at: Option<u64>,
}

錯誤是 enum，訊息自己實作 Display

三種失敗都放在 CapError 裡，呼叫端可以用 match 分辨，也可以直接印出中文訊息。沒有用 thiserror，跟微服務 PoC 的 Rust 版一致，所以 Cargo.toml 沒有任何相依套件。

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CapError {
    /// 連得到的節點沒過半（只有 CP 模式會發生）
    NoQuorum {
        reachable: usize,
        quorum: usize,
    },
    UnknownNode(String),
    /// 分組沒有剛好涵蓋每個節點一次
    InvalidPartition,
}

impl fmt::Display for CapError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::NoQuorum { reachable, quorum } => {
                write!(f, "只連得到 {reachable} 台，需要 {quorum} 台才過半")
            }
            Self::UnknownNode(node) => write!(f, "不存在的節點：{node}"),
            Self::InvalidPartition => f.write_str("分組必須剛好涵蓋每個節點一次"),
        }
    }
}

「落後」和「遺失」靠 partitioned_at 分開

恢復時輸掉的版本有兩種：分區前就存在、只是沒收到新資料的（CP 的 C 上的 x=1），以及分區期間被確認過、卻被蓋掉的（AP 的 A 上的 x=2）。partition() 記下 partitioned_at: Some(self.clock)，heal() 只把時間戳比它大的輸家算成遺失；沒有分區過時用 unwrap_or(self.clock)，什麼都不算遺失。

過半的算法，決定了 2 台不夠

quorum() 是 self.nodes.len() / 2 + 1：3 台要 2 台，2 台也要 2 台。所以 3 台切成 2 和 1 時多數派還能服務，2 台切成 1 和 1 時兩邊都不行。這就是雙機備援要加 witness 的原因。

    pub fn quorum(&self) -> usize {
        self.nodes.len() / 2 + 1
    }

AP 不丟資料：分清楚「落後」和「並行」

Cluster::heal() 的 last-write-wins 只看時間戳，所以分不出「C 只是落後」和「A、C 同時寫了不同的值」，後者就會默默丟掉一筆。src/merge.rs 改用 version vector：每個版本記下各節點寫過幾次，compare() 比較每一格，雙方各有一格比較大就是並行。reconcile() 只丟掉被別人看過的舊版本，並行的全部保留。

pub fn compare(a: &VectorClock, b: &VectorClock) -> Order {
    let nodes: BTreeSet<&String> = a.keys().chain(b.keys()).collect();
    let count = |clock: &VectorClock, node: &String| clock.get(node).copied().unwrap_or(0);
    let a_ahead = nodes.iter().any(|node| count(a, node) > count(b, node));
    let b_ahead = nodes.iter().any(|node| count(b, node) > count(a, node));
    match (a_ahead, b_ahead) {
        (true, true) => Order::Concurrent,
        (true, false) => Order::After,
        (false, true) => Order::Before,
        (false, false) => Order::Equal,
    }
}

/// 合併各節點手上的版本：已經被別的版本看過的丟掉，並行的全部保留。
pub fn reconcile(versions: &[Sibling]) -> Vec<Sibling> {
    let distinct: Vec<&Sibling> = versions
        .iter()
        .enumerate()
        .filter(|&(i, version)| !versions[..i].contains(version))
        .map(|(_, version)| version)
        .collect();
    distinct
        .iter()
        .filter(|version| {
            !distinct
                .iter()
                .any(|other| compare(&version.clock, &other.clock) == Order::Before)
        })
        .map(|&version| version.clone())
        .collect()
}

如果資料本身能設計成 CRDT，連衝突都不用處理。G-Counter 每台只累加自己那一格，合併時每格取最大值：

/// 在 node 那一格累加。G-Counter 只能增加；要能減少，就用兩個組成 PN-Counter。
pub fn add(counter: &GCounter, node: &str, amount: u64) -> Result<GCounter, MergeError> {
    if amount == 0 {
        return Err(MergeError::ZeroAmount);
    }
    let mut updated = counter.clone();
    *updated.entry(node.to_owned()).or_insert(0) += amount;
    Ok(updated)
}

/// 每一格取最大值。
pub fn merge_counters(counters: &[&GCounter]) -> GCounter {
    max_per_node(counters.iter().copied())
}

設計做法在哪裡
讀本地就等於讀到這一組的最新值寫入會同步複製給同組每一台，所以同組節點的資料永遠一致，不用再問其他節點；回傳 Option<&str>，借用叢集裡的字串，不用複製Cluster::read()
CP 連讀取也拒絕少數派手上的可能是舊資料，回舊資料就破壞一致性，所以讀寫都要過半read() 也呼叫 require_quorum()
輸入驗證分組要剛好涵蓋每個節點一次（兩邊排序後比對）、節點名稱要存在，否則回 Err，不會 panicpartition()、sorted()、reachable()
沒有外部套件Cargo.toml 沒有任何 [dependencies]，只用標準函式庫Cargo.toml
