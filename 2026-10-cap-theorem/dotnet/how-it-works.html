CAP 定理範例｜.NET 版運作說明

這頁說明 dotnet/ 裡的程式怎麼運作：怎麼在單一程序裡模擬 3 台節點和網路分區，CP 和 AP 兩種模式在分區、恢復時各發生什麼事，以及 AP 怎麼用 version vector 或 CRDT 合併才不會丟資料。用 .NET 10（C#）寫成，範例只用 BCL 的 System.Collections.Immutable，測試用 xUnit 2.9.3 ＋ coverlet.collector 6.0.4。

1. 全貌 2. 互動流程圖 3. 一筆寫入的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：兩組模組、一支示範程式、兩組測試

這份實作沒有真的網路，也不開任何 port。3 台節點 A、B、C 只是記憶體裡的資料，「網路分區」用「節點分組」表示：同一組內可以互相連線，跨組連不到。這樣每次跑的結果都一樣，不會被真實網路的抖動干擾。

Cluster.cs

模擬本體 ・ 被 Program.cs 和測試使用

Cluster record 和五個操作：Cluster.Create() 建立、Partition() 切斷網路、Write() 寫入、Read() 讀取、Heal() 恢復並合併。每個操作都回傳新的叢集（Write()、Heal() 用 tuple 連同結果一起回傳），舊的不變。

VersionVector.cs、GCounter.cs 等

AP 不丟資料的合併方式 ・ 被 Program.cs 和測試使用

version vector：VersionVector.Compare() 判斷兩個版本誰先誰後或並行，Reconcile() 保留並行的兄弟版本，NextVersion() 寫入新版本取代它們。CRDT：GCounter.Add()、Merge()、Total()。Order.cs 是比較結果，Sibling.cs 是帶時鐘的版本，PerNode.cs 是兩者共用的「每個節點一格」運算。

Program.cs

示範程式（top-level statements）・ ./run.sh demo

依序跑四段：3 台 CP、3 台 AP、只有 2 台的 CP、AP 不丟資料的兩種合併方式，把每一步的結果印出來。三種語言版本的輸出逐字相同。

ClusterTests.cs、MergeTests.cs

14 ＋ 18 個測試 ・ ./run.sh test

README 的每一條成功標準都對應一個測試：CP 少數派被拒、AP 兩側分歧、LWW 合併丟掉已確認的寫入、2 台 CP 全停擺、version vector 保留並行寫入、G-Counter 合併不丟累加等。

2. 互動流程圖：分區前、分區中、恢復後

點下面的按鈕切換情境。藍色虛線是寫入或複製實際走的路徑，紅色是被擋下的路徑，紅色長虛線是網路斷掉的位置。節點方框裡是那一台目前 x 的值。情境順序跟 Program.cs 一樣。

正常：沒有分區（CP、AP 都一樣）

呼叫
cluster.Write("A", "x", "1")
結果
成功。A、B、C 都有 x=1（時間戳 1）。
為什麼
沒有分區時只有一個分組，3 台都連得到。Write() 把新版本放進同組每一台的 store。這時 CP 和 AP 的行為完全一樣，差別只在網路斷掉之後。
模擬的簡化
同組內的複製是瞬間完成的。真實系統複製要花時間，AP 系統通常是非同步複製。
對應測試
Write_ReturnsNewCluster_WithoutChangingTheOriginal

CP：分區中，少數派那側停止服務

呼叫
cluster.Partition(["A", "B"], ["C"]) → cluster.Write("A", "x", "2") → cluster.Write("C", "x", "3") → cluster.Read("C", "x")
結果
A 寫入成功，複製到 B。C 的寫入和讀取都回 Result(Ok: false, Reason: "只連得到 1 台，需要 2 台才過半")。
為什麼
RejectWithoutQuorum() 比較「同組有幾台」和 Quorum（3 台要 2 台）。{A, B} 有 2 台，過半；{C} 只有 1 台，不過半。
代價
C 那側完全不能用。但沒有人讀到舊資料，兩邊的資料也沒有分歧。
對應測試
Cp_MinoritySide_RejectsWritesAndReadsDuringPartition、Cp_MajoritySide_KeepsServingDuringPartition

CP：恢復後，C 追上進度，沒有遺失

呼叫
cluster.Heal()
結果
三台都是 x=2，回傳的 Lost 是空的。
為什麼
合併時 x 有兩個版本：A、B 上的 x=2（時間戳 2）和 C 上的 x=1（時間戳 1）。x=2 比較新，勝出。x=1 在分區前（PartitionedAt = 1）就存在，輸掉只算「落後」，不算遺失。
對應測試
Cp_Heal_LosesNoAcknowledgedWrite

AP：分區中，兩邊照常服務，但資料分歧

呼叫
跟 CP 一樣：cluster.Write("A", "x", "2") → cluster.Write("C", "x", "3")
結果
兩筆寫入都成功。cluster.Read("A", "x") 讀到 2，cluster.Read("C", "x") 讀到 3。
為什麼
AP 模式下 RejectWithoutQuorum() 直接放行。寫入只會複製給同組的節點，所以兩組各有各的值。
代價
同一個 key 在兩邊的值不一樣。在 C 寫入之前讀 C，會讀到分區前的舊值 1。
對應測試
Ap_BothSides_AcceptWritesDuringPartition、Ap_Reads_DivergeDuringPartition、Ap_MinoritySide_ReadsStaleValueDuringPartition

AP：恢復後，last-write-wins 默默丟掉一筆已確認的寫入

呼叫
cluster.Heal()
結果
三台都是 x=3。回傳的 Lost 裡有 A 寫入的 x=2。
為什麼
x=2（時間戳 2）和 x=3（時間戳 3）都是分區期間寫的，last-write-wins 選時間戳大的 x=3。x=2 的時間戳 2 大於 PartitionedAt（1），所以算遺失。
代價
client1 早就收到「寫入成功」，之後 x=2 被蓋掉，沒有任何通知。
對應測試
Ap_HealWithLastWriteWins_DropsAnAcknowledgedWrite

延伸：只有 2 台的 CP，分區時整個服務停擺

呼叫
Cluster.Create(Mode.CP, "A", "B").Partition(["A"], ["B"]) → A、B 各寫一次
結果
兩邊都被拒絕：只連得到 1 台，需要 2 台才過半。
為什麼
Quorum 是 Nodes.Length / 2 + 1，2 台需要 2 台。網路一斷，哪一邊都湊不到。
意義
雙機備援如果選 CP，就要加一個第三方仲裁（witness）湊出第三票，見雙機備援 PoC。
對應測試
Cp_WithTwoNodes_CannotServeOnEitherSideOfAPartition

延伸：AP 恢復時改用 version vector，並行寫入兩個都留下

呼叫
VersionVector.cs：VersionVector.NextVersion([x1], "A", "2")、VersionVector.NextVersion([x1], "C", "3") → VersionVector.Reconcile([x2, x2, x3])
結果
兩個版本都保留：x=2（時鐘 {A:2}）和 x=3（時鐘 {A:1, C:1}）。讀 x 會拿到 2、3 兩個兄弟版本。
為什麼
每個版本記下「各節點寫過幾次」。VersionVector.Compare() 發現 {A:2} 在 A 那格比較大、{A:1, C:1} 在 C 那格比較大，兩邊互相沒看過對方，判定為 Order.Concurrent，誰都不能蓋掉誰。
接下來
應用層讀到兩個值，自己決定怎麼合併（例如合成 x=5），再用 VersionVector.NextVersion(siblings, "A", "5") 寫回。新時鐘 {A:3, C:1} 涵蓋兩個兄弟版本，下一次 Reconcile() 就只剩它。
代價
不會默默丟資料，但衝突沒有消失，只是交給應用層處理。Dynamo、Riak 是這種做法。
對應測試
Reconcile_KeepsBothConcurrentWrites、ResolvedVersion_ReplacesTheSiblingsAfterAnotherReconcile

延伸：AP 恢復時改用 CRDT 計數器（G-Counter），自動合併

情境
x 是一個計數器（例如按讚數）。分區期間 A 那側 +2、C 那側 +3。
呼叫
GCounter.Merge(GCounter.Add(GCounter.Empty, "A", 2), GCounter.Add(GCounter.Empty, "C", 3))
結果
{A:2, C:3}，總數 5。如果把總數當一般值、用 Cluster 的 last-write-wins 合併（Program.cs 的 LastWriteWinsTotal()），結果是 3，A 的 +2 不見了。
為什麼
每台只累加自己那一格，合併時每格取最大值，總數是各格相加。合併的順序、次數都不影響結果，所以不用人決定，也不會丟。
限制
只適用於能設計成 CRDT 的資料型別（計數器、集合等）。「把 x 設成某個值」這種覆寫操作沒辦法自動合併，還是要用 version vector。
對應測試
Counter_IncrementsOnBothSides_MergeWithoutLoss、LastWriteWins_OnACounterTotal_LosesAnIncrement

3. 一筆寫入的旅程

以分區中「client1 在 A 寫 x=2」為例，也就是 Program.cs 裡的 WriteAndShow(cluster, "A", "2", "分區")。從呼叫到印出結果，經過這些程式碼：

  1. 示範程式發出寫入
    Program.cs 的 WriteAndShow()

    呼叫 cluster.Write()，用 tuple 解構拿回新的叢集和結果，印出來後把新叢集回傳。被拒絕時 Write() 回傳的是原本那個叢集（this），所以照樣接回來用就好。

    static Cluster WriteAndShow(Cluster cluster, string node, string value, string stage)
{
    var (next, result) = cluster.Write(node, "x", value);
    Console.WriteLine($"  [{stage}] {node} 寫 x={value} → {(result.Ok ? "成功" : "拒絕：" + result.Reason)}");
    return next;
}
  2. 找出 A 連得到哪些節點
    Cluster.cs 的 Write() → Reachable()

    在 Groups 裡找出 A 所在的分組，這裡是包含 A、B 的 ImmutableHashSet<string>。節點名稱不存在時直接丟 ArgumentException。

    private ImmutableHashSet<string> Reachable(string node) =>
    Groups.FirstOrDefault(group => group.Contains(node))
    ?? throw new ArgumentException($"不存在的節點：{node}", nameof(node));
  3. CP 檢查有沒有過半，AP 直接放行
    Cluster.cs 的 Write() 開頭 → RejectWithoutQuorum()、Quorum

    CP 模式下，{A, B} 有 2 台，Quorum 是 2，過半，RejectWithoutQuorum() 回傳 null，放行。如果是 C 寫入，{C} 只有 1 台，這裡會回傳拒絕的 Result，被 is { } rejection 接住，Write() 直接回傳 (this, rejection)，叢集原封不動。CP 和 AP 的差別只有這一個判斷。

    var peers = Reachable(node);
if (RejectWithoutQuorum(peers) is { } rejection)
{
    return (this, rejection);
}

// ……

private Result? RejectWithoutQuorum(ImmutableHashSet<string> peers) =>
    Mode == Mode.AP || peers.Count >= Quorum
        ? null
        : new Result(Ok: false, Reason: $"只連得到 {peers.Count} 台，需要 {Quorum} 台才過半");
  4. 產生新版本，複製給同組節點
    Cluster.cs 的 Write() 後半

    時鐘加 1，建立 new Version("2", 2, "A")。用 ToImmutableDictionary 建立新的 Stores：同組的 A、B 用 SetItem 拿到「多了這筆」的新字典；C 在另一組，沿用原本的字典，所以 C 還是 x=1。最後用 this with { ... } 產生新的 Cluster，舊的不受影響。

    var clock = Clock + 1;
var version = new Version(value, clock, node);
var stores = Stores.ToImmutableDictionary(
    entry => entry.Key,
    entry => peers.Contains(entry.Key) ? entry.Value.SetItem(key, version) : entry.Value);
return (this with { Stores = stores, Clock = clock }, new Result(Ok: true));
  5. 印出結果
    Program.cs 的 WriteAndShow() 裡的 Console.WriteLine

    印出 [分區] A 寫 x=2 → 成功。被拒絕時印出 拒絕：加上 Reason。

  6. 網路恢復時合併
    Cluster.cs 的 Heal()

    把每個 key 在各節點上的不同版本收集起來，依時間由舊到新排好，最後一個（時間戳最大）勝出，寫回每一台。輸掉的版本如果是分區期間寫入的（時間戳大於 PartitionedAt），就放進 Lost 回傳。

    看 Heal() 的程式碼 
    public (Cluster Cluster, ImmutableArray<Version> Lost) Heal()
{
    // 每個 key 在各節點上的不同版本，依時間由舊到新排好；最後一個就是 LWW 的贏家
    var candidates = Stores.Values
        .SelectMany(store => store)
        .GroupBy(entry => entry.Key, entry => entry.Value)
        .OrderBy(group => group.Key, StringComparer.Ordinal)
        .Select(group => (Key: group.Key, Versions: group.Distinct().OrderBy(v => v.Timestamp).ToImmutableArray()))
        .ToImmutableArray();
    var merged = candidates.ToImmutableDictionary(c => c.Key, c => c.Versions[^1]);

    // 分區前就存在的舊版本輸掉只是「落後」，分區期間寫入的版本輸掉才是「遺失」。
    var since = PartitionedAt ?? Clock;
    var lost = candidates
        .SelectMany(c => c.Versions.SkipLast(1))
        .Where(v => v.Timestamp > since)
        .ToImmutableArray();

    var healed = this with
    {
        Stores = Nodes.ToImmutableDictionary(node => node, _ => merged),
        Groups = [Nodes.ToImmutableHashSet()],
        PartitionedAt = null,
    };
    return (healed, lost);
}

每種結果在哪一步決定

狀況在哪裡決定結果
節點名稱不存在第 2 步 Reachable()ArgumentException
CP，連得到的節點沒過半第 3 步 RejectWithoutQuorum()Result(Ok: false)，回傳原本的叢集
AP，分區中第 3 步直接放行成功，但另一組看不到這筆寫入

模擬刻意簡化了兩件事：同組內的複製是瞬間完成的，以及時間戳來自一個全域邏輯時鐘。真實的 AP 系統常用各台機器自己的時間做 last-write-wins，時間不準時，「誰被丟掉」會更難預測。

4. 啟動時發生什麼

Program.cs

top-level statements 依序呼叫 RunThreeNodes(Mode.CP)、RunThreeNodes(Mode.AP)、RunTwoNodes()。WriteAndShow()、ShowRead() 都是同一個檔案裡的 static 區域函式。每個情境都從 Cluster.Create() 重新開始，互不影響。沒有設定檔，也不讀環境變數。

Cluster.Create()

Cluster.cs 有兩個多載：Create(mode) 用預設的 A、B、C；Create(mode, params string[] nodes) 自訂節點，2 台的情境傳 "A", "B"。每個節點一個空的 ImmutableDictionary，只有一個分組（全部連通），Clock、PartitionedAt 用 record 參數的預設值 0、null。

ClusterTests.cs、MergeTests.cs

ClusterTests.cs：11 個 [Fact] 和 1 個 [Theory]（[MemberData(nameof(InvalidPartitions))] 跑 3 筆分組資料），共 14 個；共用情境由 Partitioned()、WrittenOnBothSides() 組出來，AssertEveryNodeReads() 檢查每一台讀到的值。MergeTests.cs：9 個 [Fact] 和 2 個 [Theory]（Compare_OrdersClocksByHappenedBefore 5 筆、Order_ToText_IsTheWordPrintedByTheDemo 4 筆），共 18 個；共用的 X1、X2OnA、X3OnC 是 demo 的同一個情境，Clock("A:1,C:1") 把文字轉成時鐘。兩個檔案合計 32 個。

public static Cluster Create(Mode mode) => Create(mode, "A", "B", "C");

public static Cluster Create(Mode mode, params string[] nodes) =>
    new(
        mode,
        [.. nodes],
        nodes.ToImmutableDictionary(node => node, _ => ImmutableDictionary<string, Version>.Empty),
        [nodes.ToImmutableHashSet()]);

5. 關鍵設計

叢集不可變：每一步都是一張快照

Cluster、Version、Result 都是 sealed record，集合一律用 ImmutableDictionary、ImmutableArray、ImmutableHashSet。每個操作都用 this with { ... } 回傳新的叢集，所以示範程式每一步都要接回新叢集；寫入被拒絕時拿回的就是原本那個。測試也因此可以同時拿「寫入前」和「寫入後」的叢集比較。

public sealed record Cluster(
    Mode Mode,
    ImmutableArray<string> Nodes,
    ImmutableDictionary<string, ImmutableDictionary<string, Version>> Stores,
    ImmutableArray<ImmutableHashSet<string>> Groups,
    int Clock = 0,
    int? PartitionedAt = null)

「落後」和「遺失」靠 PartitionedAt 分開

恢復時輸掉的版本有兩種：分區前就存在、只是沒收到新資料的（CP 的 C 上的 x=1），以及分區期間被確認過、卻被蓋掉的（AP 的 A 上的 x=2）。Partition() 用 PartitionedAt = Clock 記下當時的時鐘，Heal() 只把時間戳比它大的輸家算成遺失。

過半的算法，決定了 2 台不夠

Quorum 是一個算出來的屬性：Nodes.Length / 2 + 1。3 台要 2 台，2 台也要 2 台。所以 3 台切成 2 和 1 時多數派還能服務，2 台切成 1 和 1 時兩邊都不行。這就是雙機備援要加 witness 的原因。

public int Quorum => Nodes.Length / 2 + 1;

AP 不丟資料：分清楚「落後」和「並行」

Cluster 的 last-write-wins 只看時間戳，所以分不出「C 只是落後」和「A、C 同時寫了不同的值」，後者就會默默丟掉一筆。VersionVector.cs 改用 version vector：每個版本記下各節點寫過幾次，Compare() 比較每一格，雙方各有一格比較大就是並行。Reconcile() 先用 Sibling 自訂的相等比較去重，再只丟掉被別人看過的舊版本，並行的全部保留。

    public static Order Compare(IReadOnlyDictionary<string, int> a, IReadOnlyDictionary<string, int> b)
    {
        var nodes = a.Keys.Union(b.Keys).ToArray();
        var aAhead = nodes.Any(node => PerNode.Get(a, node) > PerNode.Get(b, node));
        var bAhead = nodes.Any(node => PerNode.Get(b, node) > PerNode.Get(a, node));
        return (aAhead, bAhead) switch
        {
            (true, true) => Order.Concurrent,
            (true, false) => Order.After,
            (false, true) => Order.Before,
            (false, false) => Order.Equal,
        };
    }

    /// <summary>合併各節點手上的版本：已經被別的版本看過的丟掉，並行的全部保留。</summary>
    public static ImmutableArray<Sibling> Reconcile(IEnumerable<Sibling> versions)
    {
        var distinct = versions.Distinct().ToImmutableArray();
        return [.. distinct.Where(version => !distinct.Any(other => Compare(version.Clock, other.Clock) == Order.Before))];
    }

如果資料本身能設計成 CRDT，連衝突都不用處理。GCounter.cs 每台只累加自己那一格，合併時每格取最大值（PerNode.Max()）：

    /// <summary>在 node 那一格累加。G-Counter 只能增加；要能減少，就用兩個組成 PN-Counter。</summary>
    public static ImmutableSortedDictionary<string, int> Add(ImmutableSortedDictionary<string, int> counter, string node, int amount)
    {
        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(amount), amount, $"G-Counter 只能加正數，收到 {amount}");
        }
        return counter.SetItem(node, PerNode.Get(counter, node) + amount);
    }

    /// <summary>每一格取最大值。</summary>
    public static ImmutableSortedDictionary<string, int> Merge(params ImmutableSortedDictionary<string, int>[] counters) =>
        PerNode.Max(counters);

設計做法在哪裡
讀本地就等於讀到這一組的最新值寫入會同步複製給同組每一台，所以同組節點的資料永遠一致，不用再問其他節點Read()
CP 連讀取也拒絕少數派手上的可能是舊資料，回舊資料就破壞一致性，所以讀寫都要過半Read() 也呼叫 RejectWithoutQuorum()
輸入驗證分組要剛好涵蓋每個節點一次、節點名稱要存在，否則丟 ArgumentExceptionPartition()、Reachable()
沒有外部套件範例專案沒有任何 NuGet 相依，只用 BCL 的 System.Collections.Immutable；xUnit、coverlet 只在測試專案。Directory.Build.props 開了 TreatWarningsAsErrors，警告一律當錯誤CapTheorem.csproj、Directory.Build.props
三種語言結果一致Python、Rust 版本照同一個模型實作，demo 的輸出用 diff 比對逐字相同PoC 的 README「怎麼跑」
拿真實系統對照用 Docker 起 3 台 etcd 和 3 台 Cassandra，拔掉第 3 台的網路重跑同一個情境，行為和這個模擬一致../verify/、PoC 的 README「實驗紀錄」
