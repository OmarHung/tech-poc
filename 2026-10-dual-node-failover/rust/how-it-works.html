雙機備援機制｜Rust 版運作說明

這頁說明 rust/ 裡的程式怎麼運作。裡面有三種雙機備援架構：A. 主備＋資料同步（兩台資料節點怎麼決定誰是主機、一筆寫入怎麼複寫到另一台）、B. 熱熱備援（兩台不通訊、都處理每一筆）、C. 上游指派（兩台不通訊、上游把工作派給其中一台）。用 axum 0.8 + tokio 1.54 寫 HTTP 服務，程序之間的呼叫和 gateway 的轉發用 reqwest 0.13，Rust 1.98（edition 2024）。行為、時間參數和 wire format 都跟 .NET 版一樣，同一支 verify/ 黑箱腳本可以直接驗。

1. 全貌 2. 互動流程圖 3. 一筆資料怎麼流動 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三種架構、六種程式

Cargo workspace 裡有六支執行檔和一個共用的 library crate（shared）。架構 A 用 node、witness、gateway；架構 B、C 用 upstream、worker、sink。

架構 A：主備＋資料同步

兩台資料節點跑的是同一支 node，誰當主機是執行時決定的。第三個程序 witness 不存資料，只負責仲裁。client 只認得 gateway。

Gateway

127.0.0.1:8100 ・ gateway/

client 的唯一入口。每 100 ms 問兩台節點的 /health，把請求轉給回報 role = primary 的那台（兩台都說是主機時選 epoch 較新的）。

Node a / Node b

127.0.0.1:8101、8102 ・ node/

資料節點。主機接受讀寫，並把每筆寫入同步複寫給備機；備機只接收複寫，同時注意主機是不是還活著。資料存在只能附加的 log 檔。

Witness

127.0.0.1:8103 ・ witness/

第三票。一次只把租約（lease）發給一台，每換一次主機 epoch 就加 1；另外記住「備機是不是同步中」，不同步就不准它升格。只存四個欄位。

架構 B、C：兩台不通訊

兩台 worker 跑同一支 worker，用 MODE 決定是熱熱備援還是被指派。兩台之間沒有任何連線，只認得上游和下游。

Upstream

127.0.0.1:8120 ・ upstream/

工作的來源。架構 B 用它的事件流水帳：只能附加、可以從任何位置重讀。架構 C 用它的任務佇列：每件任務租給一台 worker，租約到期就改派。

Worker a / Worker b

127.0.0.1:8121、8122 ・ worker/

MODE=hothot：讀全部事件、算帳戶餘額、送結果、存檢查點。MODE=dispatch：租任務、定時心跳、做事、寫結果、回報完成。

Sink

127.0.0.1:8123 ・ sink/

下游。以事件或任務編號去重：第一份結果套用（副作用發生），其他的只計數，分成重複、衝突（內容不同）、過期（attempt 比較舊）。

2. 互動流程圖：正常、故障與恢復

架構 A：主備＋資料同步

點按鈕切換情境。藍色虛線是正在發生的流量，紅色是失敗的連線，半透明是這個情境沒用到的部分；外框加粗、底色是主機。下方的數字來自 verify/ 對 Rust 版的實測（verify/results/rust-*.json）。

正常運作：a 是主機

選主
a 每 0.5 秒向 witness 續約一次（election.rs 的 ElectionWorker::renew()），租約 3 秒。b 一直收到 a 的複寫和心跳，所以不會去搶。
寫入
client → gateway → a。a 寫進自己的 log，再送給 b；b 回覆收到後，a 才回 200 給 client。
witness 記錄
租約在 a，epoch 1，備機同步中（b 可以接手）。
實測
4 個 client 同時寫，本機寫入 p50 1.61 ms、p99 4.39 ms；兩台之間加 10 ms 單程延遲時 p50 43 ms。

主機崩潰（kill -9）：b 接手

偵測
b 超過 3 秒沒聽到 a（NodeState::try_begin_candidacy()），向 witness 要租約。a 最後一次續約的租約這時也到期了，b 又是同步中，witness 就把租約交給 b，epoch 變 2。
切換
b 升格，先請 witness 記下「a 不同步」，之後就能單獨確認寫入（Solo）。gateway 下一次輪詢就改送 b。
資料
a 確認過的每一筆，b 都已經收到過（同步複寫的規則），所以沒有遺失。
實測
RTO 3.49 秒（租約 3 秒＋續約間隔＋gateway 輪詢），3,911 筆確認的寫入遺失 0 筆。租約改 1 秒時 RTO 1.23 秒。

舊主機加回來：a 變成備機

重新加入
a 重啟後一律以備機身分啟動，馬上收到 b 的複寫。請求裡的 epoch 2 比 a 記得的 1 新，a 就接受 b 是主機（NodeState::handle_replicate()）。
對齊資料
b 用 (index, epoch) 跟 a 的 log 比對。a 崩潰前寫進本機、但還沒送到 b 的幾筆（從沒回過 200）會被丟掉，再補上 b 的新資料（ReplicatedLog::append_from()）。
恢復可接手
a 追上後，b 用最新的版本號告訴 witness「備機同步中」，a 就又能接手了。
實測
從啟動到追上 0.17 秒（含程式啟動）。接著再砍 b，a 3.38 秒接手，兩次切換共 6,438 筆寫入遺失 0 筆。

網路分區：a 跟 b、witness 都斷了，但 client 還連得到 a

a 那邊
寫入送不到 b，等 1 秒後想請 witness 允許單獨確認，但 witness 也連不到，只能回 503。2.7 秒後 a 的租約到期，連讀取都停止。
b 那邊
3 秒沒聽到 a，向 witness 要到租約（epoch 2），開始服務。
網路恢復
a 看到 epoch 2，轉成備機，丟掉 8 筆從沒確認過的寫入，0.2 秒內兩邊資料一致。
實測
舊主機在斷線後確認了 0 筆，同時有兩台主機確認寫入 0 次，遺失 0 筆，b 3.03 秒接手。

同樣的分區，但沒有 witness（ARBITER=none，對照組）

a 那邊
只覺得「備機連不到」，沒有人可以問（NoArbiter 什麼都同意），就自己繼續確認寫入。
b 那邊
3 秒＋1.5 秒的優先權延遲沒聽到 a，就自己升格成 epoch 2（實測 4.99 秒，ElectionWorker::tick_without_witness()）。現在兩台都是主機。
網路恢復
a 看到 epoch 2 而下台，它在分區期間確認的寫入跟 b 的 log 對不上，整批被丟掉，client 不會收到任何通知。
實測
兩台同時確認寫入 1,377 筆，恢復後 3,429 筆已確認的寫入消失。這就是需要 witness 的原因。

witness 掛掉 6 秒

為什麼沒事
a 有兩種租約：witness 給的，和 b 給的「承諾」（b 每次接受複寫，就承諾 3 秒內不搶主）。只要其中一個有效，a 就能繼續服務，等於 3 票中拿到 2 票。
寫入
照常同步複寫到 b，不需要 witness 參與。
witness 回來
從 witness.json 讀回狀態（租約在 a），a 下一次續約就恢復。
實測
5,099 筆寫入 0 失敗，最長空窗 0.018 秒，a 從沒下台。

備機落後時主機又掛：寧可停機也不丟資料

第一步
b 先掛。a 的寫入等 b 等了 1 秒（實測卡住 1008 ms），請 witness 記下「b 不同步」後單獨確認（Solo），共 1,500 筆只有 a 有。
第二步
a 也掛了，接著 b 先回來。b 向 witness 要租約，witness 拒絕：「b 可能缺少已確認的寫入，等 a 回來」。gateway 找不到主機，回 503。
a 回來
witness 把租約還給 a（同一個 epoch），a 繼續服務，b 再從 a 追上。
實測
停機 11.1 秒（等 a 回來），遺失 0 筆。代價是可用性：要強制讓 b 接手只能人工介入並接受遺失。

架構 B、C：兩台不通訊

同一張圖，上游是事件流水帳（B）或任務佇列（C）。兩台 worker 之間沒有線。數字一樣來自 Rust 版的實測。

架構 B 正常運作：兩台都做每一筆

上游
事件流水帳，只能附加，可以從任何位置重讀（upstream/src/event_log.rs 的 EventLog::read()）。
worker
各自從自己的位置往後讀，依序更新帳戶餘額，每筆送一個結果（event-<編號> → 帳戶:餘額）。一批送完才存檢查點（HotHotWorker::process()）。
下游
同一個事件收到兩份，第一份套用、第二份記成重複（ResultStore::record()）。
實測
1,502 筆事件下游收到 2,596 份：沒有去重的話，副作用會多發生 1,094 次。

架構 B：a 被砍

發生什麼
什麼都不用做。b 本來就在處理每一筆，沒有偵測、沒有切換。
實測
下游最長 13 ms 沒有新結果，跟平常一樣；1,502 筆全部有結果、全部正確，兩台 0 次不一致。

架構 B：a 重啟，從檢查點補讀

補讀
a 讀回 checkpoint.json（讀到哪、各帳戶餘額），從那裡往後讀，停機期間的事件一筆不漏（HotHotWorker::load()）。
重送
被砍時已經送出、但還沒存進檢查點的那批會再送一次，下游當成重複忽略。
實測
停機 3 秒間的約 600 筆，從下重啟指令算起 0.12 秒補完（含程式啟動）；之後再砍 b，a 獨自繼續，最後的餘額跟正確答案完全一樣。網路斷 3 秒的情況，恢復後 0.22 秒補完。

架構 B 的錯誤做法：重啟時直接從最新的事件開始（START_FROM=latest）

發生什麼
a 的餘額少了停機期間的事件（HotHotWorker::skip_to_latest()），之後每一筆受影響帳戶的結果都跟 b 不同。下游先收到誰的就用誰的。
實測
不一致 406 筆；b 掛掉之後，下游套用了 593 筆錯誤結果。另一種錯是結果帶本機時鐘（DETERMINISTIC=false）：536 筆中只有 18 筆（3%）不一致，偶發，最難發現。

架構 C 正常運作：上游把每件任務租給一台

租任務
worker 向上游要任務（upstream/src/task_queue.rs 的 TaskQueue::lease()），拿到 {id, input, attempt, ttlMs}，租約 2 秒。
做事
每 1/3 個租約送一次心跳延長租約，做完先寫結果到下游，再向上游回報完成（DispatchWorker::run_task()）。
實測
每秒 5 件、每件 300 ms，兩台輪流接，任務延遲 p50 約 0.8 秒。每件做 3 秒（比租約長）時靠心跳延長，0 次被誤判改派。

架構 C：a 做到一半被砍

發生什麼
a 不再心跳，租約到期後上游把那件任務放回佇列最前面（TaskQueue::expire_overdue()），attempt 變 2，叫醒正在等的 b。其他任務不受影響。
實測
那件任務 2.35 秒後完成（租約 2 秒＋做事 0.3 秒），49 件全部正確。

架構 C：a 被凍結 4 秒（長時間 GC、VM 暫停）

發生什麼
任務改派給 b。a 恢復後還以為任務是自己的，但寫結果前先檢查自己的租約（LeaseTracker::is_valid()）：從送出請求的時間起算、提早 10% 結束，早就過期了，於是放棄。
實測
有檢查時 0 次重複寫入。不檢查的對照組（LEASE_CHECK=off）多寫 1 次，上游也收到 1 次過期的完成回報；這次剛好 b 的結果先到，下游才認得出那是過期的 attempt。
還剩的空窗
寫結果的逾時不超過剩下的租約，但如果剛好在「檢查完、請求已經送出」之後才被凍結，還是會晚到。所以下游的去重不能省。

架構 C：a 連不到下游，但心跳照常送到上游

問題
心跳一直成功，租約一直被延長，上游以為 a 好好的，另一台永遠接不到這件任務。心跳只證明 worker 活著，不證明它做得完。
解法
a 寫不出結果超過一個租約就放手（DispatchWorker::deliver()），心跳跟著停，租約到期後改派給 b。放手後先不接新工作，直到下游恢復：主迴圈每 0.1 秒用 GET /health 探一次下游（DispatchWorker::sink_back()），探得到才再去租任務。
為什麼要等
不等的話，a 會一直接自己做不完的任務；沒有積壓時它常常就是等最久的那台，會把剛放掉的那件又拿回來再卡一次。同程序測試裡拿掉這個檢查，同一件任務被改派了 9 次。
實測
那件任務 4.48 秒後由 b 完成：a 先試 2 秒，租約再 2 秒到期。斷線 5 秒期間 a 沒有再接任何任務（放手 1 次、改派 1 次），下游恢復後才又開始接。放手時如果主動通知上游，還能再快約 2 秒。

架構 C：a 做完、寫了結果，但回報不出去

發生什麼
a 到上游的連線斷了。上游收不到心跳和完成回報，租約到期後改派給 b，b 再做一次。a 的 DispatchWorker::complete() 一直重試，連線恢復後收到 409，記成過期的完成回報。
為什麼避免不了
先寫結果、再回報完成，兩步之間任何中斷都會這樣：這就是 at-least-once。所以下游一定要以任務編號去重。
實測
那件任務下游收到兩份，只套用一份；上游記了 1 次過期的完成回報。

3. 一筆資料怎麼流動

架構 A：一筆寫入怎麼複寫到另一台

以正常運作時的 PUT /kv/order-1 {"value":"paid"} 為例（a 是主機、同步複寫），從進門到回 200 經過這些程式碼：

  1. Gateway 轉給目前的主機
    gateway/src/lib.rs 的 forward()、gateway/src/tracker.rs 的 PrimaryTracker::current()

    PrimaryTracker::run() 在背景每 100 ms 輪詢兩台的 /health，choose() 挑出回報 primary 且 epoch 最大的。forward() 用 reqwest 原樣轉送 method、路徑、query 和 body，再把狀態碼、body 和節點的 X-Served-By 傳回去；節點回 503 或連不上時立刻再輪詢一次（nudge()）。

  2. 主機檢查自己的租約，寫進本機 log
    node/src/hosting.rs 的 put_kv() → kv.rs 的 KvService::put() → cluster/node_state.rs 的 NodeState::append_as_primary()

    在同一把鎖裡確認「我是主機而且租約還有效」，再附加到 log。下台（step down）也要拿這把鎖，所以不可能在下台之後還寫進去。

    pub fn append_as_primary(&self, key: &str, value: &str) -> Result<(LogEntry, Arc<PrimaryTerm>), ApiError> {

        .append(term.epoch(), key, value)
        .map_err(|error| ApiError::Internal(format!("could not write the log: {error}")))?;

    ReplicatedLog::append()（storage/replicated_log.rs）給它下一個 index 和目前的 epoch，由 LogFile::append() 寫成一行 JSON。std::fs::File 沒有使用者層的緩衝，write_all() 回傳時資料已經在作業系統手上，程序被砍掉也不會不見。

  3. 複寫迴圈被叫醒，送出這一批
    cluster/replication.rs 的 ReplicationWorker::replicate()

    notify_appended() 讓 tokio::sync::watch 的版本號加 1，叫醒等在 append_signal() 的複寫迴圈。它從 next_index 讀最多 256 筆（MAX_BATCH），連同前一筆的 (index, epoch) 送到 b 的 POST /internal/replicate。一次只送一批，回來才送下一批；沒有新資料時每 0.5 秒送一次空的當心跳。訊號是在讀 log 之前先訂閱的，所以兩者之間進來的寫入不會被漏掉。

  4. 備機檢查 epoch 和前一筆，寫進自己的 log
    b 的 NodeState::handle_replicate() → ReplicatedLog::append_from()

    epoch 比自己知道的舊 → 拒絕（被換掉的舊主機就是這樣被擋下的）。前一筆對不上 → 回 mismatch，主機往回找。對得上 → 附加，並記下「剛聽到主機」：這等於承諾 3 秒內不搶主，回覆裡的 promiseMs 就是這個承諾。

  5. 主機收到回覆：延長租約、推進進度
    ReplicationWorker::replicate() 後半 → PrimaryTerm::record_replicated()

    租約從「送出請求的時間」起算，再提早 10% 結束，所以主機一定比備機先放手。

  6. 等待中的寫入確認已經安全，回 200
    KvService::put() 等在 PrimaryTerm::wait_durable()

    這筆的 index 小於等於 b 已確認的 match_index，就可以回覆。如果 b 超過 1 秒都沒確認，改請 witness 同意「單獨確認」（try_go_solo()，同時在等的寫入共用一個請求）；witness 同意後 b 就不能升格，這時只存在 a 的寫入也算安全了。

    看 wait_durable() 的程式碼 
    pub async fn wait_durable(self: &Arc<Self>, index: i64, timeout: Duration, clock: &MonotonicClock) -> Result<(), ApiError> {
    let deadline = clock.now() + timeout;
    loop {
        let mut progress = {
            let inner = self.lock();
            if index <= inner.match_index || inner.peer_state == PeerState::Solo {
                return Ok(());
            }
            if self.ended.is_cancelled() {
                return Err(ApiError::Unavailable(
                    "lost the primary role before the write reached the standby".into(),
                ));
            }
            self.progress.subscribe()
        };
        let now = clock.now();
        if now >= deadline {
            if !self.try_go_solo().await {
                return Err(ApiError::Unavailable(
                    "standby unreachable and the witness did not allow going on alone".into(),
                ));
            }
            continue;
        }
        // Progress or the deadline: either way the loop looks again.
        let _ = tokio::time::timeout(deadline - now, progress.changed()).await;
    }
}

架構 B：一筆事件怎麼被兩台各自處理

以 POST /events {"account":"acct-1","amount":10} 為例，兩台 worker 都是 MODE=hothot：

  1. verify 把事件加進上游的流水帳
    upstream/src/lib.rs 的 append_event() → upstream/src/event_log.rs 的 EventLog::append()

架構 C：一件任務怎麼被指派

以 POST /tasks {"input":12} 為例，兩台 worker 都是 MODE=dispatch：

  1. worker 租到任務
    DispatchWorker::run() → WorkClient::lease_task() → upstream/src/task_queue.rs 的 TaskQueue::lease()

    worker 先記下送出請求的時間，再 POST /tasks/lease {"worker","waitMs":500}。上游先把到期的租約放回佇列最前面，再把最前面的任務交給這台 worker：attempt 加 1，租約從現在起 2 秒。佇列空的話最多等 0.5 秒，跟事件流水帳一樣是在鎖裡先訂閱再等：

  3. 先寫結果，再回報完成
    WorkClient::deliver() → ResultStore::record()；WorkClient::complete() → TaskQueue::complete()

    結果是 task-12 → 12^2=144，attempt 是這次租約的編號。回報完成會一直重試到上游回應為止；如果租約已經不是自己的（被改派了），上游回 409 並記成過期的完成回報，worker 記成 staleCompletions。同一個 worker、同一個 attempt 重送完成回報（例如上一次的回覆遺失）會再得到 200。兩步之間斷掉，任務會被改派再做一次，下游以任務編號去重。

4. 啟動時發生什麼

Witness

witness/src/main.rs：WitnessConfig::from_env() 讀 PORT、DATA_DIR、NODES、LEASE_TTL_MS → LeaseTable::open() 從 witness.json 讀回上次的狀態；如果之前有人持有租約，就當作它還持有一個完整的 TTL，因為重啟期間那台可能還在服務 → shared::http::bind() 綁 127.0.0.1 → witness::router()。

Node

node/src/main.rs：NodeConfig::from_env()（設定互相矛盾會直接啟動失敗，例如租約短於 3 次續約）→ Node::open()：開啟 log.jsonl（最後一行寫到一半就丟掉，前面壞掉就拒絕啟動）、NodeState::new() 從 epoch.json 讀回 epoch → spawn_workers() 用 spawn_supervised() 啟動 ElectionWorker::run() 和 ReplicationWorker::run()。一律以備機身分啟動，先等一個 TTL 才可能去搶主。

Gateway

gateway/src/main.rs：GatewayConfig::from_env() 讀 PORT、NODE_URLS、POLL_INTERVAL_MS → Gateway::new() 建立 reqwest client 和 PrimaryTracker → 背景跑 PrimaryTracker::run() → gateway::router()。剛啟動還沒輪詢到主機時，所有請求回 503。

Upstream

upstream/src/main.rs：UpstreamConfig::from_env() 讀 PORT、TASK_LEASE_TTL_MS → shared::http::bind() → Upstream::new() 建立 EventLog 和 TaskQueue → spawn_reaper() 用 spawn_supervised() 啟動每 0.1 秒的到期檢查 → Upstream::router()。資料只在記憶體。

Worker

worker/src/main.rs：WorkerConfig::from_env() 讀 MODE 等設定 → Worker::open()：熱熱模式先讀一次 checkpoint.json，讀不懂就拒絕啟動（不會默默從 0 開始），再建立 WorkClient → spawn_loop() 依模式只啟動 HotHotWorker::run() 或 DispatchWorker::run() 其中一個，一樣由 spawn_supervised() 看著。熱熱迴圈每次（重新）開始都從檢查點讀起；START_FROM=latest 時改成跳到上游最新的事件。

Sink

sink/src/main.rs：sink::port_from_lookup() 讀 PORT → ResultStore::new() → sink::router()。資料只在記憶體。

run.sh 用 exec 執行 target/release/<程式>，所以驗證腳本拿到的 PID 就是伺服器本身，kill -9 打到的就是它。

「重啟後先等一個 TTL」很關鍵：備機重啟前可能剛承諾過主機「3 秒內不搶」，重啟後記憶體裡的承諾不見了，所以把啟動當成「剛聽到主機」來處理。

// node/src/cluster/node_state.rs 的 NodeState::new()
// Count startup as having just heard from a primary: a node that restarts must not seek the lease
// while the primary may still be relying on the promise this node made before it went down.
let last_heard_from_primary = clock.now();

pub fn try_begin_candidacy(&self) -> bool {
    let mut inner = self.lock();
    let silence = self.clock.now().saturating_sub(inner.last_heard_from_primary);
    if inner.term.is_some()
        || inner.candidate
        || silence < self.config.lease_ttl + self.config.election_delay
    {
        return false;
    }
    inner.candidate = true;
    true
}

5. 關鍵設計

witness 只在三種情況下換主機

現任主機續約永遠成功；別人要拿租約，必須「租約已到期」而且「自己是同步中的備機」。換手時 epoch 加 1，成為 fencing token。新狀態先寫進 witness.json，寫成功才改記憶體。

// witness/src/lease_table.rs
pub fn acquire(&self, node: Option<&str>) -> Result<LeaseReply, ApiError> {
    let node = self.require_known(node)?;
    let mut inner = self.lock();
    let now = self.clock.now();
    if inner.state.holder.as_deref() == Some(node) {
        // Also after expiry: nobody else took over in between, so the holder still has the newest data.
        inner.expires_at = now + self.config.lease_ttl;
        return Ok(self.reply(&inner.state, None));
    }
    if let Some(holder) = inner.state.holder.as_deref() {
        if now < inner.expires_at {
            return Ok(self.reply(&inner.state, Some(format!("lease held by {holder}"))));
        }
        if !inner.state.standby_in_sync {
            let reason = format!("{node} may be missing acknowledged writes; waiting for {holder} to return");
            return Ok(self.reply(&inner.state, Some(reason)));
        }
    }
    // …… 換手：epoch + 1，新的備機（舊主機）先標成不同步，存檔後才生效
}

B：處理是決定性的結果只依事件和順序計算，兩台才會逐字相同；DETERMINISTIC=false 是反例。Ledger::apply() 回傳新的 ledger，不改原本的hothot/ledger.rs、HotHotWorker::format()
B：上游比自己短就停只存在記憶體的上游重啟後編號從頭開始，繼續處理會用舊編號送出錯的結果HotHotWorker::run() 的 page.last < ledger.offset
B、C：長輪詢不漏叫醒等新事件或新任務的 watch 訂閱是在鎖裡、檢查之前拿的；附加或改派也在鎖裡發訊號，所以兩者之間進來的不會被漏掉EventLog::read()、TaskQueue::lease()
C：worker 自己算租約跟架構 A 的主機一樣，從送出請求的時間起算、提早 10% 結束，所以一定比上游先放手dispatch/lease_tracker.rs 的 LeaseTracker::end()
C：改派的任務排最前面它已經等最久了。到期的任務由大到小編號一個個塞到最前面，最舊的排第一TaskQueue::expire_locked()
C：心跳固定間隔、每次有上限一次卡住的心跳不會把下一次推到租約之後。用 interval_at() 加 MissedTickBehavior::Skip，跟 .NET 的 PeriodicTimer 一樣DispatchWorker::heartbeat()
C：心跳和工作在同一個 task用 select! 一起跑，工作結束（或迴圈被中止）心跳就跟著停，不用另外 spawn 再記得取消；任何 panic 都會傳到 spawn_supervised()DispatchWorker::run_task()
C：做不完就放手，放手後先不接新工作心跳只證明活著，不證明做得完；連不到下游還一直心跳，任務會卡住。放手後先不接新工作，直到下游恢復：不然會一直接自己做不完的任務，甚至把剛放掉的那件又拿回來。只有「下游連不到」這個原因放手才會停接，租約過期而放手的不會DispatchWorker::deliver() 回傳 Delivery::SinkDown → run() 的 sink_down → sink_back()、WorkClient::sink_reachable()
B、C：下游以編號去重重複無法完全避免（at-least-once），只能讓它無害；內容不同的重複當成衝突記下來ResultStore::record()

還沒處理：斷電（log 只寫進作業系統，沒有 fsync）、gateway 本身的備援、各程序之間的身分驗證。複寫一次只送一批，所以同步寫入要 1 到 2 個網路來回。
