模組化單體轉微服務｜Rust 版運作說明

這頁說明 rust/ 裡的程式怎麼運作：有哪幾個程式、一個請求怎麼流動、拆分前後差在哪裡。框架是 axum 0.8 ＋ reqwest 0.13 ＋ tokio。

1. 全貌 2. 互動流程圖 3. 一個下單請求的旅程 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：三個程式

這是一個小型電商：catalog 管商品和庫存，orders 管訂單。原本兩個模組都在同一個程式（模組化單體）裡，這次把 catalog 拆成獨立的微服務。

gateway

127.0.0.1:8080 ・ gateway/

所有請求的入口（Strangler Fig 門面）。/products 開頭的請求依目前設定送給 monolith 或 catalog-service，其他一律送 monolith。設定可以在執行中切換。

monolith

127.0.0.1:8081 ・ monolith/

原本的模組化單體。orders 模組留在這裡；catalog 模組⚠已轉微服務，但保留在原位，用來對照和回滾。

catalog-service

127.0.0.1:8082 ・ catalog-service/

從單體拆出來的微服務。裡面的 catalog 模組跟單體那份是同一套程式碼，現在由它負責商品資料。

2. 互動流程圖：四個階段

點下面的按鈕切換階段，圖上藍色虛線是請求實際走的路徑，紅色是失敗的路徑，半透明的是這個階段沒用到的部分。

階段一：模組化單體

設定
monolith CATALOG_MODE=inprocess；gateway CATALOG_ROUTE=monolith
查商品
gateway → monolith 的 catalog 路由 → InMemoryCatalog::get()。全部在同一個程序裡，是一般的函式呼叫。
下單
gateway → orders 模組 → CatalogPort::reserve() → InMemoryCatalog::reserve() 扣庫存 → 建立訂單。
誰回應
X-Served-By: monolith。catalog-service 已經部署，但沒有任何流量。
實測 p50
查商品 0.091 ms、下單 0.104 ms

階段二：拆出 catalog，請求仍經由單體

設定
monolith 改成 CATALOG_MODE=remote 重啟（gateway 不用動）
查商品
gateway → monolith 的 catalog 路由 → HttpCatalogClient::get() → HTTP → catalog-service。路由程式碼沒變，只是介面背後換了實作。
下單
orders 模組照樣呼叫 CatalogPort::reserve()，但現在是 HTTP 呼叫 catalog-service 扣庫存。orders 的程式一行都沒改。
重點
單體不再持有商品資料，資料只有 catalog-service 那一份，兩邊看到的庫存一定一致。
實測 p50
查商品 0.126 ms、下單 0.141 ms（每多一跳約 +0.04 ms）

階段二：gateway 把 /products 直接切給 catalog-service

設定
PUT /admin/routes {"catalog":"service"}，執行中切換，不用重啟
查商品
gateway 直接送 catalog-service，不經過單體，少一跳。X-Served-By: catalog-service。
下單
不受路由影響，還是 gateway → orders → HTTP → catalog-service。
回滾
再呼叫一次 {"catalog":"monolith"} 就切回去，立即生效。負載下來回切 15 次，42,796 個請求 0 失敗。
實測 p50
查商品 0.093 ms（跟拆分前差不多）

階段三：catalog-service 故障

狀況
catalog-service 停機。這是拆分之後才有的新故障點。
查商品
不管路由指向哪邊都回 502：直連時 gateway 回 upstream unavailable，經單體時 monolith 回 catalog unavailable。
下單
orders 呼叫 catalog-service 失敗，回 502 catalog unavailable。
仍然正常
查既有訂單（GET /orders/1）還是 200，因為訂單建立時已經存了商品名稱和價格的快照，不需要再問 catalog。
錯誤細節
客戶端只看到一句話；連線失敗的細節（網址、原因）只用 eprintln! 寫進伺服器 log。

3. 一個下單請求的完整旅程

以階段二（CATALOG_MODE=remote）的 POST /orders {"productId":1,"quantity":2} 為例，從進門到回應經過這些程式碼：

  1. gateway 收到請求，決定送去哪裡
    gateway/src/lib.rs 的 proxy()、gateway/src/routing.rs 的 resolve()

    /orders 不是 catalog 路徑，所以一律送 monolith。轉發時會拿掉 Connection、Host 這類只屬於單一連線的標頭。

  2. monolith 解析 JSON
    monolith/src/modules/orders.rs 的 create_order()

    axum 把 body 解析成 CreateOrderRequest。JSON 格式錯、欄位型別錯（例如 "quantity":"2"）、少欄位，都會在這裡變成 400。

  3. orders 模組驗證輸入，再透過介面扣庫存
    monolith/src/modules/orders.rs 的 OrderService::place()

    先在本地驗證（數量要在 1–100、商品編號要是正整數），不合格就直接回 400，不會浪費一次網路呼叫。接著呼叫 self.catalog.reserve()，它只知道 CatalogPort 這個介面，不知道背後是本地還是遠端。

    pub async fn place(&self, product_id: u64, quantity: u64) -> Result<Order, OrderError> {
    validate_id(product_id, "productId")?;
    validate_quantity(quantity)?;
    let product = self.catalog.reserve(product_id, quantity).await?;
    let order = Order {
        id: self.next_id.fetch_add(1, Ordering::Relaxed),
        product_id,
        product_name: product.name,
        unit_price: product.price,
        quantity,
        total: product.price * quantity,
    };
    self.orders
        .write()
        .expect(POISONED)
        .insert(order.id, order.clone());
    Ok(order)
}
  4. 介面背後是 HTTP client，送出 HTTP 請求
    monolith/src/modules/catalog/remote.rs 的 HttpCatalogClient::reserve()

    送出 POST http://127.0.0.1:8082/products/1/reserve {"quantity":2}，逾時 2 秒。如果是階段一（inprocess），這一步換成直接呼叫 InMemoryCatalog::reserve()，接著跳到第 5 步的邏輯，只是在同一個程序裡執行。

  5. catalog-service 扣庫存
    catalog-service/src/catalog/routes.rs 的 reserve_product() → store.rs 的 InMemoryCatalog::reserve()

    在寫鎖裡「檢查庫存 → 建立一個新的 Product 取代舊的」，所以很多人同時下單也不會超賣（有測試：50 個並行請求搶 10 件，剛好 10 個成功）。舊的 Product 物件不會被修改。

    async fn reserve(&self, id: u64, quantity: u64) -> Result<Product, CatalogError> {
    validate_quantity(quantity)?;
    let mut products = self.products.write().expect(POISONED);
    let current = products
        .get(&id)
        .ok_or_else(|| CatalogError::product_not_found(id))?;
    if current.stock < quantity {
        return Err(CatalogError::insufficient_stock(id, quantity, current.stock));
    }
    let updated = Product {
        stock: current.stock - quantity,
        ..current.clone()
    };
    products.insert(id, updated.clone());
    Ok(updated)
}
  6. monolith 把 HTTP 回應還原成原本的結果
    monolith/src/modules/catalog/remote.rs 的 decode()

    成功就解析成 Product；400、404、409 還原成跟本地實作一模一樣的 CatalogError，所以 orders 分不出差別。連不上或其他錯誤一律變成「catalog unavailable」（502），細節只寫 log。

    看 decode() 的程式碼 
    async fn decode<T: DeserializeOwned>(
    sent: Result<reqwest::Response, reqwest::Error>,
) -> Result<T, CatalogError> {
    let response = sent.map_err(unavailable)?;
    let status = response.status();
    if status.is_success() {
        return response.json::<T>().await.map_err(unavailable);
    }
    let message = match response.json::<ErrorBody>().await {
        Ok(body) => body.error,
        Err(_) => format!("catalog-service returned {status}"),
    };
    Err(match status {
        StatusCode::BAD_REQUEST => CatalogError::InvalidInput(message),
        StatusCode::NOT_FOUND => CatalogError::NotFound(message),
        StatusCode::CONFLICT => CatalogError::InsufficientStock(message),
        _ => {
            eprintln!("catalog-service error {status}: {message}");
            CatalogError::Unavailable("catalog unavailable".into())
        }
    })
}
  7. 建立訂單，回 201
    OrderService::place()（第 3 步那段程式的後半）

    訂單會複製商品名稱和單價（快照），之後 catalog 改價或停機都不影響已成立的訂單。回應加上 X-Served-By: monolith（lib.rs 的 served_by layer）。

  8. gateway 把回應原樣轉回 client
    gateway/src/lib.rs 的 relay()

    狀態碼、標頭（含 X-Served-By）和內容照原樣傳回。

每種錯誤在哪裡被擋下

狀況在哪裡被擋回應
JSON 格式錯、型別錯、少欄位第 2 步 create_order()（axum 的 JsonRejection）400
數量不在 1–100、商品編號不是正整數第 3 步 validate_quantity()、validate_id()400
商品不存在第 5 步回 404 → 第 6 步還原成 NotFound404
庫存不足第 5 步回 409 → 第 6 步還原成 InsufficientStock409
catalog-service 連不上、逾時第 6 步 unavailable()502 catalog unavailable
gateway 連不到 monolith第 1 步 proxy()502 upstream unavailable

還沒處理的情況：第 5 步扣庫存成功，但回應在第 6 步之前逾時，monolith 會回 502、不建立訂單，可是庫存已經被扣了。正式上線前要補冪等鍵和補償機制（Saga / Outbox）。

4. 啟動時發生什麼

gateway

gateway/src/main.rs：讀 PORT、MONOLITH_URL、CATALOG_URL、CATALOG_ROUTE → build_app() 建立 HTTP client（逾時 5 秒、不跟隨轉址）和路由表 → 綁定 127.0.0.1:8080。

monolith

monolith/src/main.rs：讀設定（CATALOG_MODE 打錯會直接啟動失敗）→ 依模式決定 catalog 用哪個實作 → build_app() 組合 health、catalog、orders 路由 → 綁定 127.0.0.1:8081。

catalog-service

catalog-service/src/main.rs：讀 PORT → 載入三筆種子商品 → 掛上 catalog 路由和 health → 綁定 127.0.0.1:8082。

整個遷移的開關就在 monolith 的 main.rs 這幾行：同一個 CatalogPort，依環境變數換成不同實作。

let config = Config::from_env()?;
let catalog: SharedCatalog = match config.catalog_mode {
    CatalogMode::InProcess => Arc::new(InMemoryCatalog::seeded()),
    CatalogMode::Remote => Arc::new(HttpCatalogClient::new(&config.catalog_url)?),
};
// ……綁定 port……
axum::serve(listener, build_app(catalog, config.catalog_mode)).await?;

5. 關鍵設計

介面是拆分的接縫

orders 只依賴 CatalogPort 這個 trait，所以 catalog 從「同程序內」搬到「另一個程序」時，只要新增一個用 HTTP 實作同一個 trait 的 HttpCatalogClient。這就是為什麼起點必須是模組化單體：模組之間如果直接存取彼此的資料，就沒有這條接縫可以切。

// monolith/src/modules/catalog/port.rs
#[async_trait]
pub trait CatalogPort: Send + Sync {
    async fn list(&self) -> Result<Vec<Product>, CatalogError>;

    async fn get(&self, id: u64) -> Result<Product, CatalogError>;

    /// Atomically takes `quantity` units out of stock and returns the updated product.
    async fn reserve(&self, id: u64, quantity: u64) -> Result<Product, CatalogError>;
}

pub type SharedCatalog = Arc<dyn CatalogPort>;

gateway 切換路由：一次寫入，不影響進行中的請求

目前的路由存在 RwLock<CatalogRoute> 裡。PUT /admin/routes 只是寫入一個新值；每個請求進來時讀一次、決定上游之後就不再看它，所以切換那一瞬間正在處理的請求不會被中斷。

// gateway/src/routing.rs
pub fn resolve<'a>(path: &str, route: CatalogRoute, upstreams: &'a Upstreams) -> &'a str {
    match route {
        CatalogRoute::Service if is_catalog_path(path) => &upstreams.catalog,
        CatalogRoute::Service | CatalogRoute::Monolith => &upstreams.monolith,
    }
}

其他

設計做法在哪裡
錯誤跨網路後不變形錯誤訊息用文字傳遞，遠端 client 依狀態碼還原成同一個 CatalogErrorcatalog/error.rs、remote.rs
錯誤訊息不外洩客戶端只看到「catalog unavailable」，網址和原因只寫進 logremote.rs 的 unavailable()
標示誰回應monolith 和 catalog-service 用 middleware 幫每個回應加上 X-Served-Bylib.rs、catalog-service/src/main.rs 的 served_by
兩份 catalog 不會走樣兩份 catalog/ 檔案逐字相同（模組內一律用 super:: 相對路徑），測試也跟著程式一起複製，兩份各跑一次diff -r monolith/src/modules/catalog catalog-service/src/catalog
只聽本機三個程式都只綁 127.0.0.1；/admin/routes 沒有驗證，正式環境一定要加各自的 main.rs

6. 怎麼跑

# 在 rust/ 底下
./run.sh build                     # cargo build --release
./run.sh test                      # 35 個單元測試

# 手動啟動（三個終端機分別執行），這是階段二的設定
PORT=8082 ./run.sh catalog-service
PORT=8081 CATALOG_MODE=remote CATALOG_URL=http://127.0.0.1:8082 ./run.sh monolith
PORT=8080 CATALOG_ROUTE=monolith ./run.sh gateway

# 打打看
curl -i http://127.0.0.1:8080/products/1
curl -i -X POST http://127.0.0.1:8080/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":2}'
curl -i -X PUT  http://127.0.0.1:8080/admin/routes -H 'Content-Type: application/json' -d '{"catalog":"service"}'

# 或者一次跑完三個階段的自動驗證（在 PoC 根目錄）
