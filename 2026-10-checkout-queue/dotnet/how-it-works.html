結帳排隊機制｜.NET 版運作說明

這頁說明 dotnet/ 裡的程式怎麼運作：使用者怎麼排隊、什麼時候被放行，以及下單和付款怎麼保證不超賣、不重複扣款。框架是 ASP.NET Core 10 Minimal API，透過 StackExchange.Redis 3.4 在 Redis 7.4 上執行 Lua 腳本。

1. 全貌 2. 互動流程圖 3. 從排隊到付款的程式碼 4. 啟動時發生什麼 5. 關鍵設計 6. 怎麼跑

1. 全貌：一種程式開很多台，共用一個 Redis

只有一個程式 CheckoutQueue。要撐更多流量就多開幾台，全部指向同一個 Redis、同一個 SALE_ID，就是在服務同一場活動。程式本身不存任何狀態，排隊、名額、庫存、訂單全部在 Redis 裡。

CheckoutQueue（HTTP 端點）

127.0.0.1:8090（PORT，驗證時開 8091、8092 兩台）

收使用者的請求：排隊、輪詢、下單、付款。先檢查輸入格式，再呼叫對應的 Lua 腳本，最後把腳本的結果翻成 HTTP 狀態碼。排隊狀態除了輪詢，也可以連 /queue/tickets/{id}/events 改由伺服器推送（SSE）。根目錄 / 另外附一個操作頁，可以用滑鼠模擬一群顧客。

定時任務（每台都有）

SaleMaintenanceWorker，每 TICK_MS 一次

先釋放逾時未付款的訂單，再從隊頭放行使用者。每台都跑，不需要選出一台負責，因為每一步都是原子的。

Redis

127.0.0.1:6379（REDIS_URL，驗證時用 6390）

存所有狀態，並執行 Lua 腳本。Redis 一次只執行一支腳本，所以腳本裡的「檢查再寫入」不會被別的請求插隊。

2. 互動流程圖：一張 ticket 的一生

點下面的按鈕切換情境。藍色虛線是這個情境實際走的路徑，紅色是斷掉的路徑；Redis 裡亮起來的格子是這次被改到的資料，旁邊的藍字說明改了什麼。線上的藍字是被執行的 Lua 腳本。

排隊取號：POST /queue/join {"userId":"alice"}

做了什麼
join.lua 把序號 seq 加 1，建立一張 ticket，加到 waiting 的隊尾，並記下「alice 的 ticket 是這張」。回 201，內容有目前順位 position。
重複排隊
alice 重新整理、開第二個分頁、或網路重試，都會拿到同一張 ticket（200），一個人不會佔兩個位置。只有上一張已經結束（沒輪詢被跳過、放行逾時、訂單沒付款）才會發新的一張，排到最後。
已經賣完
架上是 0、也沒有未付款訂單時，直接回 409 sold_out，不用排了。

輪詢等待：GET /queue/tickets/{ticketId}

做了什麼
ticket.lua 先更新 ticket 的 lastSeenAt，再回傳狀態、順位和預估等待秒數。回應裡的 pollAfterMs 告訴客戶端多久後再問一次。
心跳
輪詢就是心跳。之後放行時，lastSeenAt 太舊的人會被跳過（見「排隊中離開」）。
打到另一台
這次請求打到 instance-1，結果跟打 instance-0 完全一樣，因為 instance 本身不存狀態。
預估等待
TicketView.From() 用「前面人數 ÷ 最近 10 秒的放行速度」算出 estimatedWaitSeconds。速度太低（每秒不到 0.01 人）時不給預估。

改用 SSE 推送：GET /queue/tickets/{ticketId}/events

連上時
TicketEvents.StreamAsync() 先在 TicketStreams 登記這條串流，再送一次目前狀態。之後不用再問，有變化伺服器會推。
放行那一刻
instance-0 的定時任務跑 admit.lua，放行的同時 PUBLISH 被放行的 ticket。兩台都有訂閱；這位使用者的串流連在 instance-1，所以由 instance-1 的 TicketPushWorker 推給他。實測放行到使用者知道 p50 3 ms，polling 是 480 ms。
順位
每台每秒用一支批次腳本 watch.lua 取回所有連線者的狀態，順位有變才推，推送頻率不會超過 polling。
心跳
串流開著就算在線上：watch.lua 順便更新 lastSeenAt。關掉分頁，串流斷了，心跳就停。
負載
同樣 1000 人，打到 app 的請求從每秒 931 次降到 9 次，app CPU 從 57.8% 降到 17.3%；名額回收得快，每秒放行人數從 4.7 變成 9.2。

放行：兩台的定時任務都在跑

做了什麼
admit.lua 算出還能放幾人：min(MAX_ACTIVE, 架上庫存) − 已放行人數，然後從 waiting 的隊頭一個一個取出，放進 active，並設定放行截止時間（ADMISSION_WINDOW_MS）。
兩台同時跑
兩台的計時器各自觸發，但 Redis 一次只跑一支腳本：先跑的放滿名額，後跑的算出來可放 0 人。十台同時跑，結果跟一台一樣（ConcurrencyTests.ParallelAdmitters_NeverExceedMaxActive）。
看庫存放行
剩 3 件就最多放 3 人進來。放進來卻一定買不到，只是換個方式告訴他「賣完了」。
順便做的事
同一支腳本也會收回逾時的名額（見「放行後沒下單」），並更新放行速度給預估用。

下單扣庫存：POST /checkout {"ticketId":"…","quantity":2}

檢查
checkout.lua 依序檢查：ticket 存在、這張 ticket 還沒下過單、狀態是已放行、還沒過放行截止時間、架上庫存夠。
寫入
全部通過才在同一支腳本裡：庫存 DECRBY 2、建立訂單放進 pending（付款截止時間 PAYMENT_WINDOW_MS）、ticket 標成 ordered、從 active 移出。回 201。
名額
從 active 移出後，下一輪放行就能再放一個人進來。
庫存不夠
還有未付款訂單時回 409 insufficient_stock（可能是 0 件），放行期間可以重試；完全賣完才回 409 sold_out。

連點結帳，兩個請求分別打到兩台

發生什麼
兩台 instance 幾乎同時執行 checkout.lua。Redis 一次只跑一支：先到的建立訂單、扣庫存（201）；後到的看到這張 ticket 已經有 orderId，直接回傳同一張訂單（200），不再扣庫存。
為什麼
ticket 本身就是 idempotency key，不需要客戶端另外產生。
數量不同
如果第二次送的數量不一樣，回 409 ticket_used。
實測
1000 人的搶購情境裡三分之一的人這樣連點，沒有任何人拿到兩張訂單；100 個已放行的人各點 3 次（共 300 個請求同時送出），剛好成立 50 張訂單、庫存剛好 0。

付款：POST /orders/{orderId}/pay

做了什麼
pay.lua 在同一個原子步驟裡：在 payments 加一筆扣款紀錄、訂單改成 paid、從 pending 移出。回 201。
重複付款
再送一次時訂單已經是 paid，回 200，不會再加扣款紀錄。所以 201 表示「這次扣的」，200 表示「之前已經扣過」。
太晚付款
超過付款截止時間就回 410 order_expired，並在同一支腳本裡把庫存放回去。
注意
付款是模擬的。串真實金流時，扣款發生在外部，不能放進 Redis 腳本，見第 3 節最後的說明。

排隊中離開（關分頁、手機休眠）

發生什麼
使用者停止輪詢，lastSeenAt 不再更新。輪到他時，admit.lua 發現已經超過 HEARTBEAT_TIMEOUT_MS 沒輪詢，把 ticket 標成 abandoned，名額直接給下一位。
為什麼要這樣
不這樣做的話，名額會放給一個已經不在的人，白白等到放行截止時間才收回。
回來了
他回來再呼叫一次 /queue/join，會拿到新的 ticket，排到最後。
設定限制
HEARTBEAT_TIMEOUT_MS 至少要是 POLL_INTERVAL_MS 的 3 倍，漏掉一兩次輪詢不會被誤判離開；設定違反時啟動會失敗。

放行後沒下單

發生什麼
過了放行截止時間還沒下單。下一輪 admit.lua 先把 active 裡截止時間已過的人標成 expired 並移出，空出的名額在同一輪就放給隊頭的下一位。
還沒輪到定時任務
在定時任務處理之前，輪詢和下單就已經會把它當成過期（ticket_status() 依當下時間判斷）。下單回 410 admission_expired。
之後
可以重新排隊，排到最後。

下單後沒付款

發生什麼
定時任務每一輪先執行 expire_orders.lua：pending 裡付款截止時間已過的訂單改成 expired，庫存 INCRBY 放回架上。
接著放行
同一輪接著執行 admit.lua，放回的庫存馬上就能放下一位進來。
不會放回兩次
付款請求和釋放同時發生時，兩支腳本都只處理還在 pending_payment 的訂單。誰先執行誰處理，另一支看到狀態已經變了就不動（ConcurrencyTests.PaymentsRacingTheExpirySweep_ReturnEachOrdersStockOnce）。
實測
1000 人搶 200 件的情境裡，有 23 筆訂單沒付款，庫存放回後被別人買走，最後 200 件全部付款。

3. 從排隊到付款：程式碼怎麼走

以 alice 從排隊一路到付款完成為例。HTTP 端點負責檢查輸入格式；所有會改變狀態的判斷都在 Lua 腳本裡，C# 只負責呼叫和翻譯結果。

  1. 排隊請求進來，先檢查格式
    Queue/QueueEndpoints.cs 的 MapQueueEndpoints()、ValidUserId()；Http/HttpExtensions.cs 的 ReadJsonAsync()

    不是 JSON、欄位型別錯、少欄位都在 ReadJsonAsync() 變成 400。userId 只接受 1–64 個英數字和 . _ - @，因為它會成為 Redis key 的一部分。

    app.MapPost("/queue/join", async (HttpRequest request, QueueStore queue, CancellationToken ct) =>
{
    var body = await request.ReadJsonAsync<JoinRequest>(ct);
    var result = await queue.JoinAsync(ValidUserId(body.UserId), ct);
    return result.Outcome switch
    {
        JoinOutcome.Created => Results.Created($"/queue/tickets/{result.Ticket!.TicketId}", result.Ticket),
        JoinOutcome.Existing => Results.Ok(result.Ticket),
        _ => throw ApiException.Conflict("sold_out", "sold out"),
    };
});
  2. C# 呼叫 Lua 腳本
    Queue/QueueStore.cs 的 JoinAsync() → Redis/SaleRedis.cs 的 RunAsync()

    JoinAsync() 產生新的 ticket 編號（Ids.New()）、取得目前時間，交給 RunAsync()。RunAsync() 把活動的 key 前綴 cq:{SALE_ID}: 放在第一個參數，其餘照順序接上，執行後用 ScriptReply.Parse() 把回覆解析成「結果代碼 ＋ 欄位」。

    public async Task<ScriptReply> RunAsync(SaleScript script, CancellationToken ct, params RedisValue[] args)
{
    var result = await _db.ScriptEvaluateAsync(script.Source, values: [_prefix, .. args]).WaitAsync(ct);
    return ScriptReply.Parse(script.Name, result);
}
  3. 在 Redis 裡排進隊伍
    shared/lua/join.lua（前面接著 common.lua 的共用函式）

    「查有沒有 ticket → 沒有就建立」在同一支腳本裡，同一個人同時送 20 次排隊也只會拿到一張（ConcurrencyTests.ParallelJoins_FromTheSameUser_YieldOneTicket）。

local current = redis.call('GET', key('user', userId))
if current and not ended(current) then
  if redis.call('HGET', key('ticket', current), 'status') == 'waiting' then
    redis.call('HSET', key('ticket', current), 'lastSeenAt', now)
  end
  return reply('existing', ticket_view(current, now))
end

if sold_out() then return reply('sold_out') end

local seq = redis.call('INCR', key('seq'))
redis.call('HSET', key('ticket', newId), 'userId', userId, 'seq', seq, 'status', 'waiting', 'joinedAt', now, 'lastSeenAt', now)
redis.call('ZADD', key('waiting'), seq, newId)
redis.call('ZADD', key('tickets'), seq, newId)
redis.call('SET', key('user', userId), newId)
return reply('created', ticket_view(newId, now))
  4. 輪詢：更新心跳、回報順位
    QueueStore.GetTicketAsync() → shared/lua/ticket.lua → Queue/TicketView.cs 的 TicketView.From()

    腳本更新 lastSeenAt，回傳 ticket 的狀態、順位（ZRANK ＋ 1）和最近的放行速度 admitRate。TicketView.From() 用它們算出預估等待秒數，再加上 pollAfterMs。

    改用 SSE 時，客戶端連 /queue/tickets/{ticketId}/events（Queue/TicketEvents.cs 的 StreamAsync()），之後由 Queue/TicketPushWorker.cs 推送：放行靠 Redis pub/sub 即時推，順位每秒用 QueueStore.WatchAsync()（watch.lua）批次更新一次。

  5. 定時任務：先釋放、再放行
    Maintenance/SaleMaintenanceWorker.cs 的 ExecuteAsync() → Maintenance/SaleMaintenance.cs 的 RunOnceAsync() → OrderStore.ExpireOrdersAsync()、QueueStore.AdmitAsync()

    每台用 PeriodicTimer 每 TICK_MS 跑一次。先跑 expire_orders.lua 放回逾時訂單的庫存，再跑 admit.lua，所以放回的庫存同一輪就能放行。Redis 暫時連不上時只記警告，下一輪重試；其他例外代表程式有 bug，會讓程式停下來。

    -- admit.lua：從隊頭放行，跳過沒在輪詢的人
local free = math.min(maxActive, stock()) - redis.call('ZCARD', key('active'))
local inLine = redis.call('ZCARD', key('waiting'))
local admitted, abandoned, scanned = 0, 0, 0
local admittedIds = {}
while admitted < free and scanned < maxScan do
  local head = redis.call('ZPOPMIN', key('waiting'))
  if #head == 0 then break end
  scanned = scanned + 1
  local id = head[1]
  local ticketKey = key('ticket', id)
  if now - tonumber(redis.call('HGET', ticketKey, 'lastSeenAt')) > heartbeatMs then
    redis.call('HSET', ticketKey, 'status', 'abandoned')
    abandoned = abandoned + 1
  else
    local deadline = now + windowMs
    redis.call('HSET', ticketKey, 'status', 'admitted', 'admittedAt', now, 'admissionExpiresAt', deadline)
    redis.call('ZADD', key('active'), deadline, id)
    admitted = admitted + 1
    admittedIds[admitted] = id
  end
end

-- 告訴每台 instance 誰剛被放行，連著 SSE 的人馬上就能收到
if admitted > 0 then redis.call('PUBLISH', key('admitted'), table.concat(admittedIds, ' ')) end
  6. 下單：檢查數量，呼叫腳本
    Orders/OrderEndpoints.cs 的 MapOrderEndpoints() → Orders/OrderStore.cs 的 CheckoutAsync()

    端點先檢查 ticketId 是 32 位小寫 hex（HttpExtensions.ValidId()）、quantity 在 1 到 MAX_PER_ORDER 之間。CheckoutAsync() 產生新的訂單編號，連同付款期限交給 checkout.lua。

  7. 在 Redis 裡扣庫存、建立訂單
    shared/lua/checkout.lua

    防超賣和防重複下單都在這裡：所有檢查和寫入在同一支腳本，中間不會有別的請求插進來。

  8. 付款：扣款紀錄和狀態一起改
    OrderStore.PayAsync() → shared/lua/pay.lua

    先看訂單狀態：已付款就回 already_paid，已過期就回 order_expired，剛好過了截止時間就在這裡把庫存放回去（expire_order()）。都不是才記扣款。

    看 pay.lua 的程式碼 
    if not o.status then return reply('order_not_found') end
if o.status == 'paid' then return reply('already_paid', order_view(id, now)) end
if o.status == 'expired' then return reply('order_expired', order_view(id, now)) end

if now >= tonumber(o.paymentExpiresAt) then
  expire_order(id, tonumber(o.quantity))
  return reply('order_expired', order_view(id, now))
end

redis.call('RPUSH', key('payments'), id)
redis.call('HSET', orderKey, 'status', 'paid', 'paidAt', now)
redis.call('ZREM', key('pending'), id)
return reply('paid', order_view(id, now))
  9. 把腳本結果翻成 HTTP 回應
    OrderStore.CheckoutAsync() 把結果代碼對應成 CheckoutOutcome；OrderEndpoints 再對應成狀態碼；Http/HttpExtensions.cs 的 UseApiErrors() 輸出錯誤

    成功的結果用 OrderView.From() 組成 JSON（欄位 camelCase、狀態值 snake_case、時間是 epoch 毫秒、沒有值的欄位不輸出）。錯誤一律是 {"error": "…", "code": "…"}。每個回應都加上 X-Served-By，標示哪台回的。

架上不夠，但還有未付款訂單checkout.lua409 insufficient_stock（放行期間可重試）
完全賣完join.lua、checkout.lua409 sold_out
付款逾時pay.lua410 order_expired
Redis 連不上UseApiErrors()、/health503 unavailable

付款是模擬的：扣款紀錄和狀態變更在同一支腳本裡，所以天生只會扣一次。串真實金流時扣款發生在外部，要改成「待付款 → 付款中 → 已付款」，把訂單編號當成金流商的 idempotency key，並且要對帳處理卡在「付款中」的訂單。

4. 啟動時發生什麼

1. 讀設定、連 Redis

CheckoutQueueConfig.FromEnvironment() 讀所有環境變數，數字超出範圍、SALE_ID 有奇怪字元、心跳逾時小於輪詢間隔 3 倍，都會直接啟動失敗。接著 ConnectionMultiplexer.ConnectAsync() 連 Redis，連不上也是啟動失敗。

2. 註冊服務

AddCheckoutQueue() 註冊 SaleRedis、QueueStore、OrderStore、AuditStore、SaleMaintenance（都是 singleton），加上定時任務 SaleMaintenanceWorker，並設定 JSON：數字不接受字串、狀態值用 snake_case、null 不輸出。

3. 初始化活動

SaleRedis.InitializeAsync() 執行 init.lua：只有活動第一次啟動才設定庫存（SETNX）。後啟動的 instance 或重啟時沿用目前的庫存，INITIAL_STOCK 不一樣就記一筆警告。

4. 掛上端點、開始計時

MapCheckoutQueue() 掛上 X-Served-By、錯誤處理、/health、排隊和訂單端點、/admin/audit、/admin/config、/admin/tickets，以及操作頁 /（MapDemoPage()）。推送服務 TicketPushWorker 在開始接請求之前就訂閱好放行通知，不會漏掉。app.Run() 之後開始聽 127.0.0.1，定時任務也開始跑。

// src/CheckoutQueue/Program.cs
var config = CheckoutQueueConfig.FromEnvironment();
var redis = await ConnectionMultiplexer.ConnectAsync(config.RedisUrl);

var builder = WebApplication.CreateBuilder(args);
builder.WebHost.UseUrls($"http://127.0.0.1:{config.Port}");
builder.Logging.AddFilter("Microsoft.AspNetCore", LogLevel.Warning);
builder.Services.AddCheckoutQueue(config, redis, TimeProvider.System);

var app = builder.Build();
var startedWith = await app.Services.GetRequiredService<SaleRedis>().InitializeAsync(config.InitialStock);
// ……庫存跟設定不同時記警告……
app.MapCheckoutQueue();
app.Run();

Lua 腳本和操作頁放在 PoC 根目錄的 shared/，三種語言版本共用同一份；.NET 版在建置時以內嵌資源打包進組件（CheckoutQueue.csproj 的 EmbeddedResource）。SaleScripts 第一次被用到時讀出來，每支前面都接上 common.lua，所以 key()、ticket_view()、expire_order() 這些共用函式每支腳本都能用。

5. 關鍵設計

每個狀態轉換一支 Lua 腳本

超賣和重複扣款的根源都是「檢查」和「寫入」之間被別人插隊。這裡每個狀態轉換（排隊、放行、下單、付款、釋放）都寫成一支腳本，Redis 一次只執行一支，所以不需要鎖、不需要重試，也不需要選主。代價是一場活動的資料必須在同一個 Redis 執行緒上，這就是承載上限（實測每支腳本約 11 µs，約每秒 9 萬次）。所有 key 都用 cq:{SALE_ID}: 當前綴，大括號是 Redis Cluster 的 hash tag，保證同一場活動的 key 落在同一個 slot。

放行規則：名額和庫存取小的

可放行人數 = min(MAX_ACTIVE, 架上庫存) − 已放行、還沒下單的人數

MAX_ACTIVE 就是削峰的旋鈕：外面排了多少人都不影響，同時在結帳的最多就這麼多。被未付款訂單保留的庫存不算架上庫存，等訂單逾時放回，下一輪就會再放人。

截止時間當下就算，定時任務只是收尾

放行和付款的截止時間一到，輪詢、下單、付款就會當成已過期，不用等定時任務。所以就算定時任務慢了或暫時連不上 Redis，使用者看到的狀態也和實際能做的事一致。

-- common.lua：狀態依當下時間判斷
local function ticket_status(t, now)
  if t.status == 'admitted' and now >= tonumber(t.admissionExpiresAt) then return 'expired' end
  if (t.status == 'waiting' or t.status == 'admitted') and sold_out() then return 'sold_out' end
  return t.status
end

時間由各台 instance 傳入

腳本不自己讀 Redis 的時鐘，而是由 C# 用 TimeProvider 取得目前時間傳進去。好處是測試可以換成 FakeTimeProvider，逾時相關的測試不用 sleep，跑起來又快又穩定；代價是各台 instance 的時鐘要同步（NTP）。時鐘差幾毫秒時，admit.lua 算放行速度的時間範圍至少取 1 秒，不會因此出錯（ConcurrencyTests.AdmitterWithAClockSlightlyBehind_StillCompletesItsPass）。

其他

設計做法在哪裡
ticket 就是 idempotency key同一張 ticket 重送下單回同一張訂單，客戶端不用另外產生 keycheckout.lua
編號不能被猜到ticket 和訂單編號都是 128-bit 隨機值（32 位小寫 hex）。拿到 ticket 就能結帳，所以不能從別人的編號推出來Ids.New()
預估等待時間前面人數 ÷ 最近 10 秒的平均放行速度，從開始有人排隊起算。第一版用指數移動平均，起步太慢、誤差很大，改掉了admit.lua 第 3 段、TicketView.From()
對帳不靠計數器從每一張訂單重新加總，檢查「架上 ＋ 保留中 ＋ 已售 = 初始庫存」、扣款紀錄有沒有重複audit.lua、AuditReport.Oversold、AuditReport.StockBalanced
Redis 斷線不是 500Redis 例外一律回 503 unavailable，客戶端知道要重試而不是放棄；定時任務只記警告，下一輪重試UseApiErrors()、SaleMaintenanceWorker
只聽本機只綁 127.0.0.1；/admin/audit、/admin/config、/admin/tickets 沒有驗證，只給 PoC 驗證用Program.cs、CheckoutQueueHosting.cs
操作頁不能被塞進別的程式碼每次請求產生新的 nonce，CSP 只允許帶這個 nonce 的 script 和 style，也只允許呼叫自己這台；顧客名稱等資料一律用 textContent 放進畫面Demo/DemoPage.cs、shared/demo/index.html
放行用推的，順位每秒更新SSE 串流只在放行時即時推（pub/sub），順位和預估每秒批次更新一次，推送頻率不超過 polling。pub/sub 漏掉訊息時，最晚下一秒的批次更新補上；15 秒沒東西送就送一行註解保活admit.lua、watch.lua、TicketPushWorker、TicketEvents
每個分頁看到同一條隊伍操作頁每秒向自己這台拿 /admin/tickets，通道只從這份資料畫，所以兩台、兩個分頁看到的一樣，也會記下同樣的事件。這個端點唯讀、不算心跳，旁觀的人不會幫顧客續命；心跳只由建立顧客的那個分頁送tickets.lua、TicketBoardStore.ListAsync()、shared/demo/index.html
操作頁只打自己這台從 :8092 的分頁對 :8091 加入的顧客下單，請求就打到 :8092，剛好示範跨 instance；不需要開跨網域（CORS）shared/demo/index.html
